# Projects Hub / Мира: запись и анализ телефонного звонка
## Самодостаточная постановка для аудита Claude

Дата проверки: 15 октября 2026. Результат этой работы — материал для аудита, не реализация и не подтверждение работоспособности на телефоне. Код, сервисы, настройки и репозитории при подготовке не изменялись; записи и платные модельные прогоны не запускались.

## 1. Что нужно владельцу

Менеджер разговаривает по телефону и не пересказывает разговор Мире второй раз. После разрешённой записи Мира получает сохранённый исходник, выделяет факты, договорённости, открытые вопросы и предложения задач, связывает их с нужными проектами. У каждого вывода должно быть проверяемое происхождение. Личный разговор не становится общедоступной проектной записью автоматически.

В существующем исследовании указаны Samsung и Redmi, небольшое число менеджеров и возможность индивидуальной настройки через ADB. Также описана одна плавающая кнопка Миры с управлением текущей записью, отдельным режимом будущих звонков и явным Stop. Точные модели/прошивки и подтверждённые аппаратные результаты пока не представлены. Это исходные условия прежнего исследования, которые нужно сверить перед реализацией.

**Задание Claude:** сначала проверить сценарии, текущий код и границы полномочий. Затем предложить минимальные изменения с максимальным reuse. Не создавать новый ASR, LLM-router, transport, брокер или параллельную базу «на всякий случай». Если существующий путь не подходит, предъявить воспроизводимый провал, его причину и минимальную альтернативу. Этот файл сам по себе не поручает реализацию, установку приложений, включение записи, передачу реальных разговоров провайдерам или изменение защищённых требований.

## 2. Главная развилка: три разных возможности

1. **Импорт завершённой записи.** Владелец выбирает уже существующий файл OEM-рекордера или другого разрешённого источника через Share/SAF. Это наиболее короткий проверяемый E2E: файл → приватный оригинал → существующая Мира → результат с provenance. Не зависит от успеха нового двухстороннего захвата.
2. **Прямая запись обеих сторон телефонного звонка.** Отдельный аппаратный пилот, например рассматривавшийся ShizuCallRecorder + Shizuku + scrcpy. Наличие соответствующего кода или выбранного audio source не доказывает звук обоих участников на Samsung/Redmi. Неудача пилота блокирует этот способ захвата и его форк, но не импорт готового файла.
3. **Обычный нативный микрофон Миры.** Требуется для устойчивого разговора с Мирой при фоне/блокировке. Это не право читать внутренний телефонный аудиоканал и не доказательство пункта 2.

Анализ **после окончания** звонка — минимальный первый продуктовый сценарий. Анализ **во время** звонка — самостоятельное последующее решение: нужна измеренная польза, безопасная граница источника, контроль задержки и завершения. Не делать его обязательной зависимостью импорта.

## 4. Что непосредственно видно в текущем коде

### 4.1. Есть основа для повторного использования

- В [web/src/bufferedReplay.ts](https://github.com/onedayonemasterpiece/projects-hub/blob/76bc5f2d84424f26bf3d0056687ae6a5dfcbde81/web/src/bufferedReplay.ts) уже есть `replayLocalVoiceSource`: shared `createLiveClient`, WSS, `audio_mode: buffered`, `client_source_id`, `microphone: false`, явные activity_start/end и PCM 16 kHz. Перед отправкой проверяется серверный source; terminal source не отправляется провайдеру повторно. При неподтверждённом disposition локальная копия сохраняется. Это существующий buffered-voice путь, **не готовый импорт произвольного AAC/Opus-файла**.
- В [web/src/offlineSources.ts](https://github.com/onedayonemasterpiece/projects-hub/blob/76bc5f2d84424f26bf3d0056687ae6a5dfcbde81/web/src/offlineSources.ts) есть IndexedDB, source/chunks, SHA-256 чанков, capture timestamp, восстановление прерванного capture/replay. Текущий формат — PCM16/16 kHz. Наличие chunk hash не равно готовой дедупликации повторного Share одного файла.
- В [store.py, create_source/get_source, строки 2850+](https://github.com/onedayonemasterpiece/projects-hub/blob/76bc5f2d84424f26bf3d0056687ae6a5dfcbde81/src/projects_hub/store.py#L2850) source повторно находится по actor_id/client_source_id; перенос того же client_source_id в другой conversation вызывает конфликт. Чтение проверяет владельца и membership. Новому source присваивается путь `.pcm`, а captured_at_ms берётся из текущего времени создания. Для импорта это недостаточно: время звонка необходимо хранить отдельно от времени загрузки, не выдумывая неизвестное.
- В [store.py, append_source_event, строки 3139+](https://github.com/onedayonemasterpiece/projects-hub/blob/76bc5f2d84424f26bf3d0056687ae6a5dfcbde81/src/projects_hub/store.py#L3139) сохраняются события и растёт transcript_revision; input_transcript дописывается в текст. Это не доказательство word-level timestamps, diarization или идентификации говорящих.
- В [store.py, commit_memory, строки 3224+](https://github.com/onedayonemasterpiece/projects-hub/blob/76bc5f2d84424f26bf3d0056687ae6a5dfcbde81/src/projects_hub/store.py#L3224) есть command result reuse, проверка durable transcript, archive, memory revision и хеши. Полный путь проверки доменных ACL нужно проследить через адаптер и tools; одна эта функция не доказывает все permissions.
- [Тесты source identity](https://github.com/onedayonemasterpiece/projects-hub/blob/76bc5f2d84424f26bf3d0056687ae6a5dfcbde81/tests/test_offline_source_identity.py) содержат сценарии переиспользования source, запрета перемещения между разговорами, terminal replay без повторной memory и receipt без раскрытия transcript/audio_path. При подготовке они прочитаны, **не запущены**.

### 4.2. Критичная граница reuse: оригинал нельзя присвоить mutable replay-файлу

[store.py:3084–3115, reset_source_for_replay](https://github.com/onedayonemasterpiece/projects-hub/blob/76bc5f2d84424f26bf3d0056687ae6a5dfcbde81/src/projects_hub/store.py#L3084) для незавершённого client-owned source открывает audio_path в режиме `wb`, удаляет source_events и обнуляет transcript/revision/audio counters. Terminal source защищён от такого reset.

**Вывод из кода:** безопасно переиспользовать механизм отправки/receipt только после проверки его семантики. Нельзя назначить единственный immutable оригинал звонка этому очищаемому audio_path. Нужна отдельная неизменяемая исходная сущность/attachment и связь с изменяемыми попытками декодирования/анализа либо доказанное минимальное расширение нынешнего source. Это не требование новой базы или отдельного сервиса.

Аналогично `archived`/`ephemeral_processed` — terminal состояния существующего live source, а не автоматически доказанная сохранность импортированного оригинала. Cleanup импорта должен опираться на подтверждение хранения нужного оригинала и согласованную политику, а не механически копировать текущий cleanup PCM-чанков.

### 4.3. Android и смежный рекордер

В [AndroidManifest.xml Projects Hub](https://github.com/onedayonemasterpiece/projects-hub/blob/76bc5f2d84424f26bf3d0056687ae6a5dfcbde81/android/app/src/main/AndroidManifest.xml) есть RECORD_AUDIO, но нет microphone foreground service; не объявлен ACTION_SEND/audio import intent. Это подтверждает отсутствие этих интеграционных точек в manifest, а не исчерпывающий аудит всех способов открытия файла.

[RecordingService.kt Record Idea Hub](https://github.com/onedayonemasterpiece/record-idea-hub/blob/35fb24ee20ef2845824032793dedb60aee7ea6fa/android/app/src/main/java/com/onedayonemasterpiece/recordideahub/RecordingService.kt) использует AudioRecord с VOICE_RECOGNITION, mono PCM и VAD/паузы, сохраняет M4a chunks. ## 5. Что установлено только как требование/предложение

- Нативный Android voice edge в общем versioned live-interaction, WebView как UI, один capture/transport на сессию.
- Логический разговор живёт независимо от конкретного сокета; bounded recovery, no-stale-replay, damaged-turn mutation fences и authoritative readback сохраняются.
- Opus между клиентом и backend, PCM на границе провайдера; compressed durable capture и неизменный импортированный оригинал.
- Готовый file import → приватный source → Мира → связанные заметки/кандидаты задач.
- Предварительное направление ShizuCallRecorder/Shizuku/scrcpy и, только после успешного hardware gate, небольшой форк с одним Mira-overlay и защищённым IPC.

**Не подтверждено:** завершённый импорт звонков в Projects Hub, рабочий native microphone lifecycle, универсальная двухсторонняя запись, аппаратная приёмка Samsung/Redmi, diarization с надёжными таймкодами, streaming-анализ звонка, реализация/приёмка Opus. Требование сжатия есть в §4.4; по истории обсуждения отдельное дополнение защищённого реестра было отменено. Claude должен сверить актуальный реестр, не считать этот файл разрешением его изменять.

## 6. Ограничения Android: официальные источники, проверено 15 октября

1. Android различает обычный input capture и захват телефонного канала. При конкуренции приложение может работать и получать тишину. Документация описывает захват voice call для privileged/pre-installed приложения с CAPTURE_AUDIO_OUTPUT; обычное RECORD_AUDIO само по себе такую возможность не предоставляет. Проверять `isClientSilenced`, route и наличие разборчивой речи **каждого** участника. Отсутствие тишины не доказывает две стороны. [Sharing audio input](https://developer.android.com/media/platform/sharing-audio-input).
2. AudioPlaybackCapture/MediaProjection — не универсальный телефонный рекордер: нужны разрешение пользователя и совместимые playback/capture policies; перечислены usages MEDIA, GAME, UNKNOWN. Нельзя считать «разрешил запись экрана» доказательством захвата VOICE_COMMUNICATION или любого звонка. [Capture video and audio playback](https://developer.android.com/media/platform/av-capture).
3. Для microphone foreground service нужны соответствующий type/permission и RECORD_AUDIO. Действуют while-in-use и background-start ограничения с отдельными исключениями. Продолжение уже начатой записи в фоне отличается от её нового запуска из фона/после reboot. Не обещать «сервис всегда сам стартует». [Foreground service types](https://developer.android.com/develop/background-work/services/fgs/service-types), [background-start restrictions](https://developer.android.com/develop/background-work/services/fgs/restrictions-bg-start).

Это технические ограничения, не юридическое заключение и не исчерпывающая таблица всех версий Android. Для целевых OS/targetSdk и OEM нужно проверить применимые правила. Shizuku/shell-пилот не следует объявлять эквивалентом обычного microphone permission; не обходить запреты доступа и не выдавать модели произвольный shell.

## 7. Минимальная целевая схема для проверки Claude

```text
Вариант A: выбранный владельцем завершённый файл через Share/SAF
Вариант B: доказанный на устройстве разрешённый recorder → finalized file
                  ↓
Одна авторизованная точка импорта + durable очередь
                  ↓
Private immutable original + source_id + hash + provenance + receipt
                  ↓
Проверяемая производная: decode/normalize → существующий buffered audio
                  ↓
Центральная Мира / текущий shared provider boundary
                  ↓
Сохранённая версия transcript и, только если доказано, сегменты/говорящие
                  ↓
Анализ Миры: факты, договорённости, вопросы, кандидаты изменений
                  ↓
Личная заметка/результат со ссылками на источник
                  ↓
Только разрешённые проектные сущности через текущие ACL + command_id + readback
```

Порядок transcript → анализ здесь логический. Если текущая Мира понимает исходное аудио и выдаёт transcript/анализ в одном взаимодействии, не добавлять отдельный распознаватель ради схемы. Не считать обычную input transcription полным дословным transcript с diarization: измерить полноту и пригодность на длинном двухстороннем разговоре. Уже принятый V32 text-structuring не запрещён; его фактическую реализацию и место в reuse проверить отдельно.

### Минимальные данные и происхождение

Названия полей ниже — предложение к аудиту, не утверждение о существующей schema:

- original_source_id, owner/tenant, import identity, способ получения, original SHA-256, bytes, MIME/container/codec, channels, sample rate, duration и completeness;
- recorded_at/timezone только при наличии основания, imported_at отдельно; неизвестное явно null/unknown;
- receipt хранения и версия производной, decode parameters, диапазоны исходного timeline, gaps/обрезка;
- transcript revision, model/provider/version при наличии, время обработки, coverage и ошибки;
- speaker labels только с evidence: «говорящий 1/2» не равны установленным людям; stereo channels не автоматически равны участникам; overlap/неразборчивое не заполнять догадками;
- analysis revision с точной ссылкой на transcript revision/original source; факт, мнение участника, договорённость и предложение Миры различаются;
- у проектного объекта source link + релевантный interval/цитата, actor и receipt принятия. Если точного interval нет, писать «таймкод не установлен», а не генерировать ложную точность.

## 8. Безопасность и полномочия

- Аудио — недоверенный цитируемый источник. Фразы «удали», «отправь», «создай», включая прежние слова владельца, не являются текущими командами приложению.
- **Проверить техническую границу исполнения:** существующий buffered mode предназначен и для собственных голосовых поручений. Одной инструкции в prompt недостаточно для гарантии. Claude должен найти или предложить минимальный source-only режим, deny-by-default capability/tool scope и отдельное актуальное разрешение на принятие кандидатов. Это обязательный вопрос, а не утверждение, что защита уже реализована.
- Импорт одного файла не разрешает автоматическую запись следующих звонков, каталог-watch, массовую загрузку старых записей или отправку третьим лицам. Отдельно выбрать и разрешить каждый расширенный режим.
- До реального пилота определить правила информирования/согласия участников для конкретной организации, юрисдикций и сценария. Нельзя утверждать универсальное «достаточно согласия одного» или «всегда нужны все». Технический checkbox не заменяет такую проверку.
- Указать, куда фактически передаётся аудио/текст, кто получает доступ и каковы правила хранения/удаления. Не передавать реальные разговоры внешнему провайдеру только потому, что удалось открыть файл.
- Исходник приватен; доступ коллег к проектной заметке не даёт права на весь звонок/личную ленту. Проверить ссылки, signed URLs, expiry, повторные запросы после отзыва membership, отсутствие transcript/PCM/телефонных номеров в обычной телеметрии.
- Если будет IPC с рекордером: явные адресаты, проверка вызывающего приложения/подписи или эквивалентная узкая авторизация, минимальный URI grant, недоступные посторонним start/stop, отсутствие произвольного shell/tool passthrough. Конкретный механизм должен соответствовать выбранной упаковке и подписи APK.

## 9. Возобновление, дедупликация и длинные звонки

Различать состояния: файл выбран → локально сохранён → загрузка завершена → оригинал подтверждён сервером → анализ начат → transcript сохранён → кандидаты сохранены → разрешённые mutations подтверждены. ACK транспорта не означает ни одну последующую стадию.

- Один stable import/source ID переживает restart. Повторный Share того же содержимого должен находить существующий результат в области того же владельца, а не объединять источники разных пользователей. Сравнение hash и metadata не должно раскрывать существование чужого файла.
- Дедупликация bytes, дедупликация попыток анализа и идемпотентность доменных effects — три отдельные проверки. Новая версия анализа допустима; повторное создание той же задачи из lost receipt — нет.
- Разрыв после upload/commit с неизвестным результатом: сначала readback/reconcile, затем retry только недостающего шага.
- Не очищать единственный оригинал при retry, ошибке decoder, таймауте Live, остановке UI или создании заметки. Ошибочная производная заменяется новой версией, исходник остаётся в рамках согласованного retention.
- Завершённость контейнера проверяется до анализа. Пустой/обрезанный/односторонний файл не маркируется «полный разговор». Не полагаться на событие «файл появился» как на finalized.
- Проверить лимиты длительности/bytes/decode work, memory, provider session и стоимость на реальных разрешённых тестовых образцах. Если нужна chunking-адаптация, сохранять общий source timeline, overlap/gap accounting и единое итоговое покрытие, не превращать каждый чанк в новую задачу.
- В текущем browser replay есть общий timeout 120 секунд; это факт кода, не доказанный бюджет для часового звонка. Нельзя исправлять длинные файлы произвольным увеличением таймаута без измерения, recovery и bounded resource contract.

## 10. Сжатие

Существующий §4.4 требует экономного транспорта/хранения с приёмкой; реализация не подтверждена. Для импорта сохранить исходные байты AAC/Opus/другого поддержанного формата. Decoder PCM и дополнительные сжатые версии — производные. Не делать lossy перекодирование оригинала по умолчанию и не терять каналы/таймлайн.

Проверить provider input/output contract в актуальной официальной документации перед реализацией; указанный в проектном договоре путь — Opus на клиентском участке, PCM на provider boundary, а не «отправить Opus прямо в Live». Согласовать codec/wire version и fallback явно. Codec не устраняет lifecycle, stale replay и command-idempotency проблемы.

На одинаковых разрешённых источниках сравнить исходный/PCM и выбранный compressed profile: полнота transcript, ошибки в именах/числах/обязательствах, атрибуция, задержка, размер, CPU/батарея и decoder failures. Численные критерии согласовать до acceptance; коэффициент экономии не объявлять гарантией.

## 11. Пилот записи: отдельный gate, без разработки форка заранее

Прежний аудит предложил ShizuCallRecorder + Shizuku + scrcpy, а затем GPL-форк с Mira-overlay. В этой подготовке исходники стороннего рекордера повторно полностью не аудировались, commit/лицензия/release не закреплены. Перед любым использованием Claude должен проверить официальный репозиторий, поддерживаемые ОС, конкретный source/ref, лицензии зависимостей и условия распространения. Не копировать код в другой продукт до проверки совместимости лицензий. Раздельные APK не считать автоматическим юридическим решением.

На явно разрешённом пилоте составить matrix: точная Samsung/Redmi модель, Android/OEM build, SIM/VoLTE/VoWiFi, входящий/исходящий, обычный динамик/громкая связь/Bluetooth, lock/background, reboot, потеря Shizuku/permission, недостаток места, interruption, waiting/переключение вызовов. Для каждой записи зафиксировать, слышны ли **оба** человека и полно ли покрыт разговор. Проверка кнопки/непустого файла сама по себе не PASS.

Если пилот пройден, минимальный UX: отдельные armed и current_recording; skip-current не меняет будущую политику; Start/Stop и реальный статус; один overlay, резервное управление уведомлением. Отказ записи виден, прежние файлы не удаляются. Не обещать overlay поверх любых системных экранов.

## 12. План аудита и ожидаемый результат от Claude

### Сначала статический аудит

1. Сверить current SHAs и требования, отделить historical receipts от runtime.
2. Проследить весь путь source/adapter/tools/ACL: способен ли imported source вызвать mutation как live команда? Где enforce source-only authority?
3. Составить reuse map: компонент, существующая функция, нужная минимальная доработка, тест/источник доказательства. Обязательно разобрать immutable original против reset_source_for_replay.
4. Проверить transcript/coverage/timestamps/speaker evidence и условия длинных файлов; не выдумывать diarization.
5. Сравнить importer готового файла с прямым capture. Дать независимые GO/NO-GO и блокеры.
6. Предложить минимальный ADR и изменения по этапам; не писать новый конвейер без измеренного провала нынешнего.

### Затем согласованный план проверок, не объявлять их уже пройденными

- Импорт разрешённого готового файла, оригинал/хеш/receipt доступны владельцу, результат привязан к нему.
- Повторный Share, upload interruption, restart до/после receipt, provider failure, повторный анализ: один original, контролируемые версии, ноль дублирующих effects.
- Пустое/одностороннее/обрезанное аудио, unsupported codec, шум/перебивания, длинный звонок: честный coverage/status, recoverable source.
- Записанный prompt injection и императивы участников не исполняют tools; проектная mutation требует текущего разрешения и readback.
- Два пользователя/тенанта, удалённый membership, проект без прав: ни утечки, ни cross-user dedup.
- Review конкретного предложения с interval/source и явным различением «собеседник сказал», «договорились», «Мира предлагает».
- Native mic lifecycle и прямой call capture проходят разные аппаратные gates; импорт не блокируется отсутствием второго.
- При необходимости compression A/B и долгий provider-run с ограниченной нагрузкой, источником до terminal receipt и измеренными budgets.

### Формат ответа Claude

Один отчёт:
1. Executive verdict по импорту, прямой записи и обычному голосу отдельно.
2. Findings по приоритету: доказательство `repo@SHA:path:line`, наблюдаемая проблема, влияние, минимальное исправление, regression test.
3. Матрица «реализовано / требуется изменение / не проверено» без смешивания docs и runtime.
4. Минимальная схема reuse и точные безопасные границы source/attempt/transcript/analysis/mutation.
5. Этапы и независимые acceptance gates, стоимость/нагрузка как измеряемые вопросы, список решений владельца.
6. Только после этого — рекомендация, можно ли начинать реализацию и с какого конкретного изменения.

## Итоговая рекомендация для проверки

Начать с аудита и минимальной интеграции **готовой разрешённой записи** с существующим private source/buffered audio/Мирой, сохранив оригинал отдельно от сбрасываемой попытки обработки и заблокировав исполнение команд из источника. Параллельно проектировать аппаратный пилот двухсторонней записи. Native mic, Opus и Shizuku не считать взаимозаменяемыми решениями. Качество transcript/атрибуции и пригодность текущей Миры для длинного звонка необходимо доказать, прежде чем добавлять новый распознаватель или pipeline.

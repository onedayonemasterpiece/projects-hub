# Projects Hub / Мира: запись телефонных разговоров на Android через Shizuku

**Дата:** 13 октября 2026  
**Тип:** продуктовый и технический анализ / feasibility и предварительное архитектурное решение  
**Статус:** исследование по коду и документации; **не реализовано, не проверено на реальных Samsung и Redmi**  
**Область:** стандартные входящие и исходящие телефонные звонки (SIM / VoLTE; VoWiFi проверяется отдельно), Android-клиент Миры, Projects Hub.

## 1. Краткий вывод

Для небольшого числа менеджеров, чьи телефоны можно индивидуально настроить через ADB, наиболее короткий путь — проверить **ShizuCallRecorder + Shizuku + scrcpy-server**, затем, после подтверждения записи **обеих сторон** на целевых Samsung и Redmi, сделать небольшой **GPL-форк рекордера** с одной плавающей кнопкой **Миры** и защищённым обменом состояниями/записями с Android-клиентом Projects Hub.

Это **не** попытка получить звонок через обычный микрофон. Android может отдавать обычному рекордеру тишину, пока активен телефонный звонок. Фактический пользовательский опыт: запущенный **Record Idea Hub** во время звонка записывал тишину. Это наблюдение согласуется с ограничениями Android; причина на конкретном устройстве пока не подтверждена логами.

**Продуктовая цель:** менеджер разговаривает по телефону, не пересказывает разговор повторно; после разрешённой записи Мира получает исходное аудио, извлекает договорённости и факты, формирует предложения по задачам и изменениям, связывает их с нужными проектами и сохраняет источник.

**Выбранное направление:** управлять записью из интерфейса Миры, не из отдельной звонилки; не требовать открытой Activity/экрана Projects Hub. Вызов определяется нативным компонентом, запись запускает отдельный процесс с полномочиями Shizuku, а backend Projects Hub остаётся единственной границей Live-модели и предметных операций.

Это **решение о направлении пилота**, а не заявление о совместимости всех Android-устройств.

## 2. Исходные продуктовые условия

- Целевые устройства: **Samsung и Redmi**, не одна конкретная модель или прошивка.
- Менеджеров **немного**; администратор может один раз провести настройку каждого устройства через **ADB** и обеспечить поддержку после обновлений/перезагрузок.
- Возможность решать, **какой звонок записать, а какой нет**, важнее бесконтрольной записи всех вызовов.
- У Миры должна быть **одна плавающая кнопка аудио поверх приложений**, доступная при телефонном звонке; её можно перетащить к краю, а для закрытия — в отдельную зону удаления.
- Режим записи не должен зависеть от того, находится ли WebView/Projects Hub на переднем плане.
- Надо переиспользовать код/SDK там, где возможно; избегать второго аудиоконвейера, второй смысловой модели и тяжёлой инфраструктуры.
- Аудио и результаты должны быть приватными по умолчанию; перенос фрагментов в общие проекты — только по действующим правам и разрешённому намерению.

| --- | --- | --- | --- |

## 5. Целевая модель управления записью: плавающая кнопка Миры

Кнопка отображается средствами **нативного Android** поверх обычных приложений (`WindowManager` + `TYPE_APPLICATION_OVERLAY`); **не** как элемент PWA/WebView. Звонок должен захватываться независимо от того, открыта ли Activity Projects Hub.

**Разделить два независимых признака:**
1. `armed` — разрешена ли автоматическая запись **новых** звонков.
2. `current_call_recording` — реально ли записывается **текущий** звонок.

Это позволяет не путать «Мира включена» с «каждый звонок записывается», а «остановить эту запись» — с «отключить все будущие звонки».

### Рекомендуемые действия

| Ситуация / жест | Результат |
| --- | --- |
| Короткое нажатие вне звонка | Переключает `armed`. Включено — готовность автоматически записывать новые звонки, выключено — не записывать. |
| Пришёл звонок, `armed=true` | Нативная логика определяет вызов, начинает запись; кнопка показывает **только подтверждённое** состояние захвата. |
| Пришёл звонок, `armed=false` | Ничего не записывается; доступна заметная команда «Записать этот звонок» через пузырёк/уведомление. |
| Нажатие во время звонка | Запуск или остановка **текущей** записи, не меняя автоматически `armed` для следующих звонков. |
| «Пропустить этот звонок» при `armed=true` | Прекратить / не начинать запись *только этого вызова*, не возобновлять её самопроизвольно в рамках того же вызова; будущие звонки сохраняют общий режим. |
| Перетащить кнопку | Свободное перемещение по X/Y, притяжение к ближайшему краю, сохранение позиции с учётом экрана и вырезов. |
| Перетащить в зону закрытия | **Явно** остановить текущую запись (если есть), снять `armed` и убрать overlay; не удалять уже сохранённое аудио. При активной записи предусмотреть короткое подтверждение/достаточно явную зону и обратную связь. |
| Оверлей скрыт / система запретила показ | Управление через нативное уведомление и экран приложения; **никакой скрытой активной записи без индикатора**. |

Для режима автоматической записи обязательно видимое состояние согласия/информирования участников согласно применимому законодательству; функция управления им в рекордере не заменяет юридических требований.

**Машина состояний (минимум):** `DISARMED`, `ARMED_READY`, `STARTING`, `RECORDING`, `PAUSED_OR_SKIPPED_CURRENT`, `FINALIZING`, `FAILED`, `HIDDEN`. `ARMED_READY` никогда не отображается как `RECORDING`. Нельзя показывать «успешно записано» при пустом файле или отказе Shizuku.

Внутри Projects Hub действует уже описанная [voice island UX](../product/13-ui-floating-islands.md). Системный плавающий bubble — **дополнительное Android-only управление**, а не второй параллельный Live-разговор и не изменение PWA-интерфейса. Внешний вид соответствует Мире, но функция — управлять телефонным аудиозахватом.

## 6. Минимальная архитектура без второго агента

```text
Android (Samsung / Redmi)
  Событие входящего/исходящего звонка
     └─ GPL-форк ShizuCallRecorder
          ├─ локальная политика armed / skip-current
          ├─ один overlay «Мира» + уведомление
          ├─ Shizuku (ADB/shell) → scrcpy-server → аудио
          └─ финализированный Opus/AAC-файл + событие завершения
                           │ защищённый IPC / SAF
                           ▼
       Android-клиент Projects Hub (имеющийся native shell + WebView)
          └─ durable upload queue, retry, дедупликация, статусы
                           │ авторизованный HTTPS/WSS
                           ▼
       Projects Hub backend (DevCoveer)
          ├─ private source + provenance + ACL
          ├─ адаптация файла в существующий buffered-audio путь
          └─ shared live-interaction → центральный Gemini Live / Мира
                 ├─ input transcription / цитируемые интервалы
                 ├─ выявление фактов, договорённостей, поручений
                 └─ typed tools + permissions + readback
                           ▼
       личная лента Миры и, только при разрешении, объекты проектов
```

**Ключевой запрет:** не добавлять второй ASR/LLM-router/agent и самостоятельный VAD в Projects Hub. Использовать [текущий one-agent backend](../product/04-architecture.md), [сохранность источника](../product/10-conversation-memory.md), [единую личную ленту и ACL](../product/20-basic-collaboration-and-personal-timeline.md).

- **Приём аудио.** Сначала весь завершённый Opus/AAC; при необходимости decode → PCM и отправка в **уже существующий** buffered-audio/Live контур. Внутренние чанки — транспортная механика, не самостоятельные решения об окончании разговора. Live-обработка «во время звонка» — отдельная следующая стадия, не блокирующая MVP.
- **Доставка.** Долговечная локальная очередь, offline/retry, идемпотентный `source_id`, привязка к устройству/пользователю, контроль окончания записи. Сигнал о завершении помогает быстро импортировать файл, периодическая сверка каталога SAF покрывает пропущенные сигналы.
- **Граница прав.** Два приложения обмениваются только определёнными командами/событиями через защищённый IPC (например, signature-permission + явные адресаты); **не** делаем exported recording service без авторизации и не допускаем команд произвольного shell от Live-модели.
- **Данные.** Первичный телефонный разговор остаётся личным источником. Идентификаторы звонка, time range, статус захвата и ссылка на аудио — provenance. Номер/контакт может быть неизвестен на некоторых Android. Извлечённое решение должно ссылаться на фрагмент речи и отличать предложение от согласованного решения. Неподтверждённые или внешние действия выполняются только по текущим продуктовым правилам полномочий/подтверждения.
- **Экран.** Фоновое «открытие Projects Hub» не нужно и ненадёжно из-за ограничений Android на запуск Activity. Нативный call detection и recorder service должны работать при закрытом UI. «Приложение открыто» и «разрешена запись» — разные понятия.
- **Privacy.** Не помещать сырые записи в Git, технические логи или доступную всем проектную заметку. Сохранять источник в соответствующем приватном storage с ограниченным retention; учитывать потерю телефона и отзыв доступа.

### Кому принадлежит оверлей

Для первой поставки **один owner окна — GPL-форк рекордера**, поскольку он уже управляет call lifecycle и знает факт записи; визуально bubble называется «Мира». Android-клиент Projects Hub предоставляет настройки, статусы и просмотр результатов. **Второй параллельный оверлей в нём не создаём**. При переносе реализации внутрь одного APK позже нужен отдельный ADR и лицензионная ревизия.

## 7. Лицензирование и переиспользование

- **ShizuCallRecorder** — GPLv3-or-later с дополнительными условиями `7, которые в [LICENSE](https://github.com/kitsumed/ShizuCallRecorder/blob/main/LICENSE) требуют для форка сменить название и package ID, явно обозначить fork/edited clone и дать видимую атрибуцию со ссылкой на оригинал. Использовать исходный GPL-код в закрытой сборке Миры без соблюдения лицензии **нельзя**.
- **Shizuku SDK / scrcpy** — отдельные зависимости со своими лицензиями (в основных проектах Apache-2.0); конкретные модули/сборки и уведомления необходимо сверить при включении. Они не превращают автоматически GPL-код форка в проприетарный.
- **Предложение:** распространять форк как **отдельный GPL-компонент** с исходниками и уведомлениями, сохранять Projects Hub Android + backend отдельными продуктами со строго ограниченным IPC. Раздельные APK сами по себе не гарантируют отсутствие вопросов о комбинированном произведении: юридическую границу и условия распространения следует отдельно проверить.
- Для небольшого внутреннего пилота обязанности GPL относительно распространения отличаются от передачи APK внешним людям; не считать «внутри команды» универсальным освобождением от лицензии.

Это инженерный анализ, не юридическое заключение.

## 8. Риски, эксплуатация, безопасность

1. **Совместимость OEM:** наличие пунктов `VOICE_CALL` в коде **не гарантирует** звук двух сторон на конкретной Samsung/Redmi-прошивке, особенно VoWiFi/Bluetooth. Проверяется запись, а не только старт сервиса.
2. **Shizuku lifecycle:** при запуске через ADB без root возможна необходимость повторного запуска после перезагрузки; автоуправление рекордера может задержать начало записи. Для важных разговоров нужна диагностика `READY / NOT_READY`, а не молчаливый успех.
3. **Overlay:** разрешение `SYSTEM_ALERT_WINDOW`, спецэкраны и экран блокировки, фоновые ограничения Redmi/HyperOS и One UI, энергосбережение, свайпы и случайное закрытие. Уведомление — обязательный fallback.
4. **Юридические требования и приватность:** до захвата обеих сторон обеспечить необходимые уведомления/согласия, в частности учитывать различия юрисдикций. По умолчанию безопасный `DISARMED` до явного выбора пользователя; исключения по контактам/личным звонкам.
5. **Перепутанные звонки:** ожидание/переключение между вызовами, конференции, параллельные события, повторный звонок на ту же линию; не объединять разных собеседников в единый источник без маркировки.
6. **Неполное аудио:** фрагмент тишины, пустой файл, обрыв pipe, недостаточно места. Контролировать размер, наличие аудиосигнала, длительность, финализацию контейнера; отсутствие тишины **не доказывает**, что оба собеседника слышны.
7. **Нагрузка и обработка:** звонки могут быть длинными; не отправлять их как один огромный неконтролируемый запрос; сохранить source до подтверждённой обработки и readback. Не удалять оригинал только потому, что UI показал результат.

## 9. Короткий план до продуктового результата

### Этап 0. Проверить гипотезу записи (без новой разработки)

На **одном Samsung и одном Redmi** установить официальные Shizuku + ShizuCallRecorder, провести настройку через ADB и включить подходящий `VOICE_CALL`-источник. Проверить **обе стороны** на реальных входящих/исходящих звонках и получение завершённого файла в SAF-папке.

Проверить вызовы после перезагрузки, с заблокированным экраном, на громкой связи и с гарнитурой; VoWiFi — если используется. Фиксировать Android/One UI/HyperOS version и результаты. Если хотя бы один телефон не проходит, искать исправление на конкретном устройстве, а не объявлять Android универсально поддержанным.

**Gate 0:** обе стороны разборчиво слышны, а ошибки записываются и видны пользователю. Иначе форк не разрабатывать.

### Этап 1. Минимальный GPL-форк с Mira-управлением

- Изменить package/name/branding, выполнить GPL-атрибуцию.
- Реализовать `armed`, управление текущим звонком и `skip-current` в существующем decision engine; не ломать прежнюю авто-/ручную запись.
- Переделать **один** существующий Android overlay: двусторонний drag, snap to edge, drop-to-close, состояния и доступность.
- Добавить защищённый API статуса/команд, не экспортировать неограниченные service intents, внедрить сигнал «файл финализирован».
- Минимизировать работу с ADB/Shizuku — переиспользовать работающий pipeline и механизмы запуска, не изобретать новые.

### Этап 2. Интеграция с Projects Hub

- Android shell подписывает события к device identity, принимает конечный файл по явному разрешению, сохраняет очередь, отправляет с идемпотентностью.
- Backend создаёт приватный source, отправляет обработку в **существующую центральную Live-модель**, получает transcript, задачи/договорённости с provenance и проверенным readback.
- Результат доступен в **личной ленте Миры**; в общий проект попадает только разрешённый фрагмент/объект, а не запись всего звонка.

### Этап 3 (после MVP, необязателен)

При подтверждённой необходимости — читать аудиопакеты существующего scrcpy-pipe **во время звонка** для near-real-time обработки. Сначала проверить, даёт ли это дополнительную продуктовую пользу по сравнению с гарантированным постобработочным сценарием.

## 10. Критерии приёмки

- На **Samsung и Redmi** минимум входящий и исходящий звонок, в обоих **физически слышны обе стороны**; подтверждены модель и версия ОС.
- При `armed=false` запись не создаётся; ручное «Записать этот звонок» работает; «Пропустить этот звонок» не записывает его повторно при том же вызове.
- При `armed=true` запись начинается без открытия Projects Hub; интерфейс показывает реальное состояние и явную ошибку при недоступной Shizuku.
- Плавающая кнопка перетаскивается по X/Y, фиксируется на краю, может быть закрыта броском в зону удаления; закрытие прекращает запись/авторежим, **не удаляет** ранее записанные файлы.
- Поведение проверено при блокировке экрана, после reboot, при отказе разрешения overlay, а также с альтернативой через уведомление.
- После звонка готовый файл один раз доставляется через offline/retry, имеет стабильный source ID, историю/длительность/статус и не пропадает при перебоях связи.
- Мира создаёт в личной ленте источник и извлечённые **с атрибуцией к фрагментам** договорённости/поручения, отличая подтверждённое от предположения; разрешённое изменение проекта проходит backend ACL и readback.
- Нет дублирующего VAD/ASR/LLM-конвейера, второго overlay, незащищённого IPC и неподтверждённых заявлений о продуктовой готовности.

# Projects Hub: аудит базовой коллаборации и обновление проектирования

Дата: 6 октября 2026, Europe/Kaliningrad.

**Статус: аудит исходников и проектные рекомендации.** Этот документ фиксирует проверенные разрывы и основания решений. Нормативный контракт следующей реализации — [«Базовая коллаборация и личная лента»](../product/20-basic-collaboration-and-personal-timeline.md). Предложения ниже не являются заявлением, что соответствующая функция уже реализована.

**Ближайший продуктовый результат:** пользователь А создаёт заметку в проекте; пользователь Б видит её по правам, получает адресованный вопрос или поручение, отвечает в своей личной переписке с Мирой; ответ сохраняется, связанная работа продолжается. Доска и переписка показывают одни и те же предметные объекты. Для первого результата не нужен универсальный workflow/BPM-движок.

## 2. Что добавили новые требования

Из V1 следуют следующие требования:

- Базовый совместный объект — заметка/идея проекта, доступная коллегам в пределах их прав.
- После команды Миры готовый текст структурируется в Markdown с использованием наработок Record Idea Hub.
- Контекст структурирования включает автора и список его ролей в проекте.
- Заметка должна быть в проектном репозитории; карточка ссылается на этот документ.
- Чтение заметки внутри Projects Hub не требует личного подключения читателя к GitHub. Допустим раскрываемый Markdown без служебного frontmatter.
- Прослушивание — отдельное явное действие; текст остаётся доступным.
- Структурирование, дальнейшая аналитика и обсуждение имеют различимые состояния.
- Сильная модель может подготовить вопросы, а Мира ведёт спокойную дискуссию, уточняет полноту ответа и позволяет развивать тему. [V1]

V2 уточняет:

- У вопроса есть собственный контекст; связанные вопросы могут иметь общий контекст пакета.
- Мира вводит общий контекст один раз и постепенно задаёт вопросы, не читая одинаковое вступление перед каждым.
- Пользователь может уточнить контекст, пропустить вопрос, ответить «не знаю» или отложить решение.
- Не все вопросы блокируют продолжение работы.
- Приоритет — работающий небольшой продукт; избыточная идеальная схема неприемлема. [V2]

Дополнительно действует прямое уточнение владельца в переписке: функциональные widget-блоки внутри личной ленты являются основным представлением. Popup может раскрывать документ или доску, но не заменяет блок в переписке. У каждого пользователя одна личная текущая переписка по разным проектам; одновременно открыта одна доска. При старте/приветствии приоритет имеет лично адресованное важное. Обзор общей активности проектов предлагается отдельно и раскрывается добровольно.

## 3. Подтверждённые разрывы в исходниках

### 3.1. Память ещё не является корректной совместной заметкой в репозитории

**Факт.** В main `DurableStore.commit_memory` берёт авторизованный source, формирует Markdown, пишет его через `_write_verified` в `memory/<workspace>/<memory_id>.md` и фиксирует receipt/ревизию в SQLite. Этот метод не выполняет GitHub commit/readback. Наличие поля `markdown_path` и результата `status=archived` не доказывает сохранение в проектном репозитории. [M1]

**Факт.** `list_memories` проверяет workspace membership, а затем выбирает memories по workspace и, опционально, project. В этом пути нет отдельного условия «личное автора»/«опубликовано проекту», а main не содержит `project_grants`. Проверка принадлежности проекта workspace не равна явному разрешению конкретному участнику читать проект. [M1]

**Вывод.** При добавлении коллег нельзя объявить текущую memory-выдачу готовым shared notes API. Нужны область заметки и предметная проверка прав. При этом существующие source IDs, revisions и проверяемая локальная запись полезны для переиспользования.

**Предложение.** Отделить приватный источник речи от разрешённой проектной заметки. В репозиторий и коллегам передавать только материал заметки, а не полный многопроектный личный монолог. Показывать GitHub sync как отдельный факт: локально сохранено, синхронизация ожидается, проверенно синхронизировано. Не объявлять GitHub-сохранение до readback.

### 3.2. Поручения пока принадлежат создателю, а роль — строка

**Факт.** `ReadinessService` хранит tasks с `actor_id`, `project_id` и строкой `assignee_role`. Методы чтения и смены состояния фильтруют `actor_id` создателя. Нет связанного получателя, групповой адресации или принятия поручения другим человеком. Состояния: proposed, accepted, done, snoozed, rejected. [M2]

**Вывод.** Строка «менеджер» или «owner» ещё не маршрутизирует поручение тому, кто занимает роль. Назначение и принятие задачи должны оставаться разными действиями.

**Предложение.** Добавить небольшой проверяемый слой назначения людям/существующим проектным ролям/группам поверх предметных задач. Не строить организационный редактор ради первого сценария А → Б. Контекстные роли автора заметки также отделить от технических прав viewer/editor/owner.

### 3.3. Вопрос, ответ и продолжение не представлены как работающий цикл

**Факт.** Main `DevelopmentService` использует `needs_owner` для terminal `blocked` после лимита rework либо отсутствующего verdict. Записывается `finished_at_ms`; последующий `status` не продолжает такой execution. Вопрос с адресатом, ответом и официальным resume-путём не создаётся. [M3]

**Факт.** В PR #87 `AnalysisRun.question` — исходный запрос консультанту. Таблица хранит `result_markdown/result_json`; вопросы консилиума выводятся в Markdown. Для одиночной консультации compact result содержит summary, participant и purpose. API имеет start/list/get/refresh/cancel/publish/materialize/report, но не цикл question → answer → continue. [B1], [B2]

**Факт.** Спецификация ветки уже описывает связь `question_id/run_id`, ответы и различие предложений и принятых решений. Эта часть документа не подтверждена соответствующей реализацией. [B6]

**Предложение.** Добавить тонкую предметную связь вопроса с задачей/run, адресатом, контекстом и revision; сохранять ответ до продолжения. Не создавать отдельную новую «систему аналитики вопросов». Протокольная ошибка агента, например отсутствующий verdict, не должна автоматически превращаться в вопрос владельцу о рутинной починке.

### 3.4. Межстадийное выполнение всё ещё зависит от клиентского poll

**Факт.** `DevelopmentService.status(sync=True)` читает provider result и может запустить следующий этап через start/continue. `App.tsx` вызывает latest execution с sync каждые 15 секунд. Main app lifespan не запускает фоновый обход durable executions. Новый запуск при наличии starting/running execution отклоняется с `DEVELOPMENT_EXECUTION_ACTIVE`. [M3], [M4], [M5]

**Вывод.** Provider turn асинхронен, но весь продуктовый процесс ещё не независим от открытого клиента. Новый push-интерфейс сам по себе этого не исправит.

**Предложение.** Вынести продвижение разрешённых этапов в небольшой backend pump по сохранённым записям. UI читает состояние. Остальные разрешённые задачи могут ожидать в durable очереди при сохранении существующих ограничений параллельности. Ожидание человека не удерживает inference slot.

### 3.5. PR #114/#115 исправили MCP transport/runtime, а не всю оркестрацию

**Факт.** Точный compare `21b755… → 32a4f750…` затрагивает AGENTS, deploy installer, MCP client, launcher, версии и тесты; `development.py`, `App.tsx`, `store.py` и `readiness.py` не менялись. [M0]

**Факт.** Клиент DevCoveer теперь держит stdio и MCP/AnyIO contexts в одной asyncio-задаче. Запросы передаются через внутрипроцессную очередь. Это устраняет межзадачное закрытие contexts и сохраняет bridge между start/read/continue. Worker ждёт вызовов из очереди; он не восстанавливает бизнес-очередь из БД. [M6]

**Факт.** PR #115 запускает stdio через transient user-systemd bridge вне mount namespace web backend; основной unit сохраняет свои настройки защиты. [M7], [M8]

**Граница вывода.** Нельзя писать «фоновые задачи уже исправлены полностью» на основании слова worker. Исправлен конкретный transport/runtime-блокер owner development. Для нового сценария всё ещё нужен durable product progression.

### 3.6. Доска реализована отдельным overlay, переписка остаётся текстовой

**Факт.** В PR #87 `ChatMessage` содержит role, text и поля состояния транскрипта. JSX перебирает `chatMessages` и показывает текстовые bubbles. `BoardShell` смонтирован отдельно, вне `chat-stack`, управляется `boardOpen`. [B3]

**Факт.** `.board-shell` использует `position: fixed; inset: 0; z-index: 40`. Сама доска и панель аналитики живут внутри этого overlay. [B4], [B5]

**Вывод.** По исходникам базовое требование «функциональный блок в переписке» не выполнено. Это не вывод из визуального теста и не утверждение о поведении каждой версии приложения.

**Предложение.** Сделать типизированный блок ленты со ссылкой на предметный объект. Для доски — компактное представление/preview и раскрытие того же board ID. Для заметки — карточка и раскрываемый Markdown. Для вопросов — действия и актуальное состояние в ленте. Popup/fullscreen остаются дополнительным режимом отображения, а не отдельной копией объекта.

### 3.7. Аналитика доски слишком узка для всей коллаборации

**Факт.** `AnalysisRun` в PR #87 требует board ID и frozen набор объектов доски. get/list проверяют initiating actor; отчёт не становится автоматически общепроектным. [B1]

**Вывод.** Такой анализ полезен для доски, но не покрывает произвольную аналитическую задачу, обсуждение заметки и вопросы нескольким участникам. Ограничение инициатором сейчас защищает приватность; просто убрать его нельзя.

**Предложение.** Разрешить анализу ссылаться на задачу/заметку и её разрешённый snapshot. Доска — один из источников и представлений. Совместная доступность отчёта появляется через явную проектную область, а не через снятие проверки инициатора. Публикация результата и автоматический запуск разработки остаются разными действиями.

| Функция | Полезная существующая опора | Что добавить в ближайшей поставке |

| Обсуждение | Центральная Мира, одна личная conversation с меняющимся project focus [M9] | Связь дискуссии с note/question IDs без отдельного чата на проект |
| Поручения | Readiness tasks и состояния [M2] | Реального получателя, принятие/отказ, личные входящие |

| Уведомления | Android Notifier для события/обновления [M12] | Личные вопросы/поручения, пакетирование, тихое открытие, отдельное состояние доставки |

В просмотренном tool list центральной Миры есть GitHub/память/Regional Knowledge и другие предметные tools, но нет универсального web-search tool. Поэтому пример «исследовать погоду и климат Лондона» не следует объявлять уже работающим через Regional Knowledge. Если для прототипа требуется внешний поиск, необходимо явно реализовать/подключить подходящий retrieval-путь либо дать подготовленный проверяемый evidence bundle. Нельзя ради примера молча расширять filesystem/web/tools права provided-only консультанта. [M9], [M10], [B6]

## 5. Переиспользование Record Idea Hub: текстовое структурирование

**Проверенный существующий код:**

1. `SummaryPayload` описывает title, short/detailed summary, theses, ideas, decisions, tasks, facts, entities, related_projects, open_questions, contradictions, uncertain_fragments и tags. У task есть `explicitly_stated`, позволяющее отличать прямое поручение от вывода модели. [R1]
2. `GeminiVoiceService.summarize` получает текст из `TranscriptChunk`, вызывает генерацию с `SUMMARY_JSON_SCHEMA`, валидирует `SummaryPayload` и передаёт `audio=None`. Это уже текстовое структурирование, отдельное от `transcribe`. [R2]
3. `voice_intake_v2/markdown.py` строит структурированные секции, помечает выведенные моделью задачи и формирует стабильную публикацию. Но его `PublicationProjection` и frontmatter специфичны для voice intake: устройство, аудио, chunks, запись Record Idea Hub, полная расшифровка. [R3]

**Предлагаемая адаптация, ещё не реализованная:**

- Выделить тонкий вход для уже готового текста и доверенного metadata/context, сохранив существующие schema, limiter и валидацию. Не вызывать transcribe повторно.
- Не фабриковать аудиосессию, chunk timing и digest ради использования старой сигнатуры; адаптировать текстовую часть.
- Переиспользовать структуру Markdown, но создать проекцию проектной заметки без ложных аудиометаданных и полной приватной расшифровки.
- Автор, project ID и роли поступают от авторизованного backend-контекста. `related_projects`, выведенные моделью, не определяют место публикации или права.
- `decisions`, `tasks` и `open_questions` из summary — извлечённый материал. Они не становятся автоматически принятыми решениями, назначенными поручениями и уведомлениями конкретным людям.
- Исходный текст сохраняется до успешного структурирования. Ошибка Gemini оставляет заметку доступной, со статусом повторяемой обработки.
- Состояния «структурировано», «синхронизировано в репозиторий» и «проведён анализ» не смешиваются. Заметка может быть структурированной без сильной аналитики.

Это ограниченное переиспользование явно запрошенной обработки текста, а не новый скрытый ASR или второй семантический диспетчер разговора.

## 6. Предлагаемый короткий путь к прототипу

### Шаг 1: общая заметка и сценарий А/Б

Первый вертикальный результат — заметка проекта, которую А сохраняет через Миру, а Б действительно видит внутри приложения. Проверить проектную область, приватность источника, роли автора, статус обработки и repo readback. Автору показать note-widget в личной ленте; коллегам дать доступ к тому же объекту. Карточка доски лишь ссылается на note ID.

Не начинать с общей очереди сотен типов событий, если коллега ещё не может открыть одну корректно сохранённую заметку.

### Шаг 2: тонкий вопрос/поручение и продолжение

Добавить предметный вопрос с task/run/note reference, получателем, общим контекстом, revision и признаком blocking/optional. Поручения используют существующие task объекты с реальной адресацией.

Мира получает bounded пакет, вводит его контекст один раз и ведёт обычную беседу. Backend сохраняет типизированный ответ и затем ставит разрешённое продолжение. Для анализа не обязательно запускать новую сильную модель после каждого короткого ответа: допустима одна следующая итерация по накопленному пакету.

Вопрос группе должен иметь понятный способ завершения: один уполномоченный ответ, ответы указанных людей либо итоговое решение назначенного ответственного. Сам факт адресации группе не вводит автоматического голосования.

### Шаг 3: независимое выполнение, уведомления и обзор

Небольшой backend pump обрабатывает сохранённые pending-записи, GitHub sync, provider readback, continuation и notification outbox. Существующий SQLite/WAL пригоден для начала; отдельный брокер или новый workflow framework не являются prerequisite.

Пакетирование предотвращает спам. Смахивание push не меняет вопрос. При неизвестном исходе запуска сохраняются прежние IDs/request keys; новая попытка не используется для обхода неизвестного результата.

Общепроектный activity brief строится из подтверждённых событий, отдельно от личных входящих. Его можно добавить после работающего сценария А/Б и thin continuation.

## 7. Минимальные различия состояний

| Факт | Семантика |
|---|---|
| Заметка сохранена | Есть долговечный предметный объект; Gemini/GitHub могут ещё ожидаться |
| Заметка структурирована | Получен валидный summary; это не подтверждение всех извлечённых решений |
| Repo sync подтверждён | Материализация и readback состоялись |
| Вопрос открыт | Ответ/решение ещё требуется |
| Ответ частичный | Содержимое сохранено, но вопрос может требовать уточнения |
| «Пропустить» | Не задавать снова в текущем обсуждении; не считать решённым |
| «Не знаю» | Зафиксирован ответ об отсутствии знания; обязательная зависимость не удовлетворена |
| «Решу позже» | Отложено по понятному правилу, а не удалено |
| Вопрос снят | Предмет исчез/заменён/отменён, причина сохранена |
| Уведомление смахнуто | Закрыт только сигнал доставки |

Успешное завершение вычислительного run может дать отчёт с открытыми вопросами. Поэтому правило «run completed → снять все вопросы» неверно. Закрывать нужно исчезнувшую зависимость, а не сам факт окончания генерации.

Ответы с двух устройств требуют проверки revision и защиты от повторов. Поздний ответ не возобновляет отменённую работу. Обновление исходной заметки не должно молча применять старый ответ к другой постановке.

## 8. Личная лента, одна доска и приветствие

**Предложение для реализации контракта:**

- У каждого actor одна личная текущая переписка, охватывающая доступные проекты. Проект — контекст предметного блока/действия, а не повод создать ещё один чат.
- Заметка, вопрос, поручение и отчёт имеют функциональные блоки с устойчивыми предметными ссылками. Обновление статуса меняет представление того же объекта.
- Одновременно открыт один board. Его раскрытие сохраняет голосовой контекст и доступ к лично адресованному вниманию.
- Popup допустим для чтения Markdown/деталей. Кнопка «Прослушать» запускает озвучивание явно; раскрытие документа не обязано закрывать доску.
- При старте/приветствии сначала кратко обозначается лично адресованное важное. Начатая пользователем конкретная задача не перебивается обзором.
- Общепроектная активность предлагается отдельно: «В проектах есть обновления. Рассказать?» Перечень вроде «Ольга добавила две заметки» появляется после добровольного раскрытия.
- Тихий режим не включает микрофон и речь при открытии приложения/push. Колокольчик и блоки работают без голосового вывода.
- Фоновое получение данных не считается просмотром обзора. Просмотр обзора не закрывает вопросы.

Это сохраняет насыщенную коллаборацию при простом основном интерфейсе и не превращает каждое новое событие проекта в обязательную реплику Миры.

## 9. Девять проверяемых критериев следующей поставки

1. **А/Б и приватность.** А создаёт заметку проекта. Б с доступом читает её внутри Projects Hub без собственного GitHub-подключения. Участник без доступа не получает заметку или её snippets; полный личный source А не раскрывается.
2. **Один документ.** Заметка имеет автора/роли, revision и понятные статусы. GitHub readback подтверждён. Виджет ленты и карточка единственной открытой доски открывают ту же заметку.
3. **Адресованное взаимодействие.** Вопрос и поручение появляются в личных входящих указанного человека/разрешённой группы. Назначение не считается принятием задачи.
4. **Свободная дискуссия.** Мира вводит общий контекст пакета один раз, принимает естественные ответы и связывает их с нужными IDs. Уточнение контекста не теряет текущий вопрос; смена проекта не создаёт отдельный чат.
5. **Пропуски и независимая работа.** «Пропустить», «не знаю», «позже» сохраняются. Optional вопросы не останавливают всю работу; нерешённый blocking выбор не считается согласованным.
6. **Фон и восстановление.** После закрытия приложения/рестарта backend результат и вопросы сохраняются, после ответа продолжается прежний разрешённый процесс. Повторный ответ/доставка не создают второй continuation.
7. **Уведомления.** Несколько вопросов пакетируются. Смахивание push не закрывает их. Тихое открытие не включает голос; колокольчик доступен с доски.
8. **Приветствие.** Приоритет имеет важное лично адресованное. Общепроектный brief раскрывается добровольно. Конкретный запрос пользователя не перебивается обзором, фоновые fetch не отмечают обзор прочитанным.
9. **Полномочия и актуальность.** Отзыв доступа запрещает дальнейшее чтение/ответ/доставку; поздний ответ не оживляет отменённую задачу. Аналитическая коллаборация не даёт owner development. Принятые ресурсные правила NVIDIA и Codex сохраняются.

## 10. Границы применения аудита

- Аудит не разрешает продолжать остановленный PR #87 или менять голосовой transport.
- Здесь не заявляется приёмка браузером, двумя реальными участниками или physical Android: это сценарии предстоящей проверки.
- Предлагается переиспользовать текущие задачи, memory provenance, analysis runs, GitHub bindings и типизированные adapters, добавив недостающие связи. Не предлагается общий реестр произвольных workflows.
- Возможность дополнять Codex-лестницей существующие Kimi/DeepSeek варианты и gate эффективного остатка строго больше 10% сохраняется. NVIDIA использует разрешённые два distinct credential/project slots без повторного пользовательского budget-confirmation; ожидание человека освобождает ресурс. Действующий контракт следующей поставки уточняется в документе 20; устаревший текст PR не меняет решение владельца. [B6]
- Главный порядок поставки: shared note А/Б → адресованный вопрос/поручение и ответ/continue → пакетирование и optional activity brief. Технические компоненты считаются принятыми по этому пути, а не отдельно по наличию таблиц, popup или зелёного unit-теста.

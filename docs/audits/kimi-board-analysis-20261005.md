## Ответ консультанта

# Консультация: доска проекта + асинхронная аналитика (READ-ONLY)

Сконсультирован по гипотезе правообладателя контракта; подтверждено, что `devcoveer_client.py` — честно allowlisted и `start_task` всегда `access: "write"`, а `store.py` — SQLite/WAL с атомарными коммитами (`synchronous=FULL`), что важно для board-ревизий. Дальнейшего сервера не исследовал.

## Findings

1. **Несоответствие: аналитика сейчас невозможна через существующий DevCoveerClient.** `start_codex_task` жёстко шлёт `access: "write"`, а задача-консультант должна быть read-only. Пункт 5 гипотезы правильно требует отдельной линии, но вносите его как *новый allowlisted client/профиль* (`analytics_client`, access=read, без write-инструментов), а не расширение существующего класса — иначе смешаете owner-development и пользовательскую аналитику в одной админской поверхности.
2. **SQLite multiwriter.** Один board WSS + broadcast-after-commit + optimistic concurrency на объекте нормально ложатся на текущий store, но append-only object events при нескольких одновременных редактированиях упираются в единственный writer. Решение простое: сериализовать коммиты доски через один внутренний gate (как сейчас `self._lock`), но сделать это явным контрактом, иначе при переезде на PostgreSQL (заявлен в docstring) порядок seq молча изменится.
3. **Формулировка «Мира действует от имени пользователя»** в events — корректно: immutable initiator_subject + executor. Не забыть, что owner-development требование (CORE-OWNER-SELF-DEVELOPMENT) делит аналитику и запуск разработки: отчёт консилиума не должен даже гипотетически содержать кнопку/вызов, приводящий к start_task, иначе он станет скрытым путём запуска реализации.
4. **Guest share и requirements contract.** Share-view — новая поверхность авторизации, а файл требований покрывает authenticated issuer+subject. Гостевая ссылка — фактически анонимный capability-токен; это допустимое исключение, если оно зафиксировано в явном проектном решении (owner-visible), иначе рискует трактоваться как послабление CORE-MULTIUSER-ISOLATION.
5. **Избыточно в гипотезе:** PixiJS для MVP со стикерами сильно переоценён — Canvas 2D/SVG-слой с тем же дизайном градиентов и уголков покроет сотни стикеров без WebGL-зависимости и гораздо проще в accessibility; заводить PixiJS имеет смысл только при реальной нужде (тысячи объектов, сложные слои). Также рано: после-seq resync *и* snapshot (достаточно snapshot + последние N событий), отдельный channel для drag-preview (можно ephemeral-тегом на том же WSS).
6. **Чего не хватает в гипотезе:**
   - (а) Контракт purging/retention отчётов и доски (append-only события без политики роста → неограниченная таблица).
   - (б) Политика soft-delete по зеркалу «tombstone», но без undo tombstone → случайное удаление стикера голосом невосстановимо.
   - (в) Rate/capacity для аналитических jobs: council вызовов — это несколько сильных моделей на клик; без bound per-user/per-board она станет дорогой точкой злоупотребления (думает в сторону ai-resource-admission как готовой authority, не локального счётчика).
   - (г) Поведение при голосовом переключении: «Открой доску» посреди речевой очереди/буфера (PR #84 — long-input voice!) требует явного правила, что голосовой turn не «проглатывает» начало команды, адресованной доске.

## Edge cases (выбрано 7 самых опасных)

1. **Concurrent edit одного стикера:** A тащит, Мира (по команде B) меняет цвет с той же expected_revision → чья-то правка молча проигрывает при last-write-wins. *Исправление:* отказ 409 + diff, initiator решает; ваш пункт 2 уже это даёт — зафиксируйте тестом.
2. **Reconnect в середине drag:** клиент A отвалился с незафиксированной позицией, клиент B видит старое место и редактирует текст; вернувшийся A шлёт drag-commit со stale revision → фальшивый конфликт или потеря текста. *Исправление:* drag-preview всегда ephemeral; commit только по свежей ревизии из reconnect snapshot.
3. **Переключение голосового режима при открытии доски:** поверх voice PCM открывается board WSS; команда «открой доску» должна быть атомарной сменой UI+tool-bundle (прогрессивное раскрытие по AGENTS.md), иначе Мира продолжает отвечать «старыми» инструментами без доски. *Исправление:* детерминистский UI-state→mode-overlay, описанный в canonical live-agent архитектуре.
4. **Viewport/search расходятся:** Мира получает viewport rev 100, объект найден по смыслу в rev 103 и уже переместился → фокус ведёт «в никуда». *Исправление:* search возвращает revision объекта; клиент при фокусе сверяет с локальной сценой и при расхождении запрашивает свежий bbox.
5. **Гостевой токен переживает revoke:** активный guest WSS после отзыва токена продолжает получать broadcast уже открытой доски. *Исправление:* проверка токена на каждом N-ом событии / heartbeat, мгновенное закрытие.
6. **Дублирующая отправка аналитики:** таймаут клиента → retry с новым id → два запуска сильной модели (двойная стоимость, два отчёта). *Исправление:* durable command_id/idempotency-key на analysis run; неизвестный исход — readback по ключу, не повторный запуск (паттерн operations.durable-recovery).
7. **ACL ссылки на MD в отчёте:** консультант-аналитик ссылается на GitHub-документ в private repo; гостевая доска/отчёт покажут ссылку, и клик уйдёт 404 или, хуже, попытка «предпросмотра» протащит контент. *Исправление:* ссылки — только opaque reference, рендер предпросмотра только после проверки доступа зрителя.

## Recommendation

Гипотеза по существу верна и консервативна. Корректировки: (1) canvas 2D вместо PixiJS до доказанной нужды; (2) отдельный read-only `analytics`-профиль клиента DevCoveer; (3) явный retention/tombstone-undo; (4) capacity-гейт для аналитики через ai-resource-control; (5) зафиксировать guest-share как owner-visible исключение из multi-user isolation. Тесты (опровергающие наивную реализацию): concurrent color-vs-drag edit с ожиданием одного 409 и сохранённой второй правки; reconnect mid-drag без потери чужого текста; голосовое «открой доску» в середине речевого turn открывает доску и сменяет tool bundle; фокус поиска на объекте, перемещённом между поиском и ACK, не уводит камеру в пустоту; revoke guest-токена обрывает live WSS немедленно; повторный submit аналитики по idempotency-key возвращает тот же run, не создаёт второй; гость на просроченной по 7 дней ссылке получает отказ и на WS, и на HTTP.

**2–3 улучшающие идеи (не из запроса):**
1. **Привязка аналитического отчёта к revision доски:** отчёт всегда показывает diff «с тех пор изменилось N объектов» — решает вечную проблему устаревших рекомендаций дёшево.
2. **Голосовой диктофон-стикер:** короткая голосовая заметка как стикер с transcript прямо на доске — доска становится естественным продолжением голосового продукта, а не параллельным инструментом.
3. **«Скрыть доску» как микрофон-безопасный режим:** при демонстрации гостю один жест закрывает board из voice-контура Миры (она перестаёт видеть viewport), что защищает приватные проекты при screen sharing.

## Confidence

Средне-высокая по архитектуре (подтверждена контрактом и реальным `store.py`/`devcoveer_client.py`); средняя по UI-стеку (не проверял лицензию PixiJS, renderer намеренно оставлен на ваш выбор); низкая по масштабам нагрузки — обещаний производительности не делал.

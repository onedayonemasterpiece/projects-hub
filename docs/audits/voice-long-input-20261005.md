## 1. Жалоба и граница задачи

После обновления пользователь не видит собственную речь текстом в правом сообщении. При длинной реплике примерно через 20–30 секунд микрофон выключается; вместо «Слушаю» появляется «Готова слушать». Пользователь просит оставить аудиты в текущем окне ChatGPT, а реализацию и обновление приложения выполнять в новом окне.

Предыдущее утверждение, что после установки 0.1.25 это должно работать, было преждевременным: наличие кода и описаний возможностей провайдера не заменяет проверку реального маршрута микрофон → распознавание → интерфейс → сохранение.

## 4. Подтверждённая корневая причина: устаревшее резервирование бюджета

В центральном реестре для этой сессии прочитаны безопасные поля одной соответствующей lease и её grants; секреты и текст речи не выгружались. Результат:

```json
{
  "state": "released",
  "terminal_reason": "RESOURCE_TOKEN_BUDGET",
  "initial_tokens": 16384,
  "grant_seq": 2,
  "heartbeat_seq": 1,
  "grants_tokens": [16384, 22518, 16384],
  "policy_minute_token_limit": 60000,
  "policy_lease_seconds": 90,
  "policy_max_session_seconds": 7200
}
```

Важно: это **единицы внутреннего admission/reservation**, а не счёт Gemini и не число уже потраченных моделью токенов.

В установленном старом SDK:

1. Первичное разрешение резервирует 16384 единицы.
2. Для крупного setup выдаётся новая резервация 22518. Старая резервация продолжает учитываться authority; клиент не использует правильное резервирование только недостающего объёма.
3. Начало аудио получает ещё 16384.
4. Локальное окно расходования grant истекает примерно через 29 секунд. Для очередного небольшого PCM chunk клиент снова запрашивает минимум 16384.
5. Уже зарезервировано `16384 + 22518 + 16384 = 55286`. Новая заявка дала бы `71670 > 60000`. Остаток до лимита — 4714: он значительно меньше фиксированного блока, но не обязательно меньше реальной потребности очередного аудиофрагмента.
6. Authority корректно отказывает такой заявке. Старый SDK не уменьшает запрос после окончательного отказа. PCM resource failure завершает provider run; framework отправляет error и закрывает сессию.

SQL удерживает резервации до `spend_until + 60 seconds`; поэтому неиспользованный большой grant не перестаёт учитываться сразу после замены следующим. Возвращённые после release timestamps отдельных grants уже могут быть уменьшены процедурой release; нельзя по ним восстанавливать прежний deadline без учёта этого изменения.

Пин находится в [deploy/devcoveer_install.py](https://github.com/onedayonemasterpiece/projects-hub/blob/06407e7e623cb50c0baaf0844072edbb18bebb78/deploy/devcoveer_install.py#L30-L34).

В актуальном shared SDK **уже есть** исправления: меньший default grant (1024), резервирование недостающей части, уменьшение аудиозаявки после окончательного `RESOURCE_TOKEN_BUDGET`, вплоть до фактической потребности. Существенные коммиты: `cf13fca3af65d5817d4a4a766a2b7ad60ef8e498`, `fb14979ee9c6187dde39af174eaa506c8c1a6789`, `8f5a0dc9aed257515d2ed5dd71ba1dc866d8b1fe`. [Актуальный before_send](https://github.com/onedayonemasterpiece/ai-resource-control/blob/f31738077dc4ad3f1e141a9eb252f84bce7d5379/src/ai_resource_control/client.py#L436-L488).

**Первое исправление — интеграция и проверка существующего общего решения, а не ещё одна локальная версия limiter.** Отдельно проверить корректность carry и сроков старых grants: перенос остатка не должен незаконно продлевать разрешённое время расходования. Не поднимать лимит 60000 без основания, не отключать authority, не переходить на другой ключ после ready и не превращать повторный запуск в обход исчерпанного бюджета.

Установленная policy допускает до 7200 секунд, а client liveness timeout — 180000 ms. Это не означает гарантированные два часа без сбоев; лишь показывает, что исследованный stop не является заданным 30-секундным продуктовым пределом.

## 5. Почему пользователь видит просто выключенный микрофон

В [framework browser/client.js](https://github.com/onedayonemasterpiece/live-interaction/blob/v0.3.18/browser/client.js) `handleEvent(error)` вызывает `onEvent`, затем `stop({reason:'provider_error'})`. Этот путь не вызывает полезный error notice.

В Projects Hub `applyLiveEvent` не обрабатывает `error`. `onState` принимает только state и игнорирует второй аргумент с reason. `onTiming` при создании client не подключён. HTTP stop отправляет `{}`; серверный stop-log сохраняет только `result=stopped`.

Получается цепочка: реальный отказ бюджета → terminal error → reason теряется для UI → `off` → «Готова слушать». Автовосстановление реализовано для `transport_error`, но не для этого provider/resource error. Простое добавление restart к любому error небезопасно: тот же budget может быть ещё занят, а незавершённая мысль не восстановлена.

Нужно сохранять первопричину, различать штатный user stop, quota wait, transport failure и provider failure; показывать пользователю, какая часть речи сохранена и какая ещё не распознана. Подробности — в защищённой диагностике, понятный текст — в UI.

## 6. Отсутствующая транскрипция: доказательства и гипотезы

Нельзя объявлять это исправленным только обновлением SDK. Подтверждено существование обработчика и UI, но не доставка промежуточного текста именно в неудачной сессии.

Google документирует `interimInputTranscription` для обновляемой транскрипции во время речи; `inputTranscription` поступает независимо от других серверных сообщений, без гарантированного порядка. Источник: [официальный Live API reference](https://ai.google.dev/api/live), проверен 05.10.2026. Наличие поля в API не доказывает, что конкретная сессия реально выдала его с нужной задержкой.

| Гипотеза | Статус | Различающая проверка |
|---|---|---|
| Resource stop оборвал длинный фрагмент до его финализации | Подтверждён stop; вклад в конкретную недостающую транскрипцию вероятен | После устранения over-reservation записать 60/180/300 s и сопоставить финализацию текста с остановками |
| Provider не присылает interim в текущем model/setup либо задерживает до конца реплики | Не установлено | На входе provider adapter считать только типы полей, длины и времена событий при настоящем длинном PCM |
| Interim приходит, но теряется/перезаписывается в host → WSS → React/DOM | Не установлено | Один correlation chain и одинаковые sequence/segment revision от provider до фактического DOM |
| Пользователь продолжает говорить поверх преждевременного ответа Миры | Реальный риск по коду, вклад в этот тест не измерен | Сопоставить playback interval с capture_suppressed_playback и речью контрольного сценария |
| На телефоне всё же исполняется старый bundle | Не основная гипотеза; полностью не исключена | Session-bound native version + actual JS build hash, а не только версия в health |

Interim специально не сохраняется как authoritative transcript. Поэтому отсутствие interim в SQLite НЕ доказывает отсутствие этих событий у провайдера. Сейчас нет долговечных счётчиков, позволяющих восстановить этот участок задним числом.

Дополнительные доказанные дефекты текста:

- App обрезает накопленное сообщение по первым 4000 символам. После этого продолжение перестаёт попадать в сообщение.
- Interim показывает только последние 1200 символов. Это может быть preview, но не полная доступная пользователю реплика.
- Shared host проецирует отдельный final transcript event до первых 2000 символов и добавляет `truncated`. UI не восстанавливает полный текст по source.
- На `turn_complete`/`interrupted` UI сбрасывает interim и индексы. При независимом порядке input transcription нужны поведенческие тесты поздних фрагментов и revision/segment semantics; нельзя гарантировать правильность простым объединением строк.

Исправление: provider-derived evolving user message справа, ясное отличие предварительного и сохранённого текста, целиком доступная текущая мысль с пагинацией/виртуализацией вместо потери хвоста. Пока provider text отсутствует — «Микрофон работает; текст ещё не получен», а не выдуманная расшифровка или утверждение «Мира всё поняла».

## 7. Паузы, playback и память

**Пауза — не stop.** В deployed config VAD ожидает 5000 ms тишины. Он может завершить пользовательский turn, но не должен закрывать всю Live-сессию. Не лечить подтверждённый budget failure ещё одним изменением VAD.

`continuousCapture=true` отменяет локальную тишинную отсечку sender, однако `suppressCaptureDuringPlayback=true` по-прежнему отбрасывает кадры до sender, пока есть playback buffers. Поэтому этот флаг не означает «любая речь всегда записывается». Не снимать подавление без проверки эха; нужна измеренная согласованная политика capture/barge-in и честное состояние интерфейса.

**Запись на диске и рабочая память модели — разные гарантии.** При новой Live-сессии продукт восстанавливает последние 8 сообщений примерно по 700 символов, отбрасывает незавершённый хвост и turn с interrupted. Shared host дополнительно ограничивает history, а DialogueHistory имеет лимиты 8×700 и внутреннюю сборку до 4000. Исправление только store.py не устранит весь маршрут потери.

Исходный PCM исследованной сессии остался в recovery source, но полной финальной расшифровки там нет. Новая Мира не получает автоматически все недавно произнесённые сведения. Нужны actor-private чтение полной source/transcript с пагинацией, список pending thoughts и корректное восстановление недофинализированного аудио через ту же Live-модель. Нельзя автоматически исполнять старую незавершённую команду как новую. Исходник, текущая инструкция пользователя и подтверждённые side effects должны храниться отдельно.

## 8. Почему прежняя приёмка не выявила проблему

Ряд voice lifecycle tests читает `App.tsx` и проверяет регулярными выражениями наличие `continuousCapture`, `interim_input_transcript`, «Слышу сейчас». [Пример](https://github.com/onedayonemasterpiece/projects-hub/blob/06407e7e623cb50c0baaf0844072edbb18bebb78/web/tests/app-voice-lifecycle.test.mjs#L23-L48).

Это полезные статические guardrails, но они не включают микрофон, не проходят несколько окон выдачи grants, не читают DOM в работающем приложении и не доказывают восстановление смысла. Нельзя подменять ими продуктовую приёмку. Результаты всех тестов заново в этом аудите не прогонялись; утверждение «весь CI исправен» не делается.

## 9. Порядок доработки без переписывания продукта

1. Интегрировать проверенный актуальный shared resource SDK и воспроизвести бюджетный сценарий без искусственного увеличения квоты.
2. Сделать terminal reasons и end-to-end counters наблюдаемыми; исключить тихий переход ошибки в idle.
3. Доказать живую транскрипцию через реального провайдера и исправить место разрыва, сохранив одну центральную Миру.
4. Убрать усечение свежей мысли и закрыть pending-source recovery без повторных действий.
5. Выпустить согласованные backend/PWA/APK и принять длинный ввод на физическом устройстве. Автоматические PCM/браузерные прогоны провести ДО перекладывания проверки на владельца.

Между поставками сохранять checkpoint и evidence. Не стартовать новую архитектуру; не смешивать этот инцидент с owner development orchestration, embeddings или Street Story.

## 10. Ограничения и сохранность доказательств

В аудите читались журнал, точные релизные файлы, безопасные поля одной conversation/source и соответствующей resource lease. Диагностика production — read-only: quota/config/DB не менялись, сессии не запускались, провайдер заново не вызывался, сервис не перезапускался. Физический микрофон телефона в этом окне не тестировался. В GitHub записана только документация; это не новая версия приложения.

Два небольших диагностических скрипта были написаны ChatGPT для ограниченных read-only выборок; они не являются исправлением продукта. Не переносить секреты, полную речь или audio в публичный репозиторий. Существующий source сбоя следует сохранить до завершения расследования согласно действующей политике приватности и retention.

Самостоятельно стоящие рабочие ветки Projects Hub действительно отстают: основной checkout на `226c014...`, owner checkout на `726b741...`, тогда как production на `06407e7...`. Это операционный риск. Однако подтверждённая потерянная интеграция в данном сбое — **обновление ресурсного SDK в deploy pin**, а не отсутствие всех последних voice patches.

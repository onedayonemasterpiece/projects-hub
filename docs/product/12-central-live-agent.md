# Центральный Live-агент: единственное когнитивное звено

> **U04 / 2 октября 2026:** WSS меняет транспорт, но не когнитивную архитектуру. Мира остаётся единственным semantic orchestrator; Regional Knowledge подключается как узкая evidence capability, а не второй агент. См. [16-wss-platform-reliability.md](16-wss-platform-reliability.md).

[Индекс](README.md) · [UX](03-product-and-ux.md) · [Память](10-conversation-memory.md) · [Проекты/словарь](11-routing-and-vocabulary.md).

**Ревизия 3, 27 сентября 2026.** Этот документ исправляет архитектурную ошибку ревизии 2: отдельный ASR/semantic pipeline перед Live-моделью не является продуктовой архитектурой Projects Hub. Центральный интеллект продукта — одна Live-модель в пользовательском разговоре. Детерминированный код обеспечивает захват, доставку, права, долговечность и исполнение function calls, но не подменяет собой понимание речи, выбор проекта, оценку ценности или решение, что делать с содержанием.

## 1. Главный инвариант

Пользователь говорит **Live-агенту**. Live-агент:
- слышит исходное аудио;
- сам понимает смысл речи;
- получает собственную input transcription от Live API;
- знает разрешённые проекты и может сам запросить дополнительный контекст;
- сам решает, к какому проекту относится сказанное;
- при неоднозначности сам задаёт уточняющие вопросы;
- сам решает, что является идеей, требованием, решением, поручением, просто вопросом или не требующей долговременной памяти служебной репликой;
- сам вызывает строго типизированные функции для чтения/сохранения/изменения данных;
- получает результаты этих function calls и продолжает тот же голосовой разговор.

Детерминированный слой **не содержит параллельного “мозга”**. В нём нет отдельного LLM-классификатора, отдельного LLM-маршрутизатора, скрытого “суммаризатора перед Live”, отдельной модели, которая сначала решает ценность реплики, или pipeline “ASR → классификатор → Live”.

## 2. Нормальный online-путь

```text
микрофон
  │
  ├─ локальный durable capture/VAD ──────────────┐
  │                                              │ страховка и восстановление
  ▼                                              │
live-interaction ── PCM ──> Gemini Live <────────┘
                              │
                              ├─ inputTranscription events ──> durable source journal
                              ├─ voice response ──────────────> пользователь
                              └─ function calls
                                      │
                                      ▼
                           thin authorized tool adapters
                                      │
                ┌─────────────────────┼─────────────────────┐
                ▼                     ▼                     ▼
         project/doc reads       durable memory        tasks/calendar/etc.
                │                     │                     │
                └──────────── tool result/readback ─────────┘
                                      │
                                      ▼
                                 Gemini Live
```

Транскрипция входного голоса включена в самой Live-сессии. Она сохраняется как provenance той же модели и того же пользовательского хода. Приложение может собирать provider events в надёжный transcript journal, но это **не второй распознаватель и не второй интерпретатор**.

Локальный аудио-журнал нужен не для “подготовки текста модели”, а чтобы обычный сетевой сбой, закрытие процесса или неполный transcript не заставили пользователя повторять сказанное.

## 3. Offline — это отложанный Live-turn, а не другой AI pipeline

Если сети/Live нет, пользователь продолжает говорить в тот же продукт. Клиент надёжно сохраняет исходный звук с VAD/chunks и последовательностью. Никакая отдельная модель в этот момент не пытается понимать, маршрутизировать или суммаризировать содержание.

Когда Live снова доступна:
1. продукт создаёт/восстанавливает пользовательский разговор;
2. поднимается **тот же тип центрального Live-агента** с теми же product tools;
3. сохранённое аудио преобразуется только технически в требуемый Live API PCM;
4. аудио целиком поступает в Gemini Live;
5. агент получает/формирует input transcription, слышит запись и понимает её сам;
6. агент вызывает функции сохранения, маршрутизации и предметных действий;
7. только после function-call receipts агент голосом объясняет, что именно понял и что фактически сделал.

Это не “сначала распознать другим ASR и передать текст Live”. Даже длинная offline-запись должна попадать центральному агенту как **аудио**.

### Граница одного buffered turn

Длинная офлайн-запись может содержать естественные паузы. Нельзя позволить server-side VAD ответить после первой паузы, пока ещё передаётся остальная запись. Для deliberate buffered replay требуется режим общего `live-interaction`, который использует ручную границу activity:
- Live setup с отключённым automatic activity detection для такого turn;
- `activityStart`;
- вся последовательность сохранённого PCM в правильном порядке;
- `activityEnd`;
- затем разрешить ответ и function calls.

Gemini Live API прямо поддерживает `activityStart/activityEnd` при отключённом automatic activity detection. Это должно быть общей возможностью framework, а не частным обходом Projects Hub.

Если offline-пакет очень большой, pacing/backpressure остаются транспортной задачей. Нельзя заменять звук summary, чтобы “влезть”. Разрешено отправлять его частями в **тот же логический buffered turn**, сохраняя coverage и не позволяя агенту считать пакет полным до activityEnd.

## 4. Кто сохраняет Markdown

Live-агент принимает смысловое решение, а backend исполняет его.

Provider input transcription сохраняется автоматически как журнал source events, связанный с `turn_id/recording_id`. Агенту не нужно пересылать весь transcript аргументом function call. Когда агент понимает, что текущий пользовательский эпизод стоит сохранить долговременно, он вызывает, например:

```text
memory.commit_voice_source(
  source_id,
  title?,
  project_links?,
  kind?,
  importance?,
  notes?
)
```

Thin tool:
- проверяет actor/scope;
- берёт уже накопленный transcript/source journal этого source_id;
- создаёт/обновляет отдельный Markdown;
- сохраняет provenance, capture time, dictionary snapshot и ссылки;
- делает exact/readback;
- возвращает receipt агенту.

Именно **агент** выбирает смысловые поля и проектные связи. Tool не запускает второй LLM и не “улучшает” смысл за него.

Для короткой служебной реплики агент может вызвать `memory.finish_ephemeral(source_id)`. Тогда source остаётся в recovery-retention до безопасной очистки, но не становится постоянным Markdown.

Если агент не успел принять disposition, source остаётся `pending_agent_disposition` и **не удаляется**. Это fail-safe, а не скрытый deterministic classifier.

## 5. Никакого жёсткого “20 секунд = сохранить”

Длительность — лишь сигнал и страховка эксплуатации, но не когнитивное решение.

- трёхсекундная фраза «срок переносим на пятницу» может требовать постоянного сохранения;
- двухминутный вопрос может быть чистой итерацией без отдельного archival Markdown;
- длинный offline-пакет должен обязательно пережить доставку и обработку, но постоянный смысловой статус принимает агент после того, как действительно услышал запись;
- явное «сохрани / запомни» — сильная пользовательская команда агенту;
- пока решение агента не зафиксировано function-call receipt, аудио/source journal не очищаются.

Поэтому старый “20 секунд” удаляется из нормативной продуктовой логики. Он может использоваться только как тестовый сигнал для observability или консервативного retention, но не как правило semantic archive.

## 6. Проекты выбирает агент, backend только проверяет права

Текущий проект — **фокус рассуждения агента**, а не обязательная вручную выбранная форма.

Backend предоставляет thin tools:
- `projects.list_accessible()`;
- `projects.get(project_id)`;
- `project_docs.search(project_id, query)`;
- `project_docs.read(project_id, ref)`;
- `conversation.set_focus(project_id | null)`;
- typed mutation tools соответствующих owning products.

Live-агент сам понимает:
- «теперь про фестиваль»;
- «это уже в клуб»;
- «сравни всё, что есть по трём проектам»;
- «нет, предыдущую мысль отнеси к подкасту».

Детерминированный backend **не угадывает project_id по ключевым словам**. Он лишь:
- валидирует, что агент указал разрешённый project_id;
- проверяет права перед каждым read/write;
- сохраняет focus/links/receipts;
- возвращает ошибку/варианты при недоступном или устаревшем объекте.

Если агент не уверен, он задаёт вопрос. Неоднозначная речь уже сохранена в личном source journal, поэтому уточнение не создаёт риска потери.

### Multi-project Live scope

Существующий `ProjectScope(tenant, subject, project_id)` в resource bootstrap недостаточен как финальная модель разговоров. Один Live-разговор пользователя должен иметь доступ к нескольким разрешённым проектам без переподключения модели при каждой смене темы.

Целевая граница:
- Live session привязана к **actor + tenant/workspace/conversation resource**, а не к одному semantic project;
- project authorization выполняется каждым tool call;
- список доступных проектов задаётся server-owned контекстом и thin tools;
- resource/quota binding не используется как механизм object authorization.

Существующий одно-проектный adapter необходимо эволюционно изменить; он остаётся scaffold, не продуктовым контрактом.

## 7. Словарь — функция агента, не отдельного “обработчика”

Live-агент может:
1. запросить список/поиск документов разрешённого проекта;
2. прочитать релевантные README, manifests, терминологические файлы и документы;
3. сравнить их с текущим словарём;
4. вызвать `vocabulary.upsert_grounded(...)`;
5. получить receipt и использовать новый контекст далее.

Thin tools не генерируют semantic aliases отдельной моделью. Они могут детерминированно:
- читать точный файл;
- выдавать diff/revision;
- хранить term/alias/source refs;
- проверять schema/ACL/optimistic concurrency.

Источником нового semantic alias является либо явный документ, либо вывод **центрального Live-агента**, основанный на прочитанных документах, либо явная поправка пользователя. Собственная ошибочная input transcription без дополнительного основания не должна сама себя закреплять.

Словарь помогает агенту понимать речь и нормализовать сохраняемый transcript. Не обещается, что arbitrary словарь напрямую настраивает provider ASR: для Live-модели он передаётся как bounded contextual terminology и/или доступен через tool result. Provider-specific speech adaptation добавляется только после фактической поддержки/приёмки.

## 8. Function calls — руки агента, а не второй мозг

### Разрешено

Детерминированные/предметные tools:
- read/list/search разрешённых источников;
- сохранить source/disposition;
- обновить документ по expected revision;
- создать/принять/завершить задачу;
- записать решение/голос;
- проверить календарь и создать событие;
- отправить разрешённое уведомление;
- обновить словарь;
- получить readback/receipt.

Tool может содержать сложную прикладную транзакцию, retries, idempotency и reconciliation. Это не делает его “интеллектом”.

### Запрещено по умолчанию

За function call не должен скрываться:
- другой LLM, который решает, что имел в виду пользователь;
- LLM-маршрутизатор проектов;
- LLM-суммаризатор речи перед центральным агентом;
- LLM-классификатор ценности/типа записи;
- отдельный conversation agent, который переписывает ответ Live-модели;
- незаявленный fallback на старую AI-архитектуру.

Если когда-нибудь появляется отдельная специализированная модель, это отдельное осознанное продуктовое решение с видимой ролью. Она не может незаметно стать “настоящим мозгом”, оставив Live-модель озвучивать её результат.

## 9. Что должно быть детерминированным обязательно

Чтобы Live-агент был умным, а не хрупким, детерминированный слой обязан делать вещи, где “догадка модели” недопустима:
- захват/локальная сохранность аудио;
- sequence/manifest/checksum и resumable transfer;
- auth/ACL;
- resource limits/leases;
- idempotency;
- optimistic concurrency;
- command/result ledger;
- readback и reconciliation;
- database constraints;
- retention по уже принятому disposition;
- формирование безопасного tool schema;
- transport backpressure;
- строгая привязка команд к device/user/session;
- indexes/retrieval как доступ к данным.

Это инфраструктура вокруг мозга, а не замена мозга.

## 10. Обнаруженные несовместимости текущего shared framework

Аудит текущего `live-interaction` показал несколько важных ограничений, которые нельзя пропустить при реализации Projects Hub.

### A. Reconnect сейчас сознательно не хранит речь

В `provider.py` есть правило: при отсутствии WebSocket capture отбрасывается — “Never queue or replay old speech”. Для обычного realtime recovery это разумно, но Projects Hub требует product-owned durable capture.

Решение: не превращать transport reconnect buffer в вечную очередь. Projects Hub сохраняет аудио **до** transport; после восстановления намеренно создаёт buffered Live turn и передаёт source через новый bounded framework path.

### B. Input transcription включена уже сейчас

`setup_config()` содержит `inputAudioTranscription: {}`. Отдельный ASR перед Live не нужен для базовой архитектуры.

### C. Transcript event режется до 2000 символов

Текущий provider делает `text[:2000]`. Это недопустимая граница для source archive длинных пользовательских реплик.

Нужное изменение framework: полный provider transcription event должен быть доступен product observer/persistence. Bounded UI/event projection может быть отдельной усечённой проекцией, но не источником архива.

### D. Session event ring ограничен 320 событиями

`LiveSessionHost` хранит 320 событий для polling UI. На него нельзя опираться как на долговечную историю. Product adapter должен сохранять source/transcript/tool receipts **до** потери из ring buffer.

### E. Browser transcript preview хранит только хвост

Текущий client держит последние ~1000 символов для голосового UX. Это UI preview, не transcript store. Projects Hub не читает из него архив.

### F. Start history урезана

Python host передаёт максимум 8 последних элементов, по 700 символов. Это допустимый lightweight bootstrap, но не память проекта. Центральный агент получает старые источники через product context/tools и conversation memory, а не надеется на provider history array.

### G. Buffered turn требует явной границы activity

Текущий wire знает `audio` и `audio_stream_end`, но не `activityStart/activityEnd`/manual activity mode. Для длинного offline replay framework нужно расширить версионируемо и проверить на настоящем provider.

Эти пункты — **реальные implementation dependencies**, а не повод вводить отдельный ASR/agent pipeline.

## 11. Критерий архитектурной чистоты

Любая новая функция проходит вопрос:

> Если убрать Live-модель, останется ли в tool/backend код, который самостоятельно решает смысл пользовательской речи?

Если да — нужно проверить, не появился ли второй скрытый агент.

Допустимы только точные deterministic policy decisions (ACL, schema, revision, quota, idempotency, retention после disposition) и механический retrieval. Смысловая интерпретация, проектная маршрутизация, диалог, выбор следующего вопроса и semantic memory disposition принадлежат центральному Live-агенту.

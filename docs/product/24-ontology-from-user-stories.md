## 1. Коротко

- **Центр модели — процесс.** Владелец: «в проекте может быть энное количество workflow, которые настраиваются и действуют», «задача workflow — ничего не забыть». Проект подключает виды процессов. Конкретная работа идёт как **дело** — запущенный процесс над конкретным предметом: выпуском, спикером, фестивалем, гипотезой, доработкой.
- **Процесс собирается из стандартных элементов:** этапы, пункты чек-листа, данные, роли, обращения, подпроцессы и выходы во внешние системы. Владелец: «workflow должны строиться сугубо на стандартных инструментах, на стандартной онтологии».
- **Три процесса уже работают в коде,** но каждый зашит отдельно: аналитика с вопросами, доработка через Codex, готовность события. Предложение — описать их и новые процессы одинаково.
- **Вопрос уже реализован** и почти целиком покрывает обращение: адресат и роль, блокирующий, приоритет, срок, варианты, «ответ, не знаю, пропуск, позже». Обращение — это вопрос, расширенный видами «сделать», «выбрать», «напомнить», «рассмотреть» и правилом ответа.
- **Процесс описывается данными, а не кодом.** Действия правил берутся из фиксированного набора, реализованного в projects-hub. Это совместимо с [ADR-10](04-architecture.md#adr-10-базовая-коллаборация-без-отдельной-workflow-платформы) и запретом BPM-конструктора в [07](07-delivery.md).
- **Процессы донастраиваются.** Владелец проекта или системы описывает изменение историей, dot задаёт вопросы по стандартному потоку и выпускает новую версию процесса. Версии неизменны, дело помнит свою версию, изменения приходят с бэкенда без переустановки приложения.
- **Slack.** Если проект включён в projects-hub, обсуждения его каналов хранятся полностью. Дело связано с тредом.

## 2. Схема

```
ПРОЕКТ ─── вид проекта ───► подключённые ВИДЫ ПРОЦЕССОВ (workflow)
  │                            этапы · пункты чек-листа · данные · роли
  │                            правила · подпроцессы · канал Slack
  │                                        │ запускается над предметом
  │                                        ▼
  ├─ ДЕЛО ═══════════════ экземпляр процесса ════════════════════════════
  │   предмет ──► ОБЪЕКТЫ: персона, мероприятие, идея, гипотеза, риск,
  │                        документ, решение, файл
  │   этап, пункты с состоянием, данные, ответственный, роли, сроки
  │   ОБРАЩЕНИЯ: вопрос · задача · выбор/голосование · напоминание · рассмотреть
  │   подпроцессы: дочерние дела, например аналитика или разбор звонка
  │   ЗАПИСИ: связанные сообщения Slack, голос, звонки, заметки
  │   треды Slack, документы GitHub, журнал
  │ ═════════════════════════════════════════════════════════════════════
  ├─ УЧАСТНИКИ: человек │ агент (Мира, dot) │ бот; права и роли в проекте
  └─ ПРЕДСТАВЛЕНИЯ, не данные: доска, сводная таблица, карточка дела,
                               брифинг, колокольчик, «что нового»
```

Записи, объекты и обращения могут существовать и без дела: идея вне процесса, вопрос «просто спросить», напоминание себе. Процесс подключается, когда работе нужна полнота и порядок.

## 3. Процесс: вид процесса

Вид процесса — это workflow-шаблон проекта. Его настраивает владелец, Мира и dot помогают его описать.

```
ВИД ПРОЦЕССА  «Подготовка выпуска подкаста», версия 3
├─ предмет: выпуск; связанные объекты: гость, мероприятие записи
├─ роли: владелец процесса, менеджер, ведущий
├─ этапы (ориентир, можно вернуться):
│    подбор → подготовка → согласование → готовность к записи → запись
│    → монтаж → подготовка публикации → опубликовано
├─ пункты чек-листа:
│    вид:      данные (поле) │ действие │ подтверждение
│    этап, обязательность, срок до события, ответственный по роли
│    если не выполнен к сроку: напомнить │ поставить задачу │ спросить
├─ правила (действия только из фиксированного набора):
│    когда: вход в этап │ пункт выполнен │ наступила дата │ итог обращения
│    что:   создать обращение │ запустить подпроцесс │ событие в календаре
│           │ публикация │ уведомить по правилу │ сообщение в тред Slack
├─ подпроцессы: подготовка гостя, согласование встречи, аналитика, публикация
├─ уведомления: кому и о чём сообщать, что только копить
└─ Slack: канал по умолчанию, что бот пишет в тред дела
```

**Почему это не BPM-движок.** В виде процесса нет языка программирования, ветвлений и произвольных скриптов. Этапы — ориентир, а не жёсткая машина переходов. Каждое действие правила — заранее реализованная и проверенная операция projects-hub с квитанцией. Новый вид процесса — это новые данные, а не новый код.

### Донастройка процесса

Идеального процесса не бывает, что-то всегда забудут. Настраивают процесс не профессионалы, а владельцы своими историями. По решению владельца вся настройка пока у dot.

```
владелец проекта или системы:
«я хочу …, сделав …, в итоге получив …, чтобы …»   голосом Мире или в треде Slack
   │
   ▼
ДЕЛО «Изменение процесса: Подготовка выпуска»      процесс: Донастройка процесса
   ├─ dot переводит историю в проект изменения: этапы, пункты, поля, правила
   ├─ dot задаёт вопросы по стандартному потоку вопросов: немного и по делу
   ├─ итерации, пока владелец не подтвердит
   ├─ проверка: новая версия проходит Gherkin-пример истории на тестовом деле
   ├─ одобрение тем же владельцем
   └─ публикация новой версии на бэкенде
        не хватает вида поля или действия правила → доработка через Codex
```

Требования к хранению, чтобы донастройка была гибкой и безопасной:

| Требование | Как это устроено |
| --- | --- |
| Определение процесса — данные | Версия хранится документом определения: этапы, пункты, поля, правила, подпроцессы. Канон — файл в репозитории проекта для процессов проекта и в репозитории projects-hub для общих процессов. Бэкенд проверяет файл по схеме и держит индекс активной версии |
| Опубликованная версия не меняется | Изменение — это новая версия с описанием, что и зачем изменено, ссылками на истории, автором и одобрившим |
| Дело помнит свою версию | Начатые дела остаются на своей версии. Перевод на новую — явное действие владельца с отчётом: новые пункты становятся «не проверено», удалённые уходят в архив вместе с данными |
| Пункт можно добавить в одно дело | Разовый пункт работает только в этом деле и может стать частью процесса через донастройку |
| Откат | Предыдущая версия снова становится активной, данные дел не теряются |
| Проверка до публикации | Схема, допустимые действия правил, ссылки на роли и поля, проход Gherkin-примера на тестовом деле |
| Права | Запросить — владелец проекта для процессов проекта, владелец системы для общих. Исполнить — dot в выданных границах. Одобрить — тот же владелец |

**Почему без переустановки приложения.** Клиент и Мира не знают о конкретных процессах. Клиент рисует карточку дела, таблицу и чек-лист по определению из стандартных видов полей: текст, число и деньги, дата и время с часовым поясом, участник, выбор, файл, ссылка, состояние пункта. Инструменты Миры тоже общие: прочитать дело, отметить пункт, заполнить поле, создать обращение. Поэтому новая версия процесса приходит с бэкенда. Сейчас Android-оболочка загружает актуальную PWA с бэкенда ([18](18-android-mvp-acceptance-2026-10-04.md)), и изменения интерфейса тоже не требуют переустановки. Для целевого нативного клиента это правило становится обязательным. Обновление приложения нужно только для нового вида поля или новой возможности телефона, и тогда оно идёт через самообновление.

## 4. Дело: запущенный процесс

Дело отвечает на вопросы «что делаем, на каком этапе, чего не хватает, кого ждём». В программе подкаста дело выпуска уже описано как задача с предметными полями; здесь та же идея обобщена.

| Часть дела | Содержание |
| --- | --- |
| Идентичность | `id`, проект, вид процесса и его версия, название |
| Предмет | ссылки на объекты: гость, мероприятие, идея, гипотеза |
| Люди | владелец дела, участники по ролям процесса |
| Этап | текущий этап и история смены этапов: кто, когда, почему |
| Пункты | для каждого пункта шаблона: состояние, ответственный, срок, основание, когда проверено |
| Состояние пункта | не проверено, не готово, готово, не применимо с причиной. «Готово» ставится по подтверждению или чтению результата, а не по намерению модели |
| Данные | значения полей шаблона. Сведения о самом предмете, например контакты гостя, хранятся в объекте, а не в деле |
| Риски | объекты-риски, привязанные к этапу или пункту |
| Обращения | открытые и закрытые вопросы, задачи, выборы, связанные с делом |
| Подпроцессы | дочерние дела, например «согласование встречи» или «аналитика» |
| Материалы | записи, документы GitHub с путём и SHA, файлы |
| Slack | один или несколько тредов дела |
| Состояние дела | идёт, на паузе, завершено с итогом, отменено |
| Вычисляется | полнота, просрочено, кого ждём, требует внимания |

Пример дела в карточке и таблице:

```
ДЕЛО «Выпуск: Иванов, 24 октября»        процесс: Подготовка выпуска v3
этап: согласование                        владелец: Максим · менеджер: Анастасия
предмет: гость Иванов (персона) · запись 24.10 15:00 Калининград (мероприятие)
пункты:
  ✓ готово       карточка гостя          досье в GitHub @a1b2c3
  ✓ готово       дата согласована        ответ гостя в Slack, 12.10
  ✗ не готово    время согласовано       ждём гостя, срок 18.10
  ? не проверено вопросы подготовлены    ответственный: менеджер
  – не применимо  обложка                 «выпуск только аудио»
обращения: «выбрать время» → гость (открыто, срок 18.10)
подпроцессы: аналитика досье (завершена, 2 вопроса отвечены)
риск: «библиотека может быть закрыта 24.10» → этап «готовность к записи»
Slack: тред в #podcast
```

## 5. Обращение и уже реализованный вопрос

### Как устроен вопрос сейчас

Вопрос реализован в `collaboration_questions` и всегда принадлежит пакету вопросов, который создаёт анализ.

| Поле вопроса | Значение |
| --- | --- |
| `asked_by_actor_id`, `addressed_to_actor_id`, `addressed_role` | кто спрашивает, кому, в какой роли |
| `prompt`, `shared_context`, `reason` | вопрос, общий контекст пакета, зачем спрашиваем |
| `blocking`, `priority`, `deadline_ms` | блокирует ли работу; критичный, высокий, обычный, низкий; срок |
| `alternatives_json` | варианты ответа |
| `state` | открыт, решён, пропущен, неизвестно, отложен |
| `disposition`, `answer_text`, `answered_by_actor_id` | ответ, «не знаю», пропуск или «позже»; текст; кто ответил |
| `deferred_until_ms` | «позже» по умолчанию возвращает вопрос через сутки |
| `expected_revision`, `stale_since_ms` | версия источника; поле устаревания пока никто не заполняет |

| Пакет вопросов и анализ | Значение |
| --- | --- |
| Источник | ровно один: заметка, документ, задача, идея или объект доски, с версией |
| Исполнитель анализа | Kimi, DeepSeek или dot; результат в Markdown и JSON |
| Состояние пакета | активен, на паузе, ждёт ответов, всё отвечено, ждёт доставки, завершён, завершён частично, отменён |
| Управление | предложение Мирой и согласие, пауза, «только важное» |
| Доставка | исходный тред Slack, уведомление Миры, квитанции ответов `collaboration_answer_commands` |

Отдельно `owner_development_questions` задаёт владельцу вопросы, когда доработка остановилась и ждёт решения.

### Обращение как расширение вопроса

Владелец просит, чтобы вопросы были «хорошо продуманными, осознанными, их было немного, они не были тупыми и не бесили пользователя». Поэтому обращение строится на уже проверенном вопросе, а не рядом с ним.

| Что добавить к вопросу | Зачем |
| --- | --- |
| вид: спросить, сделать, выбрать, напомнить, рассмотреть | задача, голосование, напоминание и решение по предложению используют тот же механизм |
| адресат: участник, роль, группа, агент, сам себе | поручение роли, голосование группы, напоминание себе |
| правило ответа | см. таблицу ниже |
| связь с делом и пунктом | итог обращения закрывает пункт чек-листа или меняет данные дела |
| для «сделать»: принял, в работе, блокер, результат, принято постановщиком | назначение не равно принятому обязательству |
| пакет без анализа | вопросы могут собираться из дела или вручную, а не только из анализа |

| Правило ответа | Истории |
| --- | --- |
| Отвечает один человек | вопрос ответственному 14, вопрос о простое 41, предложение по мероприятию 51 |
| Делает один человек, принимает постановщик | поручение 39, задача из чек-листа 34, задача после решения 56 |
| Себе со сроком | напоминание 43 |
| Роль: делает первый, кто взял | поручение роли 40 |
| Группа: отвечает каждый | приглашение волонтёров 46, ответ на слоты 48 |
| Группа: большинство с кворумом | голосование 55 |
| Мнения с рекомендательным весом, решает уполномоченный | консилиум 55, просьба партнёра 45 |
| Роль: ответы копятся | верификация 68 |
| Исполняет агент или бот | вопросы dot 25, публикация 62, импорт 67, регулярная задача 47 |

Молчание не превращается в согласие. Нет кворума — «решение не принято».

## 6. Объекты и записи

| Сущность | Поля | Отличие |
| --- | --- | --- |
| **Объект** | `id`, проект, тип, название, поля по типу, связи, ревизия с автором правки; для документа — репозиторий, путь и SHA | То, что живёт дольше одного дела. Один гость может участвовать в нескольких выпусках. Аналитика дополняет объект, а не создаёт копию |
| **Запись** | `id`, проект, автор, окно: Мира, приложение, Slack, звонок, чат, импорт; внешний ключ, например канал и `ts` Slack; время; текст или ссылка на аудио и файл; ревизия источника; признак удаления; связанные дела и объекты | Неизменный ввод. Из неё дополняют объект или дело. Slack виден 90 дней, поэтому сообщение должно стать записью в projects-hub |

Типы объектов из историй: персона, мероприятие или встреча, идея, гипотеза, риск, документ, решение, файл, цель или правило проекта.

## 9. Связка со Slack

Решение владельца 14 октября: если проект включён в projects-hub, обсуждения его каналов хранятся полностью. Каналы проектов, не включённых в projects-hub, не захватываются.

```
SLACK (бесплатный тариф)                   PROJECTS-HUB
канал включённого проекта ─────────────► проект        все сообщения канала хранятся
  тред ────────────────────────────────► дело          у дела может быть несколько тредов;
                                                       тред может быть без дела
    сообщение ─────────────────────────► запись        правка — новая ревизия,
                                                       удаление — скрытый текст и след
пользователь ──────────────────────────► участник      через внешнюю учётку
файл в сообщении ──────────────────────► файл проекта  ссылка Slack — происхождение
упоминание бота ───────────────────────► команда       создать или обновить дело, отметить
                                                       пункт, сохранить решение, ответить
```

Обратно бот пишет только по правилам вида процесса:

| Событие в projects-hub | Что появляется в Slack |
| --- | --- |
| Новое дело | Сообщение бота в канале процесса со ссылкой на карточку дела. Его тред становится тредом дела |
| Смена этапа, важный пункт, блокер, итог | Ответ в треде дела |
| Обращение по делу | Ответ в треде дела с упоминанием адресата |
| Выбор или голосование | Сообщение с кнопками. Ответ кнопкой и голосом Мире считается одинаково |
| Идея, заметка, личная запись | Ничего, пока участник явно не поделился |

Всё это делается бесплатными возможностями Slack: бот пишет сообщения, читает историю каналов включённых проектов, получает упоминания и нажатия кнопок. Платные группы пользователей, Workflow Builder, гостевые аккаунты и Slack Connect не используются. Поэтому поручение роли в Slack упоминает участников поимённо.

Для переноса данных из Slack предлагается собственный бот projects-hub. dot работает поверх уже сохранённых данных. Обоснование в [документе 23 §5](23-collaboration-swiss-watch-proposal.md#5-синхронизация-со-slack-взаимная-и-неблокирующая).

## 10. Кандидаты в MVP

MVP — это несколько процессов целиком, а не отдельные функции. В него входят только процессы, где истории имеют реальность «было» или «нужно». Окончательный список подтверждает прогон с Мирой.

| Процесс | Почему в MVP | Истории |
| --- | --- | --- |
| Аналитика с вопросами | уже работает и проверен на пилоте | 25 |
| Подготовка выпуска подкаста с подпроцессами гостя и встречи | реальный пилот, нужен владельцу сейчас | 31–33, 48, 49 |
| Доработка | уже работает | 63, 64 |
| Сигнал о сбое | нужен для эксплуатации | 13 |
| Донастройка процесса через dot | без неё процесс подкаста не улучшить после первого выпуска | 75–77 |

Вне процессов в MVP входят ввод и поиск: PH-US-06, PH-US-11, PH-US-12, PH-US-14, PH-US-17. Туда же входят поручение и напоминание: PH-US-39, PH-US-42, PH-US-43.

Каждый процесс MVP получает Gherkin-сценарий основного пути и один-два сценария сбоя: Slack недоступен, dot молчит, источник изменился. Требования надёжности из [документа 23](23-collaboration-swiss-watch-proposal.md) проверяются на этих сценариях.

## 11. Что сознательно не входит

- язык программирования процессов, ветвления и произвольные скрипты;
- сложные взвешенные схемы голосования сверх рекомендательного и решающего веса;
- платные возможности Slack и захват каналов проектов, не включённых в projects-hub;
- автоматическое создание задач из любой реплики без явной команды или правила процесса;
- отдельная таблица на каждый вид процесса или тип объекта.

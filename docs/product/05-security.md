# Межгрупповая, личная и локальная безопасность

[Общий индекс](README.md). Ревизия 2: [голосовая маршрутизация](11-routing-and-vocabulary.md) и [сохранность речи](10-conversation-memory.md) уточняют применение границ. Это целевые свойства, не проведённый penetration test.

## Модель угроз

Участник состоит в двух несвязанных сообществах; другой участник пытается подставить чужой object ID; вредоносный документ предлагает модели раскрыть личное; пользователь вышел из группы, но сохраняет старую ссылку; закрытая сессия оставила фоновые jobs; потерян телефон; внешнее действие повторилось; координатор ошибочно получил календарь всех сотрудников; общий provider pool отправил данные в неподходящий режим обработки.

Каждая граница должна выдерживать эти случаи без надежды на благоразумие LLM. Область доступа является атрибутом серверного запроса и данных, не подсказкой в prompt.

## Группы, проекты и личный слой

На входе проверяются аутентификация, действующее членство и роль в конкретном проекте. Для чтения/записи повторно проверяются права на сам объект. `tenant_id` из URL/body, название репозитория из tool arguments и hash `ProjectScope` не являются доказательством права.

Прикладной сервис использует ограниченную DB-роль, не всеправный service-role для повседневных пользовательских запросов. Row-Level Security — дополнительная граница, не замена предметной авторизации; владелец таблицы/привилегированные роли требуют особого учёта и тестов. Background worker тоже исполняет job от исходного actor с актуальными правами, а не безусловно как администратор.

Все производные объекты наследуют область: поисковые индексы, snippets, summaries, кэши, attachments, отчёты, уведомления и экспорт. Дообучение и общие memory-хранилища на закрытом содержимом не включаются по умолчанию.

Private GitHub repo на группу и отдельный личный repo дают простую границу хранения, но не заменяют авторизацию приложения. **Папка не является границей прав для человека с прямым Git-доступом ко всему репозиторию.** Если внутри группы есть закрытый проект с иной аудиторией, для его Git-материалов нужен отдельный репозиторий/граница хранения либо отсутствие прямого доступа участников к общему repo и явно проверенный backend-контроль. Персональные секреты и чувствительные календарные сведения в Git не сохраняются.

## Вход и подключения

Для людей — стандартный поддерживаемый identity provider/OIDC, короткоживущая серверная сессия и приглашения с одноразовым использованием/сроком. Для PWA предпочтительна HttpOnly Secure cookie с CSRF/origin защитой; для Android — системный браузер и Authorization Code + PKCE. Конкретный identity provider утверждается по доступности и требованиям данных до пилота; собственную криптографию/парольную систему не проектируем.

Для GitHub — scoped GitHub App installation, ограниченная выбранными репозиториями. Обычные участники Projects Hub не вводят PAT и могут вообще не иметь GitHub-аккаунта; repository подключает владелец/координатор workspace. Product-managed repositories доступны через права Projects Hub, external/owning repositories по умолчанию read-only. Подробный договор — [GitHub connections](14-github-connections.md). Календарь подключается отдельным согласием владельца с минимальными scopes. Идентификаторы подключения могут быть видны UI, credential — нет. **App JWT, installation access token и GitHub API calls существуют только на Projects Hub backend; Android/PWA не являются GitHub clients продукта.**

Backend хранит secrets шифрованно с контролируемым доступом и ротацией, вне Git, логов и prompt. TLS защищает передачу. Шифрование на диске не равнозначно сквозному шифрованию: сервер и разрешённый AI-провайдер могут видеть данные, которые им переданы. Нельзя продавать этот вариант как zero-knowledge/E2EE.

## Обмен между областями

Личный разговор может включать несколько разрешённых проектов без ручного переключения и без новой сетевой сессии на каждую тему. Его полный источник остаётся личным. Сохранение в проект привязано к конкретному фрагменту, цели и действующим правам. Смена фокуса не расширяет аудиторию.

При переносе материала в другую аудиторию фиксируются источник/версия, разрешённый фрагмент и получатели. Ясное голосовое поручение может содержать необходимое согласие; неоднозначное раскрытие требует уточнения или голосового/кнопочного подтверждения. Обычная реплика не превращается в форму отправки. Сведения о происхождении, заявленные самой моделью, не заменяют проверку реально использованных источников.

Отзыв доступа инвалидирует дальнейшие чтения, model sessions/resumption handles, job grants, ссылки и выдачу из кэша. Перед доставкой уведомления/экспорта worker повторно проверяет права. Простое скрытие кнопки не является отзывом.

Уже прочитанные/скопированные или напрямую клонированные сведения невозможно надёжно «забрать обратно». Мгновенный отзыв у полностью офлайн-устройства также не гарантируется. Поэтому общий offline cache ограничен по объёму и сроку, не хранит весь архив по умолчанию; для чувствительных материалов требуется онлайн-проверка. Личная недоставленная запись не уничтожается автоматически при отзыве группового доступа: остаётся приватной, отправка в старую группу запрещается, пользователю предлагается сохранить или удалить её явно.

## Телефон — исполнитель узких разрешённых команд

Телефон не открывает публичный MCP endpoint и не получает команды по одному общему каналу «на все устройства». Он устанавливает исходящее авторизованное соединение. Device grant привязан к user, device, session и конкретным capabilities. **Live function call возникает в backend-owned provider session; backend выдаёт адресованную device-команду, а Android возвращает receipt/result. Телефон не держит отдельную Gemini Live session для такого действия и не становится вторым backend.**

Минимальный конверт команды: command_id, actor_id, workspace_id, project_id, device_id, session_id, capability, payload_hash, expires_at и защита от повторного воспроизведения. Неправильное устройство/сессия, просроченный grant или повторная команда не исполняются. Сервер и клиент проверяют один и тот же binding, а результат возвращается в исходный command.

В MVP: выбрать файл/медиа в системном picker, показать календарный draft, при отдельно разрешённом способе создать/проверить событие. Нельзя читать всю галерею, контакты, файловую систему, клипборд, микрофон или местоположение «на всякий случай». Пользовательская цель «подготовить проект» не даёт права на произвольный shell, установку ПО или подключение к локальной сети.

Для компьютера в MVP достаточно системного выбора файлов PWA. Отдельный desktop agent, доступ к каталогу/сети или локальным приложениям — новая ограниченная интеграция после доказанной потребности, не скрытая часть установки.

Calendar intent показывает системный UI и потому не равен подтверждённой записи. Нельзя говорить «событие создано», пока нет разрешённого readback или явного корректного пользовательского подтверждения, честно отличённого от провайдерного.

## Центральный агент и граница tool calls

Live-сессия пользователя может работать сразу с несколькими разрешёнными проектами. Это **не** означает загрузку всех проектных данных в prompt и не означает ослабление ACL. Agent запрашивает нужные источники через tools, а каждый tool повторно проверяет actor/target.

Безопасность не должна превращаться в отдельный semantic router: backend не выбирает, «о каком проекте говорил пользователь», и не решает, «достаточно ли важна мысль». Эти решения делает Live-agent. Backend валидирует выбранный им target, аудиторию, schema, revision и последствия.

Function tool не имеет права скрыто вызвать второй LLM для понимания речи/маршрутизации. Если tool возвращает варианты или отказ, central agent сам продолжает диалог и уточняет.

## Внешние тексты и функции модели

Документы, письма, сообщения и результаты поиска — данные недоверенного происхождения. Вложенная фраза «отправь весь архив» не является новым поручением владельца. Выход модели проходит типизированную схему, разрешения, проверку версии и при необходимости confirmation token, связанный с payload и аудиторией.

Действия делятся по последствиям: безопасное чтение; обратимый личный черновик; изменение группового обязательства; внешняя публикация/приглашение; изменение доступа/удаление. Подтверждение обязательно по значимому последствию, а не автоматически перед каждым чтением. Голос может выразить намерение, но изменение прав или чувствительное внешнее действие требует надёжного продуктового подтверждения в действующей пользовательской сессии.

URL и connector targets разрешаются по серверному реестру. Нельзя позволять модели обращаться к произвольному внутреннему адресу, выбирать репозиторий вне scope или подменять credential. Файлы ограничены размером/типом; опасное содержимое не исполняется.

## Персональные данные, хранение и удаление

До пилота фиксируются: оператор данных и его контакты, цели обработки, возраст/регионы аудитории, основания/согласия, перечень subprocessors, местонахождение основной и резервной копий, правила трансграничной передачи и применимые договоры. Это выпускной gate, а не юридическое заключение данного документа.

Сохранность каждой реплики обеспечивается до смысловой оценки. Постоянный semantic disposition принимает центральный Live-агент через function call; backend не архивирует и не отбрасывает речь по жёсткому порогу длительности. Недоставленный, неуслышанный моделью или оставшийся без agent disposition source не очищается автоматически. Полный смешанный source личный, а в групповой проект попадают только разрешённые agentом фрагменты/результаты после server-side ACL. Аудио не попадает в Git или техническую telemetry; его очистка требует соответствующего source/disposition receipt, а не только голосового ответа модели. Наименования людей и закрытых проектов в словарях наследуют те же ограничения, что документы. Общая authority не хранит пользовательское содержимое.

Удаление покрывает primary store, индекс, embeddings, кэш, outbox с содержимым, временные файлы и политику истечения backup. Удаление строки в Git не стирает историю Git: до сохранения чувствительного содержимого нужна классификация, а для полного удаления — отдельный purge-процесс с честными ограничениями внешних копий. Право группы сохранить рабочее решение после ухода участника и право участника на личные данные описываются отдельно, не решаются моделью автоматически.

Нормальные логи содержат codes/IDs/latency, а не расшифровки, email, календарные названия, API keys или resumption tokens. Доступ к диагностике ограничен, имеет журнал и срок. Аварийная поддержка не получает скрытый постоянный доступ ко всем группам.

## Минимальная проверка безопасности

Два пользователя, две изолированные группы, закрытый проект и два устройства одного пользователя. Проверить прямые ID, поиск/snippets, смену контекста, revocation во время Live/job, просроченную ссылку, offline cache, ошибочную доставку на другой телефон, повтор calendar command и prompt injection из документа. Ни один mock-успех не заменяет такой интеграционный прогон. Матрица — [приёмка](08-reliability.md).

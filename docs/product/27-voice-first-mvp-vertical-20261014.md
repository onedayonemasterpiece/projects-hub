## 1. Вывод

- **Половина пути уже есть.** Фокус проекта необязателен, Мира сама выбирает проект и сама переключает его внутри одного разговора. Голос сохраняется до разбора. Одну реплику Мира уже умеет разложить по нескольким проектам через память, и повтор сохранения не создаёт дубль.
- **Не хватает трёх вещей.**
  1. Приватности личной записи.
  2. Справочника предметов с именами, чтобы Мира нашла «спикера Иванова» и «выпуск 24-го».
  3. Типизированной правки этих предметов с ревизией и квитанцией.
- **Для поручения волонтёру** нужны общие задачи с реальным исполнителем и повторный вход того же человека.
- **Полнотекстовый поиск по архиву для этой вертикали не нужен.** Для предметов хватает имён и связей. PH-US-14 остаётся открытым to-be.
- **Всё работает без dot.** dot получает те же данные через тот же сервис по MCP.

## 3. Маршрут с нулевого контекста

```
человек говорит
   │
   ▼
1. запись голоса сохранена (source, ревизия расшифровки)   ← ничего не теряется
   │
   ▼
2. Мира понимает, о чём реплика, и для каждой части:
   ├─ явная ссылка или текущая карточка → этот предмет
   ├─ имя, выпуск, дата → subject_find по разрешённым проектам
   │     один кандидат → он
   │     два и больше → один короткий вопрос с отличием («выпуск 17-го или 24-го?»)
   │     ни одного → новая идея или новый предмет, если человек этого хочет
   └─ ничего не подходит, проект неясен → личная запись без проекта
   │
   ▼
3. запись в цель:
   ├─ личная мысль        → memory_commit, видна только автору
   ├─ проектная новость   → memory_commit в проект с правом
   └─ изменение предмета  → subject_update с ревизией и command_id
   │
   ▼
4. квитанция: что, куда, новая ревизия → Мира говорит одной фразой
   │
   ▼
5. «нет, на субботу» → subject_update того же предмета с новой ревизией
```

Отдельный сервис, модель или слой маршрутизации не нужен. Мира уже выбирает смысл, а backend только отдаёт компактных кандидатов в разрешённой области.

**Правила выбора цели:**
- **Явная ссылка сильнее похожести.** Текущий фокус помогает, но не обязателен.
- **Уточнение только при неоднозначности, влияющей на запись.** Вопрос один и короткий.
- **Несколько проектов в реплике** дают раздельные записи. У каждой свой target и ссылка на тот же source.
- **Распознавание не даёт права на общую запись.** Общая запись требует команды или явного намерения и права на проект. Иначе запись остаётся личной.
- **«Спикер может в пятницу» меняет только доступность в участии.** Встречу, приглашение или обязательство такая фраза не создаёт.
- **Новый спикер** — это новая персона-предмет, а не новый участник projects-hub.

## 4. Что дополнить

### Данные

| Что | Минимум | Истории |
| --- | --- | --- |
| Приватность памяти | Запись без проекта видна только автору исходного голоса. Чтение памяти проекта требует права на проект. Запись в проект требует права на проект | PH-US-04, PH-US-07 |
| Предмет | `subjects`: id, проект, вид (персона, выпуск, мероприятие, идея), название, алиасы, поля, ревизия, кто и когда изменил | PH-US-27, PH-US-49 |
| Участие | `subject_links`: персона ↔ выпуск, роль «гость», поля участия: доступность, тема, согласие, гонорар; своя ревизия | PH-US-49, POD-US-03 |
| Общая задача | к `tasks`: постановщик, исполнитель-участник или роль, кто принял, результат, ревизия, проверка прав проекта | PH-US-39, PH-US-40, PH-US-42, POD-US-08 |
| Роли проекта | `project_role_members`: проект, роль, участник. Роль не даёт прав | PH-US-40 |
| Повторный вход | приглашение для уже существующего участника вместо создания нового | POD-US-01 |

Выпуск подкаста как дело с чек-листом из [документа 24](24-ontology-from-user-stories.md) сюда не входит. Для этой вертикали выпуск — предмет с полями. Чек-лист добавляется следующим шагом поверх тех же предметов.

### Инструменты Миры

Стартовый набор «ввод» заменяет нынешний core и укладывается в 6 функций, чтобы сохранять сказанное без переключения capability:

| Функция | Что делает |
| --- | --- |
| `projects_list_accessible` | как сейчас |
| `subject_find` | имя, алиас, вид, проект, дата → до 5 кандидатов с отличительными полями и ревизией |
| `subject_update` | правка полей предмета или участия: `expected_revision`, `command_id`, ссылка на source; ответ — квитанция с новой ревизией и коротким итоговым состоянием |
| `subject_create` | новая персона или выпуск, только по явному намерению |
| `memory_commit_voice_source` | как сейчас, с приватностью |
| `memory_finish_ephemeral` | как сейчас |

`conversation_set_focus` и настройки темы переходят в соседние наборы. Задачи для волонтёра идут отдельным набором из трёх функций: «что ждут от меня», «принять задачу», «сообщить результат», все с ревизией.

Имена предметов включённых проектов добавляются в словарь распознавания вместе с названиями проектов. Лимит общий, 100 терминов.

### MCP для dot

Те же методы сервиса доступны по MCP: `subject_find`, `subject_get`, `subject_update`. Действует право service-участника на проект. Это не второй канон и не имитация голосовой сессии.

## 5. Область, источник, ревизия, повтор

- **Область.** Личное видит только автор. Проектное видят участники с правом на проект. Права проверяются на каждом чтении, поиске кандидатов и записи.
- **Источник.** Каждая запись и правка хранит ссылку на source и его ревизию расшифровки.
- **Ревизия.** Правка без актуальной `expected_revision` получает конфликт и текущее состояние. Чужое изменение не перезаписывается.
- **Повтор.** `command_id` формируется из source и порядкового номера действия в нём. Повтор после обрыва возвращает прежнюю квитанцию. Другое содержимое с тем же `command_id` даёт конфликт.
- **Немедленное исправление.** После квитанции Мира знает ID и ревизию предмета. «Нет, на субботу» идёт прямо в него, без поиска.

## 6. Вход волонтёра

POD-US-01, POD-US-08. Выдача доступа в рамках этой постановки не выполняется.

1. Владелец приглашает волонтёра. Повторное приглашение того же человека выдаёт вход тому же участнику.
2. Волонтёр входит с телефона и получает право на проект и роль «волонтёр».
3. При приветствии Мира говорит, что от него ждут: адресованная задача или вопрос.
4. Волонтёр голосом принимает задачу, позже сообщает результат. Каждое действие возвращает квитанцию с ревизией.
5. Владелец читает ту же сохранённую версию.
6. После отзыва права следующие операции волонтёра отклоняются.

## 8. Шесть проб и уровень проверки

| Проба | Что подтверждает | Код | Тест | Голос |
| --- | --- | --- | --- | --- |
| 1. Идея без проекта с нулевого контекста | приватная запись, без экрана | фильтр памяти по автору | другой участник не видит запись | на телефоне |
| 2. Известный спикер и новая доступность | найдено участие, изменены поля, встреча не создана | `subject_find`, `subject_update` | квитанция, ревизия +1, нет записей календаря | на телефоне |
| 3. Два Иванова или два выпуска | один вопрос, ни слияния, ни дубля | кандидаты с отличиями | два кандидата → нет записи до ответа | на телефоне |
| 4. Два проекта и личная мысль в одной реплике | раздельные цели, личное не видно команде | несколько commit по одному source | права по каждой цели | на телефоне |
| 5. Пятница → суббота, повтор после обрыва | тот же предмет, без дубля и перезаписи | `expected_revision`, `command_id` | повтор → та же квитанция; устаревшая ревизия → конфликт | на телефоне с обрывом сети |
| 6. Волонтёр: вход, принятие, результат, отзыв | одна личность, общая версия, отказ после отзыва | общие задачи, приглашение для существующего участника | повторный вход тот же `actor_id`; после отзыва отказ | два телефона |

Тест на заглушках не засчитывается как голосовая приёмка.

## 9. Порядок

1. **Приватность памяти и права при записи.** Это небольшая правка и обязательное условие до входа второго человека.
2. **Предметы, участие и три функции ввода.** Пробы 1–5.
3. **Общие задачи, роли, повторный вход волонтёра.** Проба 6.

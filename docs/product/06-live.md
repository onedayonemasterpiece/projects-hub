## Нормальный режим

Сначала аутентификация пользователя и права проекта, затем проверка data/region policy, затем shared admission. На сервер передаются только разрешённые конфигурации; provider и authority keys никогда не поступают в клиент. Фактические квоты задаются для проверенного provider project/scope, а не считаются по количеству строк с API keys.

Один общий limiter обязан учитывать несколько consumer products и несколько пользователей Projects Hub. Один активный участник не должен занять весь бюджет сообщества. Предлагаемые tenant/user budget и fair admission реализуются совместимо с общим контроллером, а не независимыми локальными счётчиками квоты. Прикладные бюджеты не отменяют более строгий provider ceiling. Непроверенные «Unlimited» и числа из другого model family не копируются.

Live-сессия приобретает lease, использует resource_guard перед provider operations и освобождает/дренирует его при закрытии. Потеря ответа или неопределённый close не означает, что ресурс немедленно свободен. Для provider resumption сохраняется тот же разрешённый binding/lease/key в пределах общего контракта. Изменение аудитории требует новой модельной сессии.

## Аварийный fallback: строго существующая семантика

Допустим только при `RESOURCE_CONTROL_UNAVAILABLE` на исходной **read-only capabilities** проверке, до первого mutating acquire. После успешной проверки authority, потерянного acquire response, quota/429, запрета, отсутствия capacity, credential error или provider ready этот путь запрещён.

Используется только назначенный Projects Hub source alias, преобразованный в общий generic field. Не заимствуются keys других продуктов, не выбирается случайный alias и не выполняется переключение посреди разговора. Ограничение — одна emergency-сессия этого consumer на **host** с межпроцессной синхронизацией и hard expiry по SDK (сейчас два часа). Отдельной продуктовой реализации fallback нет.

Host-wide lock не равен глобальному lock между несколькими серверами. До появления подтверждённого общего multi-host аварийного договора fallback разрешается только на назначенном host; горизонтальное масштабирование не должно умножать аварийную ёмкость. При отсутствии подходящего fallback остаются текст, чтение и локальная запись с честным уведомлением об ограничении.

## Существенный preflight до реального бизнес-пилота

Проверенные официальные условия Gemini API различают unpaid/paid обработку данных и ограничивают доступные регионы/возраст. Россия отсутствует в опубликованном списке; зарубежный backend сам по себе не разрешает обслуживать любую аудиторию. Нельзя использовать неподходящий unpaid режим для закрытых бизнес-данных. [Условия и список регионов](09-research.md).

Проектное следствие: нужны проверяемые разрешения для user region, класса данных, возраста аудитории, договора и каждого provider scope. Проверяется **и central кандидат, и fallback**. Шифрование ключа защищает выдачу credential, но не меняет условия обработки содержимого моделью. Признак активного billing не является универсальной юридической сертификацией.

До этого допускаются разработка независимого ядра и синтетические тесты. Для фактической российской аудитории требуется совместимый разрешённый путь провайдера/договора, исследованный отдельно. Не обещать в этом документе, что конкретная ещё не проверенная альтернатива уже поддерживает нужный Live tool calling. Новая поддержка провайдера должна принадлежать общему framework/контроллеру, а не скрытому старому AI backend в Projects Hub.

## Жизненный цикл и экономия без потери намерения

VAD/чанки уменьшают лишнюю передачу, но не гарантируют нулевой расход во время тишины. Провайдерный контекст, выходное аудио и удержание сеанса тоже требуют учёта. Отдельно существуют process heartbeat, клиентская активность и пользовательское намерение продолжать разговор.

Stop немедленно прекращает локальный захват/воспроизведение; backend прекращает provider session и fencing блокирует поздние callbacks. Недоступный клиент не удерживает lease бесконечно лишь потому, что server worker жив. Короткая пауза на мысль не должна восприниматься как конец разговора. Конкретные inactivity/grace deadlines настраиваются после измерений и имеют конечные пределы.

При плановой смене provider connection работают общий GoAway/resumption/compression механизм и durable состояние продукта. Короткое reconnect не перепроигрывает пользовательскую речь и не выполняет повторно mutations. Документация Gemini описывает отдельные ограничения сессии и соединения; длительный диалог нельзя строить на предположении о вечном WebSocket.

## Тяжёлая аналитика и обратная совместимость

«Разобрать накопленные идеи» может стать отдельной задачей: явный объём/бюджет, progress, отмена и durable handle. Статус проверяется детерминированно без повторного LLM-вызова каждый раз. Пока анализ выполняется, дорогой Live-канал не обязан быть открытым.

Обычная запись/ASR intake остаётся отличным от Live путём с собственной явной допустимой политикой провайдера; не мигрировать работающий Record Idea Hub автоматически. Offline означает захват и очередь, не гарантированное распознавание/ответ модели на устройстве.

## Проверка интеграции

Нужны offline контракты shared API и отдельный разрешённый реальный canary: mic → provider → один разрешённый tool → подтверждённый результат → Stop → release. Затем конкуренция с другими consumers, fallback preflight outage, lost acquire, 429, reconnect/GoAway, закрытие приложения и process kill. Реальные секреты остаются в доверенном runtime; отчёт содержит только безопасные идентификаторы и итог.

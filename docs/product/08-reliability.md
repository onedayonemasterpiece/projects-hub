# Надёжность, восстановление и выпускная приёмка

[Общий индекс](README.md). Все цифры ниже — **целевые критерии для измерения**, не фактические результаты текущего scaffold.

## Что значит «работает надёжно»

Пользователь не должен гадать, записывается ли голос, куда он отправлен, принял ли человек задачу, произошло ли внешнее действие и сохранится ли результат при закрытии приложения. Надёжность — сохранность намерения, точный статус и восстановление, а не только uptime модели.

Нормальный workflow не требует от владельца ручного перезапуска, повторного наговаривания или очистки данных приложения. Если невозможно доказать успех, показывается pending/unknown/failed, а не «готово».

## Три независимых жизненных цикла

**Запись:** recording → local_saved → uploading → server_received → transcribed → materialized_verified. Сообщение «на устройстве» означает только устройство. HTTP 200 на загрузку не равно сохранению распознанного материала в GitHub. До нужной квитанции источник не удаляется молча.

**Команда:** draft → confirmation_required/accepted → queued → running → provider_pending → verified_success, failed либо outcome_unknown. При retry используется тот же command_id и fingerprint, а не новая команда.

**Обязательство человека:** proposed → accepted/declined → in_progress/blocked → done/cancelled. Успех tool call не означает, что человек выполнил задачу, а запись в календаре не означает, что встреча состоялась.

Идемпотентность обеспечивается ограничениями БД, состоянием операции и контрактом провайдера. «Exactly once» нельзя обещать для внешнего API без соответствующей поддержки: используется at-least-once delivery, deduplication и reconciliation. После timeout неидемпотентного create сначала ищется существующий результат по устойчивому ID/handle; без способа проверки статус остаётся неизвестным и требуется безопасное разрешение, а не слепой повтор.

## Инженерные меры без лишней платформы

Транзакционная запись command+outbox, lease/fence у worker, bounded retry с backoff, ограниченная concurrency, dead-letter с видимым статусом и разрешённым повтором. Сессии модели хранят ссылки на задания, а задания не зависят от живого prompt. Истёкший worker не может поздним callback перетереть новый результат.

Upload возобновляется по чанкам/устойчивым идентификаторам и проверке целостности. Очередь переживает restart/reboot в заявленном Android-сценарии; заполнение диска/квоты даёт предупреждение до невозможной записи. Нельзя считать ограничения браузерного storage устранёнными: для PWA требуется честный статус persistence и путь экспорта/восстановления, без обещания сохранности после очистки данных браузера.

Live Stop и UI restart разрывают старый lifecycle; поздние callbacks игнорируются. Scope switch создаёт новый контекст. Необработанная команда сохраняет состояние независимо от Stop. Прекращение сеанса не отменяет уже выполненное внешнее действие.

## Поведение при отказах

| Отказ | Требуемая реакция |
| --- | --- |
| Нет сети | Голос локально, текст/разрешённый кэш доступны; новая групповая запись не объявляется доставленной |
| Нет Live либо исчерпан бюджет | Нет молчаливого обхода; ручные действия и очередь сохраняются |
| Authority недоступна до acquire | Только назначенный SDK fallback и подходящая data policy; иначе отказ Live без потери материала |
| Ответ acquire потерян | Не включать локальный fallback: аренда могла уже существовать |
| GitHub недоступен | Pending материализация и источник сохранены; не говорить «документ обновлён» |
| Чужая параллельная правка | Версионный конфликт, перечитывание, новая правка; не force push |
| Calendar create timeout | Проверить существующий результат, не плодить встречи |
| Push не доставлен | Событие остаётся в личном списке; bounded retry, без нескончаемого дублирования |
| Участник потерял доступ | Прекратить чтение/доставку/новые действия; сохранить допустимое приватное состояние без утечки группе |
| Android процесс остановлен | Восстановить очередь; не изображать продолжающуюся запись после фактической остановки микрофона |
| Provider GoAway | Общий bounded resumption, без повтора mutations и без смены credential после ready |
| Прикладная БД недоступна | Не выполнять новое внешнее действие, которое невозможно надёжно зарегистрировать |

## Цели и границы SLA

Для пилота: ноль обнаруженных межгрупповых раскрытий и повторных бизнес-эффектов в обязательной матрице; все тестовые offline-записи восстановлены и материализованы; каждая команда имеет наблюдаемый терминальный или явно pending/unknown статус. Это проверяемые критерии набора сценариев, не доказательство отсутствия всех будущих багов.

Ориентиры UX: начало локальной записи p95 до 0,5 с на поддерживаемом устройстве; немедленная локальная реакция Stop; начало понятной обратной связи по сетевой операции до 3 с на согласованном профиле сети. Последнее может быть progress, а не готовый ответ модели. Provider latency и его выбросы измеряются отдельно и не прячутся усреднением.

Цель доступности прикладного ядра перед коммерческим SLA — 99,9% в месяц; это не обещание такой доступности Gemini или телефона. Для резервного восстановления исходные инженерные цели — RPO не более 15 минут при полном отказе площадки, RTO не более 60 минут, затем подтвердить restore drill или ужесточить архитектуру под обещаемый тариф. Локальный commit/репликация и аварийный RPO — разные гарантии. Нельзя говорить «никакая подтверждённая запись никогда не потеряется», пока disaster-recovery действительно этого не обеспечивает.

## Форма доказательства и остановка релиза

На каждый gate: версия клиента/backend/SDK, среда и устройство, предпосылки, вход, ожидаемый результат, фактический результат, безопасная ссылка на свидетельство, reviewer и дата. Синтетические, offline, staging, реальный provider и настоящий пользователь различаются. Unrun/blocked не переводятся в PASS по наличию тестового файла.

Любой подтверждённый межгрупповой доступ, потеря принятых записей в поддерживаемом recovery-сценарии, дублирующая внешняя запись или неподходящая обработка данных блокирует соответствующий rollout. Отключается затронутая функция/новые сеансы; безопасное ядро и имеющиеся документы сохраняются. Не обнулять central quota ledger ради восстановления видимой доступности.

## Наблюдаемость

Возраст очереди, доля/возраст outcome_unknown, конфликтные правки, незавершённые commands, микрофонные interruptions, срок живущих lease, реальные расходы, раздельная backend/provider latency. Ошибки классифицированы; уведомление поддержки не содержит пользовательский текст. Перегрузка одного workspace ограничивается без остановки остальных.

На исходном checkpoint этого пакета продуктовые gates ещё не пройдены. Существующие resource unit-tests и проверки целостности документации должны сообщаться отдельно от runtime acceptance.

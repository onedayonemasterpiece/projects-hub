# Платформы, архитектура и связность проектов

[Общий индекс](README.md). Решения этого документа — целевая реализация, а не описание уже развёрнутого сервиса.

## ADR-01: PWA и Android, один backend

**Выбор: оба клиента, но не две полноценные независимые реализации.** PWA даёт вход по ссылке, работу на компьютере и участие людей с iPhone. Android нужен для длительной записи, устойчивой локальной очереди и узких функций телефона. PWA-first означает порядок первой сквозной сборки, а не обещание заменить ею надёжный диктофон.

| Возможность | PWA | Android MVP |
| --- | --- | --- |
| Участие, проекты, карточки, голосование, текст | Полный базовый путь | Те же API и минимальные необходимые представления |
| Короткая запись и Live | В активной видимой странице | Нативный захват и общий серверный транспорт |
| Длительная запись с заблокированным экраном | Не обещается | Явно запущенная пользователем запись с microphone foreground service; тестируется на устройствах |
| Очередь без сети | Локально в браузере с видимыми ограничениями хранения | Надёжная очередь из подходов Record Idea Hub, восстановление после перезапуска |
| Локальные файлы | Выбор пользователем через системный picker | Photo Picker / Storage Access Framework, не доступ ко всему диску |
| Календарь | Авторизованный серверный коннектор или ICS | Тот же коннектор; локальный intent как ограниченная альтернатива |
| Push | При доступности платформы и разрешении пользователя | Платформенный канал и разрешение; не условие сохранения данных |

Ограничения браузера нельзя лечить обещаниями Service Worker: Screen Wake Lock относится к активному документу и может быть освобождён; push на iOS имеет условия установки/разрешения. Android foreground service тоже не означает бессмертный процесс. Источники — [проверка платформ](09-research.md).

## ADR-02: стек и границы

Сохраняем существующий Python package. Целевой backend — Python ASGI/FastAPI, модульный монолит и отдельный worker той же кодовой базы. Прикладная PostgreSQL хранит транзакции и outbox; для MVP достаточно очереди заданий в этой БД. Не нужны Kafka, Kubernetes, отдельная векторная БД или распределённый агентный оркестратор.

PWA — TypeScript/React с доступными компонентами, версионируемым API и проверяемыми build assets. Android — компактный Kotlin-клиент с нативной записью и небольшим интерфейсом; не WebView-обёртка, выдаваемая за надёжную фоновую запись. Общие схемы API, состояния карточек и тестовые сценарии важнее попытки буквально разделить весь UI-код.

Нативный Android VAD/chunk/queue переиспользуется из Record Idea Hub через поддерживаемый модуль/извлечение с совместными тестами. Существующий код не копируется в расходящиеся форки. Live audio lifecycle и provider session остаются в `live-interaction`. Если необходим адаптер для нативного потока, добавляется маленький версионируемый контракт в общий framework; нельзя предполагать, что опубликованная JS-библиотека уже является Android SDK.

Backend размещается на DevCoveer в соответствии с действующим ограничением проекта, без Fly.io и без GitHub self-hosted runners. CI — обычный облачный GitHub Actions; локальные тесты — прямые инструменты DevCoveer. Физическая локация, доступность PostgreSQL, резервное хранение и требования к персональным данным подтверждаются перед rollout: имя сервера само по себе этого не доказывает.

## ADR-03: один владелец для каждого вида данных

| Данные | Канонический владелец | Что допустимо хранить в другом месте |
| --- | --- | --- |
| Подробная идея, проектная документация, утверждённый содержательный материал | Разрешённый private GitHub repository | Поисковая проекция со source revision; восстановима |
| Статусы задач, голоса, RSVP, предложения времени | Прикладная PostgreSQL | Представление в UI и документальный итог, но не второй оперативный master |
| Пользователи, членство, роли, device grants, связи коннекторов | Прикладная PostgreSQL / серверное защищённое хранилище секретов | Только минимальные идентификаторы и разрешённые атрибуты |
| Команды, receipts, outbox, статус внешней операции | Прикладная PostgreSQL | UI-статус и ссылки на проверенный результат |
| Временное аудио и недоставленные записи | Локальная очередь; затем ограниченное серверное временное хранилище | Не Git и не общий quota ledger |
| Общий Live quota/lease/grant | Существующий `ai-resource-control` и его authority | Только минимальная прикладная ссылка на ресурсную сессию |
| Личные календарные сведения и частные черновики | Личная область пользователя с отдельными правами | В группе только явно разрешённая проекция, например свободно/занято |

Прикладная БД — не новый Supabase quota ledger. Не помещать задачи, аудио, профили и переписку в общую базу лимиттера. Начать с отдельной прикладной БД/роли; не объявлять новую установку Supabase обязательной. Точная схема размещения выбирается после инфраструктурного preflight, без переноса существующих данных вслепую.

GitHub — база документации, но не подходящая замена транзакционному хранению высокочастотных голосов/статусов. Восстановимые индексы не редактируются напрямую как альтернативная правда. Изменение документа извне обнаруживается webhook либо сверкой SHA; устаревшая проекция помечается и обновляется. Последняя успешная синхронизация видна диагностике.

## ADR-04: логические сущности и операции

Минимальное ядро: Workspace, Membership, Project, Idea/DocumentRef, Task, Proposal/Decision, MeetingProposal, DeviceGrant, Command/Receipt, OutboxEvent. Личное пространство — отдельная область доступа, не строка с особым флагом внутри общего индекса. Один проект может иметь несколько документов, но не обязан создавать отдельный репозиторий для каждого файла.

Команда содержит устойчивый ID, тип операции, ссылку на целевой объект, ожидаемую ревизию и payload. Actor/workspace/права вычисляет backend из сессии; значения из JSON и аргументов модели не являются авторизацией. Подтверждение связано с конкретными параметрами и версией аудитории. Receipt содержит статус, revision, ссылку на результат, время проверки и необходимые человеку замечания.

Для внутренних сущностей command+mutation+outbox фиксируются одной транзакцией. Внешний GitHub/calendar вызов нельзя сделать атомарным с PostgreSQL: worker выполняет его по устойчивому ID, сохраняет remote handle, затем проверяет результат. «Принято в очередь» и «сохранено в GitHub» — разные статусы.

Состояние сохраняется до расходной операции. При потере ответа после записи сначала выполняется reconciliation по известному идентификатору, а не повторный create. Для GitHub CAS используется ожидаемая версия документа и защищённое продвижение ref без force; чужое изменение приводит к перечитыванию и новой согласованной правке. Для одного документа операции упорядочены; разные проекты и чтения не блокируются общей глобальной очередью.

Не вводим CRDT-редактор одновременно с голосовой координацией. В MVP достаточно версии документа, небольшой правки и понятного конфликта. Нельзя пересохранять весь огромный репозиторий на каждом turn.

## ADR-05: контекст и поиск

Начальный контекст — только текущая разрешённая область, цель проекта, актуальные решения и выбранный объект. Остальное извлекается по запросу. Поиск фильтрует доступные документы **до** передачи модели и до ранжирования, которое может раскрыть закрытые названия. Ключи кэша включают workspace, principal/действующие права, project и source revision.

Первый индекс — текстовый поиск PostgreSQL и явные ссылки на документы. Векторный поиск добавляется после проверки качества на реальных вопросах, не как обязательная платформа. Даже будущие embeddings и summaries наследуют доступы источника и удаляются/перестраиваются при отзыве.

Переключение группы создаёт новый разрешённый модельный контекст. Нельзя просто сказать старой модели «забудь личное» и продолжать ту же сессию с общей публикацией. Межгрупповой обзор возможен в личной области человека с его правами; перенос результата в группу — отдельная операция с проверкой раскрываемых сведений.

## Связность экосистемы: роли, а не массовое подключение инструментов

| Owning project | Использование в Projects Hub | Что остаётся у владельца |
| --- | --- | --- |
| `idea-hub` | Источники требований, авторизованные документы, обратные ссылки на результаты | Канонический intake и исходная личная информация |
| `record-idea-hub` | Захват, VAD/chunks и durable queue как переиспользуемая база | Работающее приложение до независимой приёмки замены |
| `live-interaction` | Голосовой транспорт, Stop/playback, lifecycle и recovery | Общие исправления транспорта и версионируемые релизы |
| `ai-resource-control` | Общий admission, leases, budgets и назначенный fallback | Единственная quota authority; корректность общего ресурса |
| `my-data-hub` | Совместимые чтение/поиск/маршрутизация при явных разрешениях | Существующие источники и ограничения; личное не публикуется в showcase |
| `wonderful-lections` | Ссылка на лекцию и разрешённое действие с материалом | Слайды, тезисы, экспорт и предметный контракт лекции |
| `events-bot-new` / KenigEvents | Разрешённые карточки событий и подтверждённые внешние результаты | Канонические события и публикация афиши |
| `street-story` | Будущая передача выбранного брифа/готового результата | Предметная подготовка и публикация истории, не новый дубликат в Projects Hub |

Эта таблица и [contract.json](contract.json) фиксируют плановые границы. Она **не утверждает**, что все интеграции уже включены. Для передачи во внешний продукт: scoped connection, target ID, actor, command ID, expected revision, подтверждение эффекта и readback. Наличие MCP-инструмента у владельца не даёт всем участникам группы те же полномочия.

Telegram/MAX и VibePublish рассматриваются как разрешённые каналы через имеющиеся адаптеры, не повод писать ещё один издательский backend. В MVP достаточно нейтрального уведомления/ссылки; сплошное чтение переписок и двусторонняя синхронизация внешних групп отложены. Полный каталог MCP не включается в контекст каждой Live-сессии.

## Эксплуатация и переносимость

Один репозиторий продукта содержит backend, PWA, Android и контрактные тесты. Private shared SDK устанавливается доверенным deployment-процессом с pinned release integrity, не копируется в публичное дерево. Config и capability flags отделены от модели.

Резервные копии прикладной БД и materialized документов имеют отдельное размещение и проверяемое восстановление. Пользовательский экспорт включает свои разрешённые документы/задачи/решения в открытых форматах; не выгружает credentials и чужие личные данные. Смена хоста не должна требовать изменения логики модели или хранения вторых копий ключей под произвольными алиасами.

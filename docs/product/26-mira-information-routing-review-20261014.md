# 26. Маршрут информации для Миры: единый доступ, источники и поиск

**Дата:** 14 октября 2026. **Статус:** аналитическое предложение для следующего раунда Claude. Это не разрешение на реализацию, модельные прогоны, выдачу прав или deploy.

**Зафиксированные основания:** код main [`76bc5f2d84424f26bf3d0056687ae6a5dfcbde81`](https://github.com/onedayonemasterpiece/projects-hub/tree/76bc5f2d84424f26bf3d0056687ae6a5dfcbde81); [онтология 24](https://github.com/onedayonemasterpiece/projects-hub/blob/faae84048a8a65e30e5ff0af610993af31b7bff8/docs/product/24-ontology-from-user-stories.md) и [реестр историй](https://github.com/onedayonemasterpiece/projects-hub/blob/faae84048a8a65e30e5ff0af610993af31b7bff8/docs/product/user-stories.md) PR172; [предыдущий раунд dot, документ 25](https://github.com/onedayonemasterpiece/projects-hub/blob/a518e90351a3c3fb7250ec6ddf4b32b7fd1b40f7/docs/product/25-collaboration-model-dot-review-20261014.md). Документ24 и API текущего main — разные уровни готовности.

Новые решения владельца из обновлённого документа24 — донастройка без лишних согласований, автоперенос добавлений, канон процесса в базе, проектная аудитория Slack и удаление исходного текста — здесь не пересматриваются. Точные границы их применения сохраняются; внутренний выбор индекса не должен создавать новый круг продуктовых согласований.

## 1. Вердикт

Мире нужен единый понятный доступ к предметным данным и первоисточникам, а не весь проект в промпте. **Существующий краткий startup сохраняем:** основное изменение — последующее точное чтение, поиск, пагинация и запись с проверенной версией.

- Текущие состояния, сроки, исполнителей, готовность и принятые решения читаем из канонических сущностей по ID, связям и фильтрам.
- Для «где обсуждали и почему» нужен поиск содержания с последующим чтением источника и окружения. Список последних заметок этого не заменяет.
- Мира уже выбирает capability. Второй семантический router, отдельный поисковый агент и универсальный BPM не нужны.
- Один сервисный контракт должен обслуживать Live, разрешённый MCP и Slack. Одинаковая семантика не означает одинаковые полномочия.
- Vector — необязательный производный индекс кандидатов. Добавлять его при измеренных промахах на перефразах, если это улучшает реальную работу; не превращать внедрение индекса в самостоятельную цель.
- До масштабирования нужны полноценное чтение больших документов, честная полнота выдачи, source revisions, read-your-writes и единообразная фильтрация доступа до раскрытия snippets/counts.

### 2.4. Права и версия

**Сильные проверенные границы:** project_access проверяет membership, active project, неотозванный grant, требуемую роль/can_analyze/can_manage_share ([store.py:2649–2682](https://github.com/onedayonemasterpiece/projects-hub/blob/76bc5f2d84424f26bf3d0056687ae6a5dfcbde81/src/projects_hub/store.py#L2649-L2682)); notes и board используют его. Actor identity берётся из backend session, не из пользовательских tool args. GitHub repository_token rechecks project access; write требует editor + app_managed_write и запрещает external_owning_repo write ([github_connections.py:473–521](https://github.com/onedayonemasterpiece/projects-hub/blob/76bc5f2d84424f26bf3d0056687ae6a5dfcbde81/src/projects_hub/github_connections.py#L473-L521)). Regional Knowledge отдельно проверяет actor/workspace grant. Приватный voice_source нельзя читать от другого actor/conversation.

Для нового общего доступа требуется одинаковая политика actor-private и project-shared областей на list/get/search/write. Фильтры применяются до раскрытия snippets, названий и counts; чтение найденного объекта повторно проверяет актуальные grants. Индекс и сохранённый handle не являются источниками полномочий.

**Дополнительно проверенный статический дефект memory.** На main `76bc5f2d84424f26bf3d0056687ae6a5dfcbde81` цепочка [app.py:1151–1185](https://github.com/onedayonemasterpiece/projects-hub/blob/76bc5f2d84424f26bf3d0056687ae6a5dfcbde81/src/projects_hub/app.py#L1151-L1185) → Live capability guard → [memory dispatch:3007–3053](https://github.com/onedayonemasterpiece/projects-hub/blob/76bc5f2d84424f26bf3d0056687ae6a5dfcbde81/src/projects_hub/live_adapter.py#L3007-L3053) передаёт доверенную identity, но не добавляет project ACL. [list_memories:3370–3390](https://github.com/onedayonemasterpiece/projects-hub/blob/76bc5f2d84424f26bf3d0056687ae6a5dfcbde81/src/projects_hub/store.py#L3370-L3390) проверяет membership и существование указанного проекта, без project_grants; при project_id=None нет actor/project filter. [commit_memory:3224–3254](https://github.com/onedayonemasterpiece/projects-hub/blob/76bc5f2d84424f26bf3d0056687ae6a5dfcbde81/src/projects_hub/store.py#L3224-L3254) проверяет владельца source и active target project, но не grant назначения. Это потенциальное межпроектное/личное раскрытие summaries и запись без проектного grant. Фактические данные, эксплуатация и утечка в production не проверялись. Исправление: явная actor-private/project-shared область, одинаковый grant gate чтения/записи/поиска и отрицательные тесты до расширения корпуса индекса. Данные посторонних пользователей для проверки не читались.

**Версии:** memory имеет transcript_revision/revision/content_sha256; notes имеют revision+repo blob/commit SHA; board имеет object_revision/board_seq; voice paged reader возвращает transcript_revision. Но offsets без ожидаемой revision могут читать смешанную версию при изменении между страницами; для нового API нужен cursor, привязанный к source revision. GitHub read сейчас возвращает текущий blob SHA, не позволяет продолжить чтение по нему.

**Source freeze:** analysis `_freeze_note` фиксирует note revision/SHA + все replies и ограничивает evidence60000bytes ([collaboration_analysis.py:532–584](https://github.com/onedayonemasterpiece/projects-hub/blob/76bc5f2d84424f26bf3d0056687ae6a5dfcbde81/src/projects_hub/collaboration_analysis.py#L532-L584)). Это provided-context-only analysis, не автоматическое исследование всего проекта. Векторный similarity hit не заменяет этот source snapshot и не подтверждает версию ответа.

### 2.5. Что действительно доступно dot по MCP

[TOOLS:77–96](https://github.com/onedayonemasterpiece/projects-hub/blob/76bc5f2d84424f26bf3d0056687ae6a5dfcbde81/src/projects_hub/mcp_api.py#L77-L96), dispatch:213–235 — ровно:

- get_test_request

Это дополнительно подтверждено каталогом текущего подключённого Projects Hub MCP 14 октября, независимо от чтения кода. Никаких list_projects, search_information, get_note, patch_entity или общего document read/write в этом каталоге нет. Наличие GitHub/Slack коннекторов у dot — отдельный доступ, не реализация симметричного API projects-hub. Конкретные request записи без предоставленного ID не читались.

[mcp_bindings.get_request:156–199](https://github.com/onedayonemasterpiece/projects-hub/blob/76bc5f2d84424f26bf3d0056687ae6a5dfcbde81/src/projects_hub/mcp_bindings.py#L156-L199): известный request_id открывает bound note+latest50 replies, question package, все answer receipts, точные source revision/repo path/SHA, binding revision и Slack destination. Не произвольный поиск; latest50 не снабжён cursor/has_more. Complete answer receipts при этом не ограничены страницей.

Проверяются binding, контекстный человек, service grant и source revision. Slack здесь только конкретная привязка и receipt; полного архива канала и общего channel-search main не предоставляет. `record_request_result` поддерживает ограниченные typed replies/question packages/analysis results/Slack claim/receipt, не произвольную правку сущностей.

### 2.6. Симметрия пока частичная

У Миры notes поддерживают list/get/create/reply/analyze, но не общий update; repositories — list/read; memory — recent read и grounded voice commit. Board имеет search/history/edit с expected revision. У dot — bound request/result. Наличие внутреннего writer не означает публичную операцию Live или MCP. Общий сервис должен переиспользовать эти домены, а не создавать второй канон.

### 2.7. Задержки: гипотезы для измерения

Потенциально дорогие пути видны в коде: capability-switch с provider setup, дополнительные чтения каждого результата при startup, полные notes/replies в tool result, скан всей доски и последовательные GitHub token/content fetch. Это не измеренный production p95. Уже есть полезный пример compact backlog: комментарий Live:2582–2620 описывает отказ resource guard на прежнем ответе около59KB. Улучшать payload и число roundtrips следует раньше усложнения ranking; сохранять summary→details и повторно использовать действующие tools.

## 3. Целевой маршрут и предметные данные

### 3.1. Два режима доступа

**Точное операционное чтение:** что сейчас сохранено как состояние, обязательство, срок, результат и разрешённое действие. Маршрут преимущественно ID → связи → структурные фильтры.

**Поиск содержания:** где обсуждали мысль, почему приняли решение, какой документ содержит аргумент, что похоже на прошлый случай. Маршрут lexical/optional semantic → чтение первоисточника → связь с предметными данными.

Один запрос может сочетать режимы: «что изменилось и почему» читает текущую ревизию и источник изменения. Но discovery score никогда не заменяет канонический статус.

#### Текущие предметные данные

Дела, пункты готовности, задачи, назначенные исполнители, вопросы, напоминания, встречи, текущая версия процесса и их связи. Это первый источник для «что сейчас?», «кто отвечает?», «готово ли?», «что осталось?».

Общий inbox объединяет ожидания пользователя, но не смешивает lifecycle задачи и вопроса. Исполнитель может быть человеком, агентом или ботом. Поиск не должен представлять предложенную задачу как принятое обязательство или отправленный reminder как выполненную работу.

#### Первичные записи и материалы

Сообщения Slack, голосовые и их расшифровки, документы и версии GitHub, файлы, заметки, исходные ответы на вопросы. Они нужны для объяснения, подробностей, происхождения и информации, ещё не перенесённой в структурные поля.

Досье человека и договорённость с этим человеком по конкретному выпуску имеют разные области применимости. Вопрос «какой гонорар согласован с гостем?» маршрутизируется через выбранный выпуск/участие, а не просто в общую карточку персоны.

#### Зафиксированные решения и производные материалы

Решение, принятая задача и пункт дела, возникшие из обсуждения, — самостоятельные проектные данные. Удаление исходного Slack-текста не удаляет их автоматически по принятому решению владельца. Но ссылка происхождения становится tombstone: нельзя подставлять удалённую цитату из cache/embedding chunk и выдавать её за доступное доказательство.

Резюме, синтез анализа, поисковый snippet и embedding — производные. Они помогают отбирать материал, но не заменяют источник и не получают собственную предметную authority. Итоговая задача/решение сохраняется потому, что была создана как предметное изменение, а не потому, что любой автоматически сделанный пересказ считается вечным самостоятельным документом.

#### Журнал событий

«Что изменилось после вчерашнего разговора?» читается из событий с временной границей и объектными ссылками. Не следует искать вчерашнее событие вектором по всему тексту или возвращать обзор всех сообщений вместо изменений, значимых для пользователя.

Журнал, первичная запись и текущее состояние связаны, но не взаимозаменяемы. Например: журнал фиксирует назначение, задача показывает текущего исполнителя, Slack-сообщение объясняет договорённость.

### 3.2. Кратчайший маршрут

Мира определяет действие и область в существующем Live-контуре; backend проверяет допустимые фильтры. Выбор способа извлечения — развилка, не обязательные шесть последовательных поисков:

1. Явный ID/ссылка/активная карточка → прямое чтение.
2. Текущий выпуск → связи на гостя, договорённость участия, задачи, документы, вопросы и треды.
3. «Мои просроченные», «за три дня» → actor/status/deadline/time filters с часовым поясом.
4. «Где обсуждали» без точного предмета → lexical по разрешённому scope; при доказанной пользе semantic candidates.
5. Найденный кандидат → чтение канонического состояния/источника и актуальной revision, затем ответ или типизированное изменение.

Одна точная ссылка сильнее похожести. При двух подходящих Ивановых уточняется различие; старое обсуждение не заменяет актуальное обязательство. Обычному ответу предпочтительно одно structured read либо search→batch read. Это не жёсткий потолок для сложного сравнения.

Пустая выдача означает отсутствие совпадений только в проверенной области. Отдельно сообщаются partial coverage, неготовый импорт, непрочитанный файл и недоступность источника; защищённые названия/counts не раскрываются. Не заказывать сильный анализ, пока достаточно прочитать сохранённое. Не переносить найденное между проектами автоматически.

### 3.3. Один контракт для Миры и MCP

#### Небольшие контекстные наборы

Для чтения достаточно набора из четырёх логических операций:

- `get_context`: короткий паспорт выбранного проекта/предмета и актуальные ожидания;
- `query_information`: структурный запрос либо поиск с проверенной областью, без обязанности клиента выбирать FTS/vector;
- `read_information`: пакетное и постраничное чтение точных объектов/источников или разрешённых фрагментов с pinned revision и явным продолжением;
- `get_activity`: изменения по actor/project/subject/time/cursor.

Для записи контекст переключается на небольшой набор: `read_information`, `capture_information`, `apply_change`, `get_operation`. При вопросах/поручениях используются существующие предметные операции ответов и задач, а не универсальное выполнение произвольного JSON. Это предложение формы интерфейса; если действующие endpoints уже обеспечивают контракт, их нужно переиспользовать, а не заводить дубли.

#### Что принимает поиск

`query`, `project_ids` или текущий scope, `subject_ref`, допустимые `kinds`, временной интервал, actors/roles, statuses, лимит/курсор и режим результата: карточки, evidence snippets либо aggregated facts. Для structured query поля типизированы; произвольный SQL от модели не допускается.

Backend может автоматически использовать точное разрешение ID, FTS или гибрид, но возвращает, **что именно найдено и почему**. Пользовательские фразы «последний», «просроченные», «мои» превращаются в явные фильтры с часовым поясом, а не остаются лишь токенами семантического запроса.

#### Что возвращает поиск

- внутренний ID, тип предмета, project ID/название в разрешённом scope;
- краткое название и релевантный snippet с указанием, что это фрагмент, а не полный документ;
- source reference: тип, ID, revision/commit SHA, при необходимости message/root/thread IDs;
- observed/updated time и статус актуальности/полноты;
- связь с выбранным предметом и причина совпадения: ID, relation, field, exact phrase, lexical или semantic;
- read handle либо точная ссылка для последующего чтения;
- `next_cursor`, `has_more`, coverage/processing состояния только разрешённых источников.

«Confidence 0.93» без калибровки пользователю не помогает. Лучше явно различать точную связь и кандидата по похожести. Не показывать защищённые названия, snippets и counts до фильтрации доступа.

#### Симметрия Миры и dot

Мира, dot и другие разрешённые MCP-клиенты читают одни и те же предметные данные и используют одинаковые правила revision/commands. Голосовой ответ и MCP-ответ на один вопрос дают одинаковый результат при одинаковом субъекте доступа и моменте чтения. Разница — в способе взаимодействия, не в тайном дополнительном контексте или второй базе знаний.

При этом их полномочия могут различаться. Вызов от service actor не получает права человека только потому, что payload содержит его имя. Где агент действует от имени человека, связь с инициатором подтверждается доверенным auth-контекстом, а не фразой в промпте. Поиск сам по себе не расширяет существующий scope.

### 3.4. Поэтапное чтение полного источника

Для большого документа маршрут: metadata и оглавление с immutable commit/blob SHA → нужный section → необходимые соседние фрагменты и заголовки → продолжение cursor в той же pinned revision. Для треда сохраняются корень, авторы и сообщения, без которых «да, второй вариант» непонятно. Snippet выбирает кандидата, но не заменяет чтение основания.

Ответ сообщает source_revision, section/range, известный total_extent, next_cursor, has_more и complete либо причину неполноты. **Лимит одной порции — не лимит доступного источника.** При запросе полного чтения система последовательно достигает конца, проверяет покрытие без пропусков и не выдаёт краткую сводку за весь текст. Одновременно держать весь файл в Live-контексте не требуется.

Если источник меняется между страницами, продолжается закреплённый snapshot либо возвращается явный конфликт с новой версией; разные SHA не склеиваются. Каталоги тоже имеют продолжение: первая сотня элементов не доказывает отсутствия файла. Если внешний источник действительно не отдаёт остаток, сообщается конкретное ограничение. Контрольный пример — полный review25 и строка из конца его матрицы.

## 4. Запись, квитанция и немедленная видимость

### 4.1. Не смешивать сохранение ввода и изменение предмета

Если пользователь наговаривает мысль, сначала сохраняется capture с автором и происхождением. Маршрутизация/структурирование могут завершиться позже; не терять ввод, если непонятен проект. Если же говорит «измени дату этого выпуска», цель известна: прочитать текущую revision и применить предметную команду, сохранив источник изменения.

Автоматическая классификация не является общей авторизацией создавать задачи из любой реплики. Неясное «хорошо бы созвониться» остаётся записью/предложением, если нет команды или применимого правила процесса. Агент дополняет существующий предмет, когда identity однозначна; при конфликте идентичности уточняет, а не создаёт дубль.

### 4.2. Команда и квитанция

Команда содержит устойчивый `command_id`, target ID, expected revision, типизированные изменения и source ref; auth actor приходит из доверенного контекста. В одной допустимой транзакции сохраняются предметное изменение, event, receipt и intent дальнейшей доставки/индексации.

Повтор того же command ID/payload возвращает прежний результат; другой payload с тем же ID даёт конфликт. Конкурентная правка не перетирается. Receipt содержит новую revision и короткий after-state; Мира отвечает по нему, не запускает поиск, чтобы убедиться, что только что изменила.

### 4.3. Read-your-writes

Для своего последнего изменения действует правило: прямое чтение target ID и read-model должны видеть committed revision немедленно. Если индекс обновляется асинхронно, receipt передаёт `min_revision`/operation reference; следующий запрос по этому предмету идёт в канон, а не в устаревший индекс.

Нельзя говорить «не нашла» о только что сохранённой записи только потому, что FTS/vector ещё не обновился. Варианты реализации: синхронное обновление лёгкого FTS в той же транзакции, либо объединение выдачи с небольшим журналом свежих committed изменений. Выбор определяется реальным кодом; не нужен отдельный cache-контур, если простой direct read уже решает задачу.

Для внешнего канона, например документа GitHub, различать «запрос на изменение сохранён» и «документ изменён». Если операция асинхронна, локальный draft/operation не маскируется под подтверждённый новый SHA. Read-your-writes показывает честный pending draft и текущий канон до внешней квитанции/readback. Ошибка внешней записи не должна оставлять ложное «готово».

Slack-публикация и индексация не блокируют каноническую запись в projects-hub. Наоборот, сохранение намерения отправки не означает, что сообщение уже появилось в Slack. Доставка каждого окна имеет собственное состояние.

## 5. Индекс и Slack как источники для чтения

### 5.1. Что индексировать

- Названия, алиасы и разрешённые текстовые поля объектов/дел.
- Текст заметок и документов с commit/revision и привязкой к проекту/предмету.
- Доступный текст Slack-сообщений и наблюдённых текущих редакций, включая свои сообщения бота как записи, но не новые команды.
- Готовые расшифровки голоса, с оригиналом и состоянием обработки.
- Разрешённые извлечённые тексты файлов. Если извлечения нет, searchable только metadata, это видно пользователю.

Статусы, сроки, роли и числа — структурные поля для фильтра/сортировки, а не единственный длинный текст для embedding. Действующие права и наличие/удаление источника проверяются отдельно от полнотекстового индекса.

Не нужно заранее создавать пересказ каждого сообщения сильной моделью. Необязательно embedding-индексировать весь архив ради нескольких выпусков. Сначала индекс доступного содержимого с источниками; тяжёлые производные вычисления только при доказанной пользе.

### 5.2. Ключи и версии

У записи индекса есть `source_kind`, `source_id`, `source_revision`, `project/scope`, тип/subject links, время, текущая доступность и сведения об индексировании. Для chunk — стабильная связь с родителем и местом в источнике: section/page/span/message. Если появляется vector, дополнительно embedding model/version и версия chunking; замена модели не меняет IDs предметных данных.

Обновление идёт от устойчивых событий после commit. Индексатор идемпотентен, не применяет старую ревизию поверх новой и хранит watermark/ошибку обработки. Повторная сборка из канона возможна; отдельная authoritative копия текста без происхождения не создаётся.

### 5.3. ACL и удаление

Фильтры доступа применяются до раскрытия результатов и повторно при чтении. Для vector реализация должна фильтровать кандидатов допустимым scope либо искать по доступным partitions; простое «взять top-10 всей базы и потом удалить чужое» одновременно рискует утечкой metadata и теряет полезную выдачу. Как именно это обеспечить, зависит от выбранного хранилища и не требует нового сервиса само по себе.

Принятая общая аудитория подключённого проекта сохраняется; пользователя не заставляют вручную разбирать ACL каждого сообщения. Backend проверяет свои grants и корректно выполняет настроенную привязку. Неизвестный Slack-автор отображается с origin identity, но не получает права только по похожему имени.

Удалённый источник сразу перестаёт выдаваться через канонический gate, даже если фоновое физическое удаление index rows ещё идёт. Текст удаляется из FTS, snippets, доступных ревизий, caches и производных summaries в соответствии с контрактом. Vector не должен оставаться маршрутом восстановления удалённого текста. Самостоятельные решения/задачи сохраняются, но их provenance честно указывает на удалённый исходник.

При отзыве project access старый поисковый handle и cached answer не должны давать новый доступ к содержимому. Уже показанное пользователю невозможно «развидеть», но последующие чтения/доставки проверяют актуальные права.

### 5.4. Slack: поток, тред и происхождение

Предлагаемая цепочка: подписанное событие → durable inbound record → дедупликация → каноническое сообщение/revision/attachment → события индексирования → обновлённая поисковая выдача. У сообщения свой внутренний ID и внешняя идентичность workspace/channel/ts; thread root и reply links хранятся отдельно. `ts` не превращается во float.

Нужно сохранять:

- проект и канал-источник, автора с verified mapping либо origin identity;
- root/reply связь и ссылку на тред;
- текущую наблюдённую revision, edit/delete факт и времена source/observation;
- вложения, статус их скачивания/распознавания;
- связь с созданной задачей/решением/полем, если была явная материализация;
- coverage архива: с какого времени поток надёжен, какая предыстория загружена, где есть gaps.

Поиск по Slack на каждом вопросе Миры не нужен: используется сохранённый проектный архив. При недостающем диапазоне разрешённая сверка источника может восполнить доступное, но не должна незаметно превращать обычный голосовой ответ в долгий обход всех каналов.

Для «найди в треде» сначала точный thread ID. Для «почему решили так» — зафиксированное decision + доступные сообщения-основания. Для «что говорили» — исходные сообщения с правильной последовательностью, не только решения. Созданное из сообщения поручение не делает все его соседние реплики частью поручения.

Два последовательных голосовых — два устойчивых входа, каждый со своим processing state. Поздняя расшифровка первого не должна перезаписывать второе или применяться к уже сменившемуся предмету разговора. Происхождение предметного изменения связывается с конкретным capture, а не «последним голосовым».

## 6. Нужен ли vector

Для пилота vector не является обязательной предпосылкой. Сначала exact/relations/filters и лексический поиск по доступному корпусу. Русские словоформы, «ё/е», алиасы и опечатки требуют проверки на примерах; само название FTS не гарантирует качество.

Семантика полезна для запроса «где говорили, что место может сорваться?», когда исходник содержит «библиотека закрывается раньше», и для похожего прошлого случая. Она не определяет актуальный статус задачи, право доступа, identity человека или факт принятия решения. Высокий similarity score не заменяет доказательство.

Если baseline пропускает такие запросы, сравнить на одинаковой размеченной выборке: A — структура+lexical; B — то же плюс semantic candidates. Оценить каждый исправленный и новый промах, Recall@5 отдельно для перефразов, задержку, стоимость и эксплуатационную сложность. Не считать успехом одну удачную демонстрацию. Предлагавшийся прирост 10 процентных пунктов — лишь возможная инженерная гипотеза, не требование владельца и не условие, оправдывающее любую сложность. На малой выборке важнее конкретные ошибки и абсолютные counts.

При доказанной пользе добавить один перестраиваемый индекс в действующий backend: chunk→parent source/revision/span, модель embedding и версия chunking, scope/subject metadata, объединение lexical/semantic кандидатов и каноническое чтение. Не создавать вторую память или отдельного агента. Тексты нельзя автоматически отправлять новому внешнему embedding-провайдеру: использовать уже разрешённый контур либо отдельно согласовать необходимую передачу данных. Без него основной поиск продолжает работать.

## 7. Минимальная реализация и проверка

**R1. Полный точный доступ.** Сохранить действующий startup и capability-подход. Дать существующим доменным чтениям единые refs/revision, compact metadata и продолжение. Начать с пилотного выпуска: checklist, guest engagement, tasks/questions, связанные документы. Добавить тот же разрешённый доступ в MCP без дублирования канона.

**R2. Поиск и происхождение.** Единый backend query с точными фильтрами и лексическими кандидатами; source hydration, объяснение совпадения, coverage. Сохранённые Slack-сообщения подключаются по мере готовности архива; отсутствие диапазона явно видно. Write→receipt→direct read работает независимо от индекса.

**R3. Малый голосовой пилот.** Начать с 12–15 типовых запросов и негативных вариантов. Например:

1. «Что осталось для записи этого выпуска?» — checklist, blockers и доказательства.
2. «Кто делает обложку?» — актуальный assignee и acceptance, не имя из старой реплики.
3. «Что от меня требуется?» — личные адресованные ожидания.
4. «Что изменилось по гостям за три дня?» — события и связи, не весь архив.
5. «Открой досье Петрова» — правильная persona, при однофамильцах уточнение.
6. «Какой гонорар согласован?» — договорённость участия в выпуске, не глобальное поле гостя.
7. «Где обсуждали закрытие библиотеки?» — точный источник и окружение.
8. Та же мысль без исходных слов — оценка перефраза отдельно от lexical.
9. «Почему дата теперь другая?» — revision history и основание.
10. «Найди фото гостя с прошлой недели» — attachment/time/subject, честный статус содержимого.
11. «Сохрани доступность в пятницу», затем «замени субботой» — один target, две квитанции, read-your-writes.
12. Прочитать последний пункт матрицы review25, затем весь файл — страницы одной pinned версии до конца.
13. Найти файл в каталоге за пределами первых100 — продолжение, а не ложное отсутствие.
14. «Что мы делали похожего для прошлого выпуска?» — связанные дела, без автоматического копирования договорённостей.
15. Вопрос без подтверждения в доступных материалах — честный ответ, не выдуманный факт.

Негативные проверки: другой actor/отозванный доступ, stale handle, удаление source, изменение между страницами, одинаковые имена в разных проектах, два голосовых подряд, повтор command_id, конкурентная правка, отставший индекс, недоступный Slack/dot/GitHub. Snippets/counts/cache не раскрывают запрещённое; удалённый текст не восстанавливается через индекс; pending не называется выполненным. Технический прямой тест не заменяет голосовой путь.

Расширенные 70 запросов — последующая регрессионная приёмка при росте корпуса: точные12, структурные14, lexical12, перефразы12, связи6, mutation/recovery8, отсутствие/неоднозначность6. Не запускать эту программу как предварительный большой аудит. Разделить настроечные и контрольные семейства; не подгонять алиасы под каждый тест.

Публиковать правильные targets/evidence, numerator/denominator, промахи по классам, coverage, число обращений и размеры ответов. Измерять отдельно конец речи→расшифровка, выбор маршрута, backend retrieval, внешний fetch, первый содержательный подтверждённый голос и полный ответ. «Сейчас посмотрю» не результат. Cold/warm и внешние источники не смешивать. Численные SLO вроде p95 4–6 секунд или backend300–500мс — только обсуждаемые стартовые цели после baseline; это не обещания текущего продукта и не требования владельца. Средняя скорость не компенсирует неверный статус или источник.

**R4. Semantic только по выявленному дефициту.** Если пилот проходит, не задерживать полезную работу ради vector. Если систематические перефразы не проходят и гибрид их исправляет в допустимом контуре, внедрить минимальное дополнение и повторить те же проверки.

## 8. Точная постановка следующего раунда Claude

Claude, нужен адресный разбор этого документа и одна реализуемая постановка информационного доступа. Не повторяй общий аудит онтологии и не запускай модели исследования, кодовых агентов, новую серию прогонов, реализацию или deploy в аналитическом раунде. Проверь актуальный main и отдели изменившийся код от закреплённой базы этого документа.

Согласуй:

1. Какой канон отвечает на каждый тип вопроса: предметное состояние, событие, первичная запись или внешний документ; проверь на пилоте подкаста.
2. Какие существующие service methods и Live/MCP операции расширить, чтобы получить единый защищённый query/read с refs, revision, paging и coverage. Новые названия tools не являются целью.
3. Самый короткий маршрут для 12–15 примеров: ID/связи/фильтры/lexical; где действительно понадобится semantic fallback. Не добавляй второго router/агента.
4. Минимальные дополнения хранения и индекса: происхождение, текущая версия, links, read-your-writes, удаления и повторные события. Сохрани startup, working domains, независимость от dot и канон из онтологии24.
5. Границы symmetry: одинаковые данные/правила при одинаковом auth scope, но без выравнивания полномочий человека и integration service.
6. Тесты большого документа, длинного каталога, двух голосовых, повторов, stale/delete/revoke и недоступных внешних каналов. Отдели статические/контрактные проверки от реальной голосовой приёмки.
7. Решение о vector с минимальным сравнением по реальным ошибкам; не устраивай проект ради индекса и не объявляй процентные пороги уже согласованными.

Верни один компактный согласованный план: изменения по файлам/сервисам, порядок вертикальных срезов, критерии готовности и действительно оставшиеся вопросы. Расхождения поясни источниками. Не выдавай предложение за реализованное; не проси владельца выбирать каждую инженерную настройку. Новые права или передача данных остаются отдельными решениями, а внутренний выбор простого поиска — задачей инженера.

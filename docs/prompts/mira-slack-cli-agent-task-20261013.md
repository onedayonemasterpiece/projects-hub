# Запустить существующий тест Mira → Slack → dot через Slack CLI на DevCoveer

Дата постановки: 13 октября 2026 года.

## Результат

Доведи уже подготовленный транспортный стенд до проверенного запуска на DevCoveer: приложение создано или найдено и установлено через Slack CLI, Python-процесс работает независимо от открытого терминала, тестовый тред читается, команда владельца вызывает одно событие и проверяется реальный ответ dot. Если какой-либо участок не работает, установи точную границу и причину блокировки.

Это тест транспорта с синтетическими данными. Настоящую Mira, LLM, произвольные команды и бизнес-операции подключать не нужно. Fly.io не использовать.

## Продолжи существующую работу

Сначала найди подготовленный проект и проверь, не создано ли уже Slack-приложение. Не начинай заново и не создавай дубликаты.

В исходном комплекте есть `bot.py`, `manifest.json`, `requirements.txt`, `test_bot.py`, `README.md`, `WINDOWS.md` и `.gitignore`. При подготовке этой постановки комплект находился в `/workspace/shared/mira-slack-test`; этот путь не гарантирован на DevCoveer. Архив уже передан в Slack:

- канал: `C0C872SJFA7`;
- корень треда: `1791897535.208079`;
- файл: `F0C8X5XSKA5`.

Найди локальную копию или получи этот файл через доступный Slack-инструмент. Если доступа нет, попроси исходный архив. Не подменяй его новым шаблоном.

Уже написаны фильтрация владельца и треда, отправка через Python `slack-sdk`, Socket Mode, SQLite-дедупликация, чтение истории с пагинацией и учёт ACK. В исходной версии прошли 7 автономных unit-тестов; живой Slack roundtrip ещё не подтверждён. Прочитай код и инструкции, сохрани эти свойства. `WINDOWS.md` описывает прежний необязательный локальный путь, а не требование запускать бота на Windows.

## Slack CLI и доступ

Выбери минимальный рабочий путь по установленной версии CLI и актуальной документации. Проверь окружение DevCoveer, версию CLI, Python и существующую авторизацию. Если CLI отсутствует, используй официальный источник установки и действующие разрешения среды.

Сохрани существующий Python-бот. Для интеграции рассмотри CLI hooks: `get-manifest` должен отдавать существующий манифест, `start` запускать текущий слушатель, а `sdk-managed-connection-enabled: true` оставлять Socket Mode в Python. Это небольшой адаптер, а не повод переписывать логику на Bolt или Deno. Конкретный формат hooks и команды создания/установки проверь по версии CLI. См. [справочник hooks](https://docs.slack.dev/tools/slack-cli/reference/hooks/).

Авторизация CLI и установка приложения создают постоянный доступ. Перед соответствующим действием получи отдельное подтверждение владельца с указанием workspace, приложения и прав. Для новой авторизации используй штатный `slack login`: владелец подтверждает запрос в Slack, challenge code вводится в предназначенный терминал. Не создавай долгоживущий service token для CI ради этого теста. Уже действующую авторизацию не пересоздавай без необходимости. См. [авторизацию CLI](https://docs.slack.dev/tools/slack-cli/guides/authorizing-the-slack-cli/).

Сохрани минимальный манифест: bot scopes `chat:write` и `groups:history`, bot event `message.groups`, Socket Mode. Для подключения нужен app-level scope `connections:write`; проверь, выдаёт ли нужный токен сама процедура CLI. Не запрашивай user token или дополнительные scopes автоматически. Членство в приватном канале требуется отдельно: приложение и dot должны иметь доступ. Не добавляй приложение в другие каналы. Права Slack не ограничены одним тредом; ограничение тредом обеспечивает код.

CLI может передавать `SLACK_BOT_TOKEN` и `SLACK_APP_TOKEN` процессу после установки. Используй этот механизм, если он подходит, и проверь наличие переменных без вывода значений. Не проси присылать токены в чат, не включай их в команды с видимыми аргументами, отчёты, логи или Git. Если требуется ручной ввод секрета, передай этот шаг владельцу в безопасном интерфейсе. Хранение и настройку постоянных credentials согласуй отдельно. См. [переменные окружения CLI](https://docs.slack.dev/tools/slack-cli/guides/using-environment-variables-with-the-slack-cli/).

## Проверка и постоянный процесс

1. Запусти существующие тесты (`python -m unittest -v`) в подготовленном окружении. После правок повтори их и добавь узкие проверки адаптера, если это нужно. Зафиксируй фактически использованные версии зависимостей.
2. Выполни `python bot.py probe` именно с bot token установленного приложения для заданного приватного треда. В [текущей документации conversations.replies](https://docs.slack.dev/reference/methods/conversations.replies/) перечислен bot scope `groups:history`; не объявляй чтение принципиально невозможным по старой документации. Нужен фактический `read_ok: true` с полной пагинацией. При отказе сохрани только код ошибки; при rate limit соблюди `Retry-After`. Не расширяй доступ и не подменяй токен молча.
3. Настрой устойчивый запуск на DevCoveer доступным штатным способом, например существующим supervisor или systemd. Slack CLI сам по себе не предоставляет хостинг Python. Обеспечь один экземпляр слушателя, перезапуск после сбоя, постоянный абсолютный `MIRA_STATE_PATH`, безопасное окружение и журналы без содержимого чужих сообщений. Не ослабляй системную защиту ради запуска. Проверь, что процесс остаётся активным после закрытия установочной сессии и корректно перезапускается с той же SQLite-базой.
4. После готовности слушателя попроси владельца отправить `mira-test smoke-001` в указанный тред. Не отправляй команду за него и не имитируй dot. Проверь цепочку: команда владельца → ровно одно `MIRA_EVENT` с правильным `source_ts` → самостоятельный `MIRA_ACK smoke-001` от `U0C8A9GM76D` → статус `acknowledged` в `python bot.py status --event-id smoke-001`.
5. Повтор команды должен дать `duplicate` без новой отправки или действия, включая повтор после перезапуска с той же базой. Если `smoke-001` уже использован до начала работы, не очищай историю ради красивого теста: проверь прежний результат и согласуй отдельный ID для нового roundtrip.
6. Подтверди отсутствие bot loops и сохранность фильтров: чужой пользователь, другой тред/канал, bot-origin команда, изменение сообщения и произвольный текст не вызывают действие. Проверки вне разрешённого треда делай unit-тестами, не публикациями в чужие каналы.

Отправка Slack API ещё не подтверждает доставку события в dot. Если `MIRA_EVENT` принят, но самостоятельного ACK нет, результат: **Slack accepted; dot delivery unverified**. Зафиксируй наблюдаемую границу и нужный следующий шаг; не объявляй схему рабочей и не засчитывай ручной ответ или копирование текста человеком. Не меняй настройки dot и не подключай обходной транспорт без согласования.

Сохрани исходную at-most-once семантику: ID записывается до отправки; `claimed` или `unconfirmed` после сбоя требуют проверки Slack, а не слепого повтора. Перезапуск процесса не означает восстановление событий, пропущенных во время остановки.

## Центральная коррекция владельца

**Человек сразу говорит. Обязательного ручного выбора проекта, дела, карточки или dropdown перед голосом нет.** Мира сама устанавливает предмет через разрешённые списки, имена, алиасы и связи. Уточняет только неоднозначность, влияющую на запись. Текущий контекст помогает, но его отсутствие не блокирует начало разговора.

Это следует из PH-US-06: ввод без выбора проекта; PH-US-07: идея без проекта; PH-US-08: структурирование сразу; PH-US-27: дополнение существующего; PH-US-49: итоги звонка спикеру; PH-US-53: смешанный звонок по проектам; PH-US-74: разнесение постфактум. PH-US-18 даёт ссылку после разговора, а не обязательный предварительный шаг. POD-US-02 требует hands-free без экрана, POD-US-03 — изменение существующей задачи с уточнением только при неоднозначности.

Новая идея не обязана иметь дело. Для PH-US-07 допускается проект по умолчанию, но личная видимость PH-US-04 сохраняется: default project не означает общую публикацию. Не превращай всё в notes, которые потом вручную сортирует dot.

## Какой минимальный срез предложить

Проверь вертикаль: **голос → устойчивый capture → разрешённые кандидаты предмета → решение самой Миры → типизированная правка существующего либо новая идея → квитанция → немедленное исправление голосом**. Этот путь работает без dot. Исходный ввод сохраняется до разрешения неоднозначности; неизвестный target не оправдывает потерю записи.

Различи три результата: личный capture, общая предметная запись и поручение/внешнее действие. Разрешение общей записи должно следовать из команды и применимого контекста полномочий, а не из факта распознавания. Новость «спикер может в пятницу» обновляет доступность соответствующего участия; она не создаёт автоматически согласованную встречу, приглашения или обязательство. Новый спикер как предметная персона не равен новому actor account.

Resolver здесь — логическая функция, не обязательная новая модель, служба или архитектурный слой. Начни с существующих list/get и минимального дополнения: ID, тип, имя, aliases, проект, связи на выпуск/участие, revision. Мира получает компактных кандидатов и читает выбранный объект. Явная ссылка сильнее похожести, два подходящих выпуска требуют одного уточнения. Несколько проектов в одной реплике дают раздельные записи с собственными target/source refs и проверенными областями видимости.

Уже проверены project focus/list, participants с actor_id, notes list/get/reply, вопросные ответы и приглашение без GitHub. Но participants — не каталог гостей; общая задача волонтёра не появляется из свободного assignee_role; вопрос без анализа не обеспечен самим существованием analytic questions. Проверь эти границы заново и назови минимальные изменения, не обещая готовность.

## Что можно отложить, что сохранить

Общий поиск по архиву, включая SQLite FTS и vector, не обязан предшествовать полезной записи. Lookup предметов по именам/алиасам/связям не равен полнотекстовому поиску обсуждений. Если PH-US-14 откладывается, явно оставь его незакрытым to-be; доступ к текущему делу не закрывает поиск по полному архиву.

Сохрани PH-US-25: вопросы, ответы и продолжение с квитанциями. PH-US-23 regionalKB остаётся отдельной подключаемой capability; её function-call паттерн полезен, но сама база не маршрутизирует проектные записи. PH-US-65 требует общих данных для разрешённого MCP: не второй канон и не имитация голосовой сессии. Опиши минимальный вход волонтёра по POD-US-01/08 с реальным actor, доступом, принятием поручения и повторным входом; выдачу доступа сейчас не выполнять.

## Шесть голосовых проб будущей приёмки

1. С нулевого контекста наговорить новую идею без проекта: сохранение приватно, без экрана и обязательного дела.
2. Назвать известного спикера и новую доступность: найти существующее участие, изменить нужные поля, вернуть квитанцию без создания встречи.
3. Два одноимённых человека или два выпуска: одно предметное уточнение, никакого случайного объединения или дубля.
4. В одной реплике новости двух проектов и личная мысль: раздельные targets, личное не попадает команде, источник не теряется.
5. Сразу исправить пятницу на субботу, затем повторить команду после обрыва: тот же объект, актуальная revision, без дубля и перезаписи чужого изменения.
6. Волонтёр входит, голосом принимает адресованное поручение/отвечает на вопрос, сообщает результат; владелец читает ту же сохранённую версию. Отзыв доступа закрывает последующие операции.

## Результат раунда

Верни короткую постановку минимальной вертикали: что уже есть; какие service methods, поля и tools дополнить; как выбирается target с нулевого контекста; как сохраняются область, источник, revision и повторяемость. Для каждого включённого и отложенного поведения укажи PH/POD ID. Различай кодовую проверку, тест и реальную голосовую приёмку. Не меняй сами истории, не запускай реализацию, исследовательские модели или новый полный аудит. Главный критерий: человек говорит естественно, Мира сохраняет в правильное место и позволяет сразу исправить результат, не отправляя человека или dot сортировать записи вручную.

# Создание проекта с репозиторием через MCP Projects Hub

Постановка для реализации POD-SETUP-01. 13 октября 2026 года.

## Результат и границы

Добавить предметный MCP-флоу: dot создаёт обычный проект Projects Hub с названием и целью, привязывает выбранный GitHub-репозиторий либо создаёт явно разрешённый новый, обеспечивает одну доску и сохраняет ссылку на каноническую документацию. Владелец получает проверяемые ID, ссылки и состояние каждого шага. Само проектирование не разрешает создание проекта, репозитория, приглашений или доступов в runtime.

Это отдельная capability подготовки проекта. Не расширять [постановку MCP вопросов внешнего анализа](https://github.com/onedayonemasterpiece/projects-hub/blob/main/docs/prompts/projects-hub-analysis-questions-mcp-20261013.md). Допустим общий transport/auth слой, если он уже реализован к началу работы. Не добавлять Episode, программу как новую сущность, новый workflow framework, Kimi/DeepSeek-вызовы или генерацию проекта моделью внутри Hub.

## Что подтверждено в коде

Проверен `main` Projects Hub на SHA `781929a03a47af9e7ee6fdd0090662c8823dfc7b`; SHA просмотренных файлов совпали с деревом этого коммита. Развёртывание и live-сценарий этим не подтверждены.

- [DurableStore](https://github.com/onedayonemasterpiece/projects-hub/blob/781929a03a47af9e7ee6fdd0090662c8823dfc7b/src/projects_hub/store.py) содержит projects, memberships и project_grants. Проекты создаются при начальном создании workspace/владельца, обычного доменного `create_project` и соответствующего API в проверенном срезе нет. В projects нет поля цели; уникальность задаётся `(workspace_id, name)`. `project_access` проверяет membership, активный grant, роль и состояние проекта.
- [BoardService.open_board](https://github.com/onedayonemasterpiece/projects-hub/blob/781929a03a47af9e7ee6fdd0090662c8823dfc7b/src/projects_hub/board.py) создаёт или возвращает доску проекта, учитывает ACL; boards имеет уникальный project_id. Это готовая основа, не нужен второй тип доски.
- [GitHubConnections](https://github.com/onedayonemasterpiece/projects-hub/blob/781929a03a47af9e7ee6fdd0090662c8823dfc7b/src/projects_hub/github_connections.py) и [GitHubAppClient](https://github.com/onedayonemasterpiece/projects-hub/blob/781929a03a47af9e7ee6fdd0090662c8823dfc7b/src/projects_hub/github_app.py) уже проверяют installation, читают каталог и содержимое, привязывают repository connection, выполняют ограниченные записи. Создания GitHub repo здесь нет. Текущий manifest просит metadata read и contents write; это не доказательство разрешения создавать репозитории.
- `bind_repository_connection` требует workspace owner, но может заменить существующую привязку; в таблице одна connection на `(workspace_id, repository_id)`. Новый флоу обязан обнаруживать занятую привязку и возвращать конфликт, не перепривязывать чужой проект.
- `GitHubConnections.status()` вызывает `_auto_bind_exact_matches`: совпадение имени может привязать repo с `app_managed_write` и пустым allowed_paths. `refresh()` в конце вызывает status. Эти методы нельзя использовать как read-only preflight нового MCP. Нужен чистый путь проверки; автоматическое связывание по имени в новом флоу запрещено.
- `list_repository_connections` сейчас проверяет membership, а не project ACL для каждой строки. MCP не должен раскрывать этот каталог обычному участнику без фильтрации. [CollaborationService.invite_participant](https://github.com/onedayonemasterpiece/projects-hub/blob/781929a03a47af9e7ee6fdd0090662c8823dfc7b/src/projects_hub/collaboration.py) уже создаёт actor, member, project grant и login invite; создание проекта не должно вызывать его.
- В дереве и [app.py](https://github.com/onedayonemasterpiece/projects-hub/blob/781929a03a47af9e7ee6fdd0090662c8823dfc7b/src/projects_hub/app.py) предметный MCP-вход PH не найден; скрипт DevCoveer MCP им не является. Перед реализацией перепроверить актуальный код.

## Минимальный контракт

Имена ниже предлагаемые. Достаточно двух основных операций над одним общим доменным сервисом, без копирования бизнес-логики в MCP.

1. `project_create`: выполнить или продолжить ту же durable-команду с `command_id`. Возвращает результат сразу либо точный незавершённый шаг. Повтор продолжает только разрешённую работу.
2. `project_creation_get`: прочитать сохранённое состояние по command/operation ID, включая после потери ответа или рестарта. Проверяет текущие права до выдачи любых прежних результатов.

Необязательный `dry_run` у `project_create` либо существующий read-only путь проверяет вход, права, выбранный repo и доступный способ его создания. Возвращает нормализованный план и недостающие данные/разрешения, ничего не создавая. Это удобство предварительной проверки, не обязательный пользовательский шаг и не третья самостоятельная capability. При обычном вызове create те же проверки выполняются внутри операции. Одно явное поручение покрывает обычные промежуточные шаги в согласованном объёме; повторных подтверждений проекта, доски и привязки не требовать. Отдельное разрешение нужно при новом объёме действий или изменении доступа, а не на каждую техническую стадию.

Вход: `workspace_id`, `name`, `purpose`, `command_id`; repository — взаимоисключающий вариант:

- `link`: точная GitHub-ссылка либо numeric repository ID; сервер разрешает ссылку в проверенные installation + repository ID. Одного совпадения имени недостаточно.
- `create`: точные `owner`, `name`, `visibility` и проверяемое сервером разрешение пользователя на этот план. Не подставлять публичность или владельца по догадке. Само поле `approved: true` от модели разрешением не является.

Owner проекта выводится из аутентифицированного trusted principal и его отображения на actor Hub; `owner_id`, `actor_id` и имя из tool arguments не дают прав. Для первого среза создание разрешено workspace owner, в соответствии с текущей политикой repository binding. Repository owner — отдельное явно выбранное GitHub account/organization.

У проекта должен быть канонический docs root: repository ID, нормализованный путь и стратегия ref/default branch. PH хранит эту привязку; GitHub остаётся источником текста документов. Для нового проекта можно использовать согласованное стандартное место, например `docs/`, без дополнительного вопроса. Пустой repo или ещё не созданный каталог допустимы: возвращать `documentation_state: empty`, отсутствие текущего commit/ref — явно, не выдавать несуществующий URL за проверенный документ. Это успешное создание проекта с пустой документацией. Существующий первый документ можно связать дополнительно с его проверенной версией; он не обязателен для setup. Не копировать программу из idea-hub и не создавать первый документ автоматически без поручения на такую запись. Готовность материалов для менеджера проверяется отдельно.

Результат: operation/command ID, project ID и имя/цель, owner actor ID, board ID, repository ID/full_name/URL/visibility, connection role/access_mode/allowed_paths, canonical docs root и состояние документации, версия первого документа при его наличии, доступные в текущем клиенте ссылки, состояния шагов, блокер и следующий допустимый шаг. Общий успех setup возвращать после readback project, board, repo binding и сохранённого canonical docs root; первый физический документ не требуется. Ссылки на реальные объекты и логический путь для будущих документов различать.

## Выполнение и восстановление

1. Проверить principal, workspace owner, вход и полномочия GitHub; нормализовать payload и сохранить durable operation до внешнего изменения. Не создавать пустые сущности при заранее известном недостатке прав.
2. В `link` проверить доступную installation, exact numeric repo ID и отсутствие несовместимой привязки. В `create` повторно проверить утверждённые owner/name/visibility и capability создания, выполнить один узкий GitHub create и сохранить возвращённый ID. Проверить доступ PH к созданному repo отдельно.
3. В локальной транзакции создать обычный project и owner grant; обеспечить одну board, сохранить цель и связь с operation. Привязку repo сделать через существующий сервис с защитой от конкурентного rebinding. Не держать SQLite-транзакцию во время сетевого GitHub запроса. Разделённые шаги должны безопасно продолжаться после сбоя.
4. Сохранить и проверить canonical docs root, затем перечитать результат. Проверка root подтверждает repository binding, допустимость пути и политику доступа; существование файла или каталога не требуется. Project ID остаётся стабильным при незавершённом setup или недоступном repo. Пустая документация не является частичным сбоем. Не менять существующую семантику `projects.status` ради setup: прогресс хранить в небольшой durable записи операции.

Область идемпотентности: trusted actor + workspace + command ID. Тот же ID и нормализованный payload возвращают ту же операцию; другое содержимое — `COMMAND_CONFLICT`. Зафиксировать hash, шаги, ID, revision, безопасные ошибки и provenance разрешения. Предусмотреть блокировку/уникальность для конкурентных повторов; изменение плана требует новой команды/ревизии с явной связью с прежней операцией.

При timeout создания repo результат неизвестен. Сначала сверить точный owner/name и доступные доказательства исходной операции; существование repo с этим именем само по себе не доказывает, что его создала эта команда. Не повторять создание с новым именем и не присваивать случайно найденный repo. При неоднозначности вернуть `reconciliation_required` и запросить явное решение. После подтверждённого создания repo и сбоя локального шага продолжение использует сохранённый ID. Ничего автоматически не удалять в качестве rollback.

Состояния должны различать: ещё не начато, подтверждённый успех шага, временная ошибка, неизвестный внешний результат, требуется разрешение/действие владельца, завершено. Возвращать уже созданные объекты и незавершённый шаг, а не общий ошибочный ответ, скрывающий частичный успех.

## Доступ и способ создания GitHub repo

Сохранить существующую [политику GitHub connections](https://github.com/onedayonemasterpiece/projects-hub/blob/781929a03a47af9e7ee6fdd0090662c8823dfc7b/docs/product/14-github-connections.md): server-side credentials, проверенные installation/repository IDs, минимальные permissions, без PAT в чате и без обязательного GitHub account менеджера.

Создание репозитория требует отдельной capability GitHub. [REST GitHub](https://docs.github.com/en/rest/repos/repos#create-a-repository-for-the-authenticated-user) описывает специальные разрешения создания; текущие contents write их не заменяют. Поддерживаемый путь проверить для типа выбранного owner и реального connection. В первой реализации добавить узкий provider method в существующий GitHub-клиент, если нужный авторизованный доступ уже есть. Иначе вернуть явный blocked/needs-owner-action: разрешённое создание владельцем с последующим `link` или отдельно подтверждённое подключение необходимого доступа. Не объявлять автоматический create готовым, если работает только ручной обход.

Не выдавать новые credentials, не расширять installation/repository access, не менять visibility/ACL и не добавлять collaborators как побочный эффект setup. Наличие нового repo не означает, что selected-repositories installation уже имеет доступ. Все такие изменения требуют отдельного разрешённого действия и повторной проверки.

Для новой привязки default read_only; роль и ограничение путей определяются явным назначением. Для существующей сохранять mode/allowed_paths, не расширять их. `external_owning_repo` остаётся read_only. Любая будущая запись канонического документа проверяет project ACL, current connection и expected revision; prompt или MCP payload не могут включить write.

На каждом dry-run/create/resume/get повторно проверять права. Отзыв доступа прекращает продолжение и выдачу приватных metadata, даже если раньше operation была успешной. Не восстанавливать отозванные grants при replay. Проверить существующую startup-миграцию owner grants: она не должна неожиданно наделять новых участников доступом или отменять отзыв.

## Приёмка

Расширить существующие store/board/GitHub/collaboration тесты и добавить небольшой набор MCP-contract тестов:

- Link точного существующего repo: один project, owner grant, board, binding и сохранённая цель; чтение через MCP и обычный Hub согласуется.
- Create с разрешёнными owner/name/visibility: один repo; без разрешения или необходимых capability внешних изменений нет. Смена visibility/owner/имени требует нового согласования.
- Повтор, параллельный повтор, рестарт и потеря ответа на каждом шаге не дублируют repo/project/board. Другой payload с тем же ID конфликтует. Занятые имя проекта/привязка не приводят к тихому объединению или переносу.
- Repo создан, PH запись не завершена; project сохранён, board/binding/docs root ещё не сохранены; неизвестный GitHub outcome. Проверить продолжение с прежними ID и точное описание частичного результата.
- Чужой workspace, поддельный actor, отозванный grant, suspended installation, repo вне selected scope и закрытый docs path: fail-closed без утечки. Read-only dry-run не auto-bind; неизменность остальных project grants и repository policies подтверждена readback.
- Сохранённый canonical docs root позволяет успешно завершить setup пустого repo без первого документа. Если документ указан, его ссылка/версия проверяются; отсутствие документа отображается как пустая документация и не блокирует создание. Никаких Kimi/DeepSeek jobs, приглашений менеджера и автоматических write-permission upgrades.

Live-приёмка выполняется только после отдельного разрешения на конкретные изменения: реальный MCP-клиент → создание/link → readback → перезапуск → повтор без дублей; необязательный dry-run проверить отдельно. Приложить deployed SHA, безопасные IDs/revisions и проверенные ссылки. Mock-тесты не считать live-приёмкой.

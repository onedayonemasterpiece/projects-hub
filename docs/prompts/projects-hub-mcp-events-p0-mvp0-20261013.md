# Projects Hub MCP Events P0 и MVP0

Дата: 13 октября 2026 года. Адресат: разработчик Projects Hub на DevCoveer.

## Результат который нужно получить

Сделать Projects Hub подключаемым плагином ChatGPT. Backend публикует событие через MCP Events, dot с активной подпиской получает его без нового сообщения пользователя, читает контекст проекта и возвращает коррелированный ответ. Затем добавить постоянную связь обсуждения Projects Hub с конкретным Slack-тредом и получателем Mira/backend, чтобы ответ мог дойти в оба места.

Сначала закончить минимальный вертикальный P0. Не превращать проверку доставки в отдельную платформу, сложный тестовый стенд или последовательность искусственных событий. Использовать существующий FastAPI backend, его хранилище и развёртывание на DevCoveer. Fly.io и новый независимый сервис не нужны.

Техническая осуществимость подтверждена документацией MCP Events; работоспособность именно этого подключения должна быть доказана живым тестом. Этот документ ставит задачу и критерии приёмки, а не сообщает о готовой интеграции.

## Исходное состояние которое нужно перепроверить

По инспекции снимка main `e82a0b1`:

- В зависимостях есть `mcp>=2`, но это не доказывает регистрацию MCP endpoint или поддержку нужного протокола установленным SDK.
- В `app.py` middleware около строк 370–386 защищает изменяющие запросы через browser Origin; `actor_id_from_request` около строк 419–427 получает пользователя из подписанной cookie. Машинный MCP-клиент нельзя подключить простым обходом этой защиты.
- `DurableStore` в `store.py` около строк 37–52 использует SQLite WAL/FULL. Это исходная точка для постоянного хранения, а не повод вводить вторую БД.
- В `collaboration.py` около строк 140–154 есть `collaboration_events`, а около строк 981–1023 — ACL-фильтрованная timeline с cursor. Переиспользовать подходящие доменные сущности и проверки доступа.
- В просмотренном main не найдены готовая MCP-маршрутизация, постоянная Slack-привязка и outbox нового канала. Возможна работа в неслитой ветке.

Существующие постановки `docs/prompts/projects-hub-analysis-questions-mcp-20261013.md` и `docs/prompts/projects-hub-project-creation-mcp-20261013.md` описывают требования, но сами по себе не доказывают реализацию MCP. Не использовать `create_note` и `answer_questions` для безобидной smoke-проверки: они могут запускать Gemini и analysis jobs. Тестовый запрос должен оставаться отдельной малой операцией.

Предыдущий Slack smoke пользователь подтвердил как завершённый; сервер зафиксировал ACK за 38,307 секунды. Это доказательство старого Slack-маршрута, которое нельзя переносить на новый MCP-канал.

Перед кодом сверить реальный worktree, ветки, HEAD и развёрнутый commit. Сначала изучить существующую реализацию и незавершённые изменения, затем дополнять их. Отсутствие в снимке main не означает отсутствие на сервере или в другой ветке.

## Протокольная опора

[Официальная документация MCP Events](https://developers.openai.com/plugins/build/mcp-events) проверена 13 октября 2026 года. В ней заявлены поддержка dots, MCP 2.0 с версией `2026-07-28`, discovery через `server/discover` и методы `events/list`, `events/subscribe`, `events/unsubscribe` на аутентифицированном endpoint инструментов. ChatGPT передаёт callback и signing secret; сервер проверяет callback и доставляет подписанные HTTPS-события. Повторы сохраняют `eventId`; HTTP 2xx подтверждает приём, а не завершение работы. Обработка асинхронная, возможны группировка и иной порядок. Polling, streaming, `gap` и `terminated` этой интеграцией не поддерживаются.

Точные JSON-RPC-схемы, challenge, подписи, заголовки, сроки подписок, ограничения размера и правила повторов брать из актуальной страницы и указанной в ней спецификации. Не изобретать совместимый «по смыслу» wire format или собственный HMAC-вариант. Проверить установленный SDK реальным discovery/subscription обменом; при необходимости сделать минимальный совместимый адаптер в существующем backend. Вести отдельные тесты протокольного контракта. Имена доменных инструментов и полей ниже являются проектным предложением, а не частью стандарта MCP.

## P0 один полный проход события

### Объём

1. Аутентифицированный, доступный ChatGPT MCP endpoint Projects Hub и минимальная конфигурация плагина для подключения владельцем.
2. Один тип события `projects_hub.test_requested` с обязательным фильтром `project_id`.
3. Чтение сохранённого запроса через `get_test_request` и идемпотентная запись ответа через `record_test_response`.
4. Один живой тест: backend создаёт запрос, доставка MCP Events будит ожидающий dot, dot возвращает правильный nonce, результат сохраняется в Projects Hub.

Постоянная маршрутизация всех проектных обсуждений не блокирует этот первый проход. При необходимости показать ответ человеку использовать только заранее согласованный тестовый Slack-тред:

- workspace: `T0C82495TK5`
- channel: `C0C872SJFA7`
- thread root: `1791904761.279249`

Эти идентификаторы — ограниченный адрес приёмочного теста. Они не являются глобальным маршрутом, разрешением писать в любые треды или готовой моделью связей MVP0.

### Минимальные доменные данные

Запрос хранит `request_id`, `project_id`, случайный уникальный `nonce`, время создания, срок действия и состояние. Добавить владельца/tenant и необходимые ACL-связи согласно существующей модели. Не помещать nonce в предварительное сообщение dot: ответ должен подтвердить получение нового запроса через интеграцию. Nonce — контрольная метка теста, не credential.

Событие несёт идентификаторы запроса и проекта и короткое описание факта. Полный запрос доступен через инструмент чтения. Не передавать в событии команды выполнить код, изменить разрешения или отправить данные произвольному адресату.

`get_test_request(request_id)` проверяет аутентифицированного субъекта и доступ к проекту, возвращает сохранённый nonce, актуальное состояние и минимальный контекст. Если запрос недоступен или истёк, инструмент сообщает это без раскрытия чужих данных.

`record_test_response(request_id, nonce, response)` проверяет доступ и соответствие nonce сохранённому запросу. Повтор того же ответа возвращает уже сохранённый результат; конфликтующий повтор не перезаписывает его молча. Запись результата и перевод запроса в завершённое состояние атомарны. Идентификатор автора берётся из аутентификации, а не из доверенного на слово поля запроса.

Точную сигнатуру разработчик может адаптировать к существующим инструментам без потери этих гарантий.

### Доставка и хранение

Подписка, проверенный callback, фильтры, срок жизни и состояние должны переживать рестарт. Signing secrets хранить закрыто, не выводить в GitHub, логи, события и отчёты. Защиту callback от SSRF и проверку TLS реализовать по официальному контракту; не снимать проверки ради теста.

Создание доменного запроса и намерения доставить событие должно быть согласованным: минимальная транзакционная outbox-запись в существующем хранилище подходит. Отдельный брокер не требуется. В записи доставки различать «ждёт», «принято callback», «ошибка», а в запросе — «ответ ещё не получен» и «ответ сохранён».

Повтор доставки сохраняет идентичность события. Операции записи дедуплицируются независимо от транспортной дедупликации. Backend применяет фильтр проекта и проверяет права получателя до доставки; доступ к чтению и записи проверяется также при каждом вызове инструмента. Отключение подписки или утрата доступа прекращают доставку.

### Настройка без обхода защиты

Выделить явную границу аутентификации MCP-интеграции и существующего браузерного UI. Сохранить текущую Origin/CSRF-защиту браузерных изменений. Не делать общий anonymous bypass, не подставлять браузерную cookie в интеграцию и не доверять `actor_id`, переданному клиентом.

Определить поддерживаемый механизм подключения по текущим требованиям ChatGPT и существующей auth-модели проекта. Владелец подключает плагин и утверждает подписку. Если требуется создание credential, OAuth grant или иное расширение постоянного доступа, остановиться на соответствующем подтверждении владельца. Не помещать секреты в setup-инструкцию.

В плагине дать понятные описания события, фильтра и инструментов. Инструкция подписки должна задавать ограниченную реакцию на тест: прочитать запрос доступного проекта и записать nonce-ответ. Полученный payload не расширяет полномочия dot.

### Живая приёмка P0

1. Зафиксировать commit развёрнутого backend, URL endpoint и установленную версию SDK. Проверить discovery, tools и event catalog из реального подключения.
2. Владелец подключает Projects Hub и разрешает подписку на тестовый проект. Проверить успешную callback verification и сохранение подписки.
3. Завершить настройку и оставить dot без активного запроса пользователя. Убедиться, что нет параллельного опроса, таймера или Slack-webhook, подменяющих этот тест.
4. Backend-агент создаёт один тестовый запрос и отправляет соответствующее MCP-событие. Зафиксировать `request_id`, `eventId`, время отправки и результат приёма callback без секретов.
5. Без нового сообщения пользователя dot получает событие, читает запрос и вызывает `record_test_response` с правильным nonce.
6. Прочитать результат из постоянного хранилища. Сопоставить запрос, событие, получение и запись ответа. Отдельно, если это было согласовано, проверить сообщение в тестовом Slack-треде.

**PASS P0:** новый запрос без пользовательского подталкивания привёл через MCP Events к пробуждению dot и сохранённому правильному nonce-ответу. Совпадают проект и корреляционные идентификаторы.

**Не PASS:** только локальные unit-тесты; только 2xx callback; только запись сообщения backend-ботом в Slack; ответ после нового пользовательского сообщения; заранее известный nonce; старая успешная Slack webhook/ACK проверка.

Если событие принято, но подтверждённого ответа нет, статус — «приём callback подтверждён, пробуждение/обработка не доказаны». Зафиксировать согласованное окно наблюдения теста и фактические времена, не обещать недокументированную задержку. Если мешают доступность функции, настройки workspace, auth или соединение, назвать конкретный блокер и последний успешный шаг; не заменять MCP Events другим транспортом и не объявлять PASS.

## MVP0 проектные обсуждения и два адресата

После PASS P0 распространить тот же простой маршрут на реальные обсуждения. Сохранить постоянную связь между проектом, обсуждением Projects Hub, конкретным Slack-тредом и существующим адресатом Mira/backend. Одно обсуждение должно однозначно разрешаться в свои разрешённые назначения после рестарта.

### Модель связи

Для связи хранить как минимум:

- идентификатор связи, `project_id` и `discussion_id`;
- Slack workspace, channel и root thread timestamp;
- проверенный идентификатор обсуждения/запроса на стороне Mira/backend;
- владельца, границы разрешённой передачи информации и статус связи;
- время, автора и версию создания/изменения связи.

Привязку создаёт или подтверждает владелец через авторизованное действие. На сервере проверяются доступ к проекту, допустимость назначения и уникальность выбранного маршрута. Payload события не может самостоятельно сменить получателя. Изменения и отзыв маршрута журналируются. Реальные поля и ограничения согласовать с существующей моделью, не вводить параллельные сущности без необходимости.

### Ответы

Dot получает событие обсуждения, читает актуальный контекст через Projects Hub и выбирает ответ по задаче владельца. В Slack отвечает через существующий Slack connector от собственной разрешённой identity. В Mira/backend сохраняет коррелированный ответ через инструмент Projects Hub, используя существующий канал доставки Mira, если он есть.

Запись ответа в backend и фактическое получение Mira — разные состояния. Если Mira пока может только читать запись, так и обозначить результат; не выдавать сохранение за доставку активному агенту. Новую интеграцию Mira проектировать только если существующей действительно недостаточно.

Хранить общий `response_id`, связь с исходным событием/запросом и отдельные статусы назначения:

- backend: результат записан либо ошибка;
- Mira: доступен для чтения, доставлен/подтверждён либо ошибка согласно реальному механизму;
- Slack: сообщение подтверждено с возвращённым ID либо ошибка/неопределённый результат.

Успех одного назначения не скрывает сбой другого. Повторять только незавершённый шаг. После неопределённого результата Slack send сначала сверить наличие сообщения доступными средствами; слепой повтор создаёт дубль. Не обещать транзакцию или exactly-once между двумя независимыми системами.

Для защиты от циклов связать собственный ответ с исходным запросом и автором. Событие о записи собственного ответа не должно запускать бесконечные ответы на ответы. Поздние и повторные события сверять с актуальным состоянием обсуждения.

### Приёмка MVP0

- Два тестовых обсуждения одного проекта приводят ответы в разные сохранённые Slack-треды и правильные backend-контексты.
- После рестарта связи, подписки и незавершённые доставки сохраняются.
- Повтор события и повтор write-tool не создают новые доменные ответы; Slack-повтор не выполняется при уже подтверждённом результате.
- Ошибка Slack не теряет backend-ответ, ошибка backend не маркируется как полный успех.
- Отзыв доступа/связи исключает новые доставки и запись в недоступное обсуждение.
- Подмена `project_id`, `discussion_id` или назначения не раскрывает чужой контекст.

## Порядок реализации и проверок

1. Короткая инспекция фактического кода и незавершённых веток; список повторно используемых компонентов.
2. Минимальная MCP/auth-граница, событие, два доменных инструмента, постоянная подписка и доставка.
3. Контрактные тесты discovery/subscription, проверки доступа и подписи; тест идемпотентной записи; тест сохранности после рестарта. Не строить дополнительный orchestration framework ради этих проверок.
4. Развёрнутый P0, подключение владельца и реальный idle-dot тест.
5. После доказанного P0 — постоянные discussion bindings и независимый учёт ответов MVP0.

## Что передать на выходе

- Изменения в существующем репозитории и точный commit развёртывания.
- Подключаемый MCP endpoint и конфигурацию/пакет Projects Hub без секретов.
- Короткую инструкцию владельцу: как подключить плагин, выбрать проект и подтвердить подписку.
- Команду или существующий административный способ создать один тестовый запрос; не публичный незащищённый endpoint.
- Проверяемый отчёт P0: корреляционные ID, времена, сохранённый ответ и PASS либо конкретный блокер. Отдельно статус MVP0, если он выполнен.
- Инструкцию отключения подписки/интеграции с сохранением исходной защиты и пользовательских данных.

Не ограничиваться архитектурной запиской или локальным mock. Цель задачи — работающий подключаемый сервис и подтверждённый проход события. При нехватке доступа довести всё разрешённое до проверенного состояния и явно обозначить единственный следующий необходимый шаг владельца.

# Projects Hub постоянный контракт MCP Events

Дата: 13 октября 2026 года. Дополнение к [постановке P0 и MVP0](projects-hub-mcp-events-p0-mvp0-20261013.md). Адресат: разработчик Projects Hub на DevCoveer.

## Решение

Уже для первого живого теста реализовать постоянный контракт `projects_hub.request.created` с единственным обязательным фильтром `project_id`. Тестовый и рабочий запросы должны проходить через одинаковые событие, хранилище, инструменты чтения и записи результата. Различие определяется сохранённым режимом запроса и серверными разрешениями. Это позволит развивать обработку без переименования события и пересоздания подписки при каждом следующем этапе.

Документ уточняет целевую реализацию, не подтверждает её готовность. Он заменяет в исходной постановке выбор тестового публичного события для новых подписок; остальные требования P0/MVP0 сохраняются. Использовать существующий backend, SQLite, развёртывание и защищённый MCP tunnel. Новый сервис, универсальный orchestration framework и переделка аутентификации не нужны.

## Исходное состояние и граница доступа

На проверенном main `256a8cc83df8fd013673facfb977b86981a02837` уже существует тестовый маршрут `projects_hub.test_requested`, подписка с `project_id`, возобновляемый срок до 24 часов и отсутствие replay. Изменения защищённого tunnel слиты в [PR 163](https://github.com/onedayonemasterpiece/projects-hub/pull/163). Перед реализацией сверить развёрнутый commit и действительные подписки; merge не доказывает deploy и живую доставку. Сейчас создание тестового запроса владельцем требует активной проверенной подписки; сохранить эту защиту.

Текущий service principal имеет ограниченный scope `projects-hub:test` для активных и будущих проектов. Это не членство в workspace и не права владельца. Нельзя перенести существующий `project_grant()` в универсальные рабочие инструменты так, чтобы сервис автоматически получил чтение и изменение всех проектов.

Стабильный контракт первоначально допускает только тестовые запросы в пределах нынешних полномочий. Для live сервер должен проверять отдельное явное разрешение на конкретный проект, контекст обсуждения и допустимые действия. Если понадобится расширить постоянный доступ, требуется подтверждение владельца. Переход не должен незаметно создавать OAuth grants, credentials, обходить Origin/CSRF или превращать `actor_id` из контекста в доказательство полномочий.

## Протокольный контракт

Нормативная опора для ChatGPT: [MCP Events OpenAI](https://developers.openai.com/plugins/build/mcp-events). Связанный [design sketch](https://github.com/modelcontextprotocol/experimental-ext-triggers-events/blob/main/docs/design-sketch-proposal.md) является экспериментальным предложением; при расхождении следовать текущему контракту ChatGPT, в частности не копировать без сверки коды ошибок.

На аутентифицированном MCP endpoint сохраняются стандартные методы:

- `events/list`: описание события, `delivery: ["webhook"]`, `inputSchema` аргументов подписки и `payloadSchema` объекта `data`.
- `events/subscribe`: `name`, `arguments`, `delivery: {mode, url, secret}`, `cursor: null`; ответ содержит `id`, `refreshBefore`, `cursor: null`, `truncated: false`.
- `events/unsubscribe`: исходные `name`, `arguments`, `delivery: {mode, url}`. Одного subscription ID недостаточно.

Webhook содержит обычный JSON `{eventId, name, timestamp, data, cursor: null}`. Используются Standard Webhooks и заголовки `webhook-id`, `webhook-timestamp`, `webhook-signature`, `X-MCP-Subscription-Id`. Ответ 2xx подтверждает только приём. Повтор сохраняет `eventId`. Проверки callback, TLS, подписи и защита от SSRF обязательны.

Идентичность подписки: authenticated principal, callback, event name, канонические arguments. Refresh и замена signing secret обновляют существующую подписку. Реализовать конечный возобновляемый TTL; стабильность контракта не означает бессрочность. Подписка переживает restart, доставка прекращается при истечении или отзыве доступа. В этом этапе нет replay, polling, streaming, `gap` и `terminated`.

## Постоянное событие и его данные

Предлагаемый доменный контракт, не расширение стандарта MCP:

```json
{
  "name": "projects_hub.request.created",
  "arguments": {"project_id": "<project_id>"}
}
```

`project_id` — непустая строка существующего проекта, exact-match фильтр; schema запрещает дополнительные аргументы. В arguments не добавлять `mode`, `request_id`, `note_id`, nonce или флаг теста. Иначе каждый тест либо переход к рабочему запросу будет менять идентичность подписки.

Обязательные поля `data`: `project_id`, `request_id`, `mode` со значением `test` или `live`. Необязательные: `note_id`, `binding_id`, короткий `summary`. Идентификаторы — непустые строки; длина summary ограничена. Полный запрос, разрешения, nonce, тип работы и актуальный маршрут читаются из backend. Не передавать secrets или произвольные адреса назначения.

Использовать существующий `note_id` обсуждения и `project_discussion_entries`; не создавать параллельную сущность обсуждений только ради нового имени. Термин `discussion_id` исходной постановки здесь соответствует существующему `note_id`.

Совместимое расширение допускает новые необязательные поля `data`; получатель игнорирует неизвестные поля. Не менять значение прежних полей, обязательность, типы и фильтры. Ломающее изменение требует нового имени события и управляемой миграции. Обновление каталога требует rescan плагина; совместимость старых подписок проверяется тестом.

## Постоянные инструменты и обработчик

Зафиксировать имена и верхнеуровневые аргументы до подключения:

- `get_project_request(project_id, request_id)` возвращает авторизованную сохранённую запись, связанный event_id, режим, состояние, срок действия и разрешённый контекст; завершённая запись включает результат.
- `record_request_result(project_id, request_id, event_id, result)` сохраняет коррелированный результат и возвращает стабильный `response_id` и состояние backend.

Для теста `result` имеет строгую типизированную форму `{kind: "test_ack", nonce: "…", text: "…"}` с ограничениями длины и запретом дополнительных полей. Результаты live оформлять отдельными явно разрешёнными вариантами этого объекта, без смены внешней сигнатуры. Не вводить произвольный JSON для выполнения кода или передачи команд. Неизвестный kind отклоняется.

Сервер сверяет проект, запрос, связанное событие, principal, scope, режим и срок. Автор определяется аутентификацией. Нужный `actor_id` новых инструментов выводится из проверенного контекста сохранённого запроса без impersonation; legacy-обёртки сохраняют прежнюю сигнатуру и проверки. Идемпотентность обеспечивается уникальностью результата запроса и атомарной записью: одинаковый повтор возвращает прежний результат, конфликт отклоняется. `eventId` идентифицирует доставляемый факт, `request_id` — доменную работу, `response_id` — сохранённый ответ; они связаны, но не взаимозаменяемы.

Обработчик сначала читает запрос и сверяет его проект и event_id с подпиской и входящим событием. Завершённый повтор не запускает работу снова. Для test он получает свежий nonce из записи и сохраняет test_ack без внешних побочных эффектов. Nonce не сообщается заранее. Текст запроса и payload остаются недоверенными данными: они не разрешают менять код, доступы, маршруты или исполнять произвольную задачу.

Создание запроса и outbox согласованы транзакционно. Для пары событие–подписка существует одна запись доставки; повтор использует её. Собственная запись результата не порождает новый request.created и цикл ответов. Транспортная дедупликация не заменяет идемпотентность инструмента.

## Переход к обсуждениям и двум адресатам

Project-фильтр охватывает запросы выбранного проекта в пределах выданных полномочий. Сервер ограничивает фактическую доставку и доступ; отсутствие фильтра mode не является разрешением выполнять live. Тестовый grant не должен раскрывать реальные обсуждения.

Для MVP0 сохранять привязку проекта и `note_id` к проверенному Slack workspace/channel/thread и существующему контексту Mira/backend. У привязки нужны владелец/tenant, ACL, версия маршрута, допустимая передача данных и состояние отзыва. Использовать существующие editor ACL. Payload не может подменить назначение; актуальная привязка читается авторизованным инструментом.

P0 заканчивается сохранением ответа. Для MVP0 независимо учитывать: backend stored; Mira available либо доказанное delivered/acknowledged; Slack подтверждённый message ID либо ошибка/неопределённость. Сохранение в backend не означает пробуждение Mira. Slack-доставку реализовывать только через реально доступный разрешённый канал. После неопределённого send сначала проверять результат; не обещать exactly-once между системами.

## Миграция без повторной переделки

1. Добавить постоянные событие и инструменты до создания новой реальной подписки. Сохранить legacy test tools, данные и действующие подписки.
2. Проверить фактический список подписок и маршруты; исключить двойную эмиссию одного запроса через старое и новое событие одному получателю.
3. Если подписка на test_requested уже существует, переименование неизбежно требует одного согласованного перехода. Не обещать перенос её идентичности; не удалять и не останавливать её молча.
4. После перехода использовать прежние имя, project-фильтр, principal и callback для test и разрешённого live. Refresh, restart и совместимое поле не должны создавать новую подписку.
5. Смена проекта, callback, principal, имени события либо расширение полномочий рассматриваются отдельно. Отзыв доступа и последующее подключение могут требовать новой подписки. Текущая реализация включает `grant_id` в идентичность: новый auth grant даже для прежнего login может потребовать ещё одного согласованного перехода. Не обещать сохранение ID ценой расширения прежнего тестового grant.

## Приёмка

- Реальный discovery/catalog показывает постоянное событие и инструменты; subscribe проходит callback verification. Повтор и refresh сохраняют ID при неизменной идентичности.
- Один свежий test-запрос будит idle-dot через MCP Events, приводит к чтению nonce и сохранению ответа. Есть корреляция всех трёх ID и фактические времена. Slack wake и пользовательское подталкивание не подменяют проверку.
- Restart, refresh, дубли и конфликтующий результат проверены. Подписки и записи сохраняются; ошибочный повтор не перезаписывает ответ.
- После отдельного ограниченного разрешения безопасный live-сценарий проходит через ту же подписку при неизменной идентичности. Если действующая auth-модель требует нового grant, сначала явно выполнить предусмотренный разовый переход и не выдавать его за сохранение прежней подписки. До разрешения live недоступен. Произвольное выполнение задач не входит в тест.
- Добавленное необязательное поле не ломает прежнего потребителя. Неизвестные/некорректные аргументы, чужой проект, подмена note/binding и отозванный доступ отклоняются.

PASS ставится только по живому проходу на фактическом ChatGPT host. Пока нет подтверждённого пробуждения и сохранённого результата, указывать последний доказанный шаг и конкретный блокер. Этот addendum не разрешает подключение, создание credentials, новых подписок или live-действий без необходимых подтверждений владельца.

**Дата:** 6 октября 2026.

**Назначение:** полная постановка для отдельного запуска реализации.

## Короткая инструкция агенту реализации

Реализуй эту постановку до работающего прототипа Projects Hub. Прочитай [нормативную спецификацию](../product/20-basic-collaboration-and-personal-timeline.md), восстанови фактическое состояние свежего `main`, создай отдельную ветку и сначала покажи реальную совместную работу двух участников: A создает заметку в проекте, B видит ее, читает и отвечает. Затем доведи путь `заметка → сильный анализ → вопрос участнику → ответ / пропуск / позже → продолжение допустимого шага → личная сводка инициатору`. Работай последовательно до полного DoD ниже, не останавливайся на документации, макетах или unit-тестах. PR #87 не продолжай и не объединяй; его совместимые изменения можно выборочно использовать как исходный материал. Не перестраивай голосовой контур и не откатывай свежие исправления.

Явный запуск владельцем этой постановки разрешает обычные действия по ее реализации, проверке, исправлению и принятому в проекте пути поставки нового изменения. Повторно согласовывать рутинное сохранение заметки, принятый ответ или безопасный повтор той же операции не нужно. Само хранение постановки в репозитории такого запуска не означает. Сохраняются действующие ограничения доступа и внешних действий; эту постановку нельзя использовать для возобновления PR #87.

## 1. Продуктовый результат

У каждого участника одна личная активная переписка с Мирой через все разрешенные проекты. Прямо в переписке появляются функциональные блоки заметок, обсуждений, вопросов, задач и доски. Общими становятся явно созданные проектные объекты; личные разговоры участников остаются личными.

Человек может сказать «сделай заметку в проекте», получить сохраненный и структурированный материал, дать другому участнику возможность его прочитать и обсудить, а позднее продолжить работу по ответам. При входе Мира сначала кратко сообщает о важном, адресованном лично этому человеку, и только затем предлагает сводку общей активности. Пользователь свободен сразу заняться своей задачей.

Это небольшой законченный путь совместной работы. Для его реализации не нужны универсальный workflow engine, брокер сообщений, система голосований или месяцы предварительного построения инфраструктуры вопросов.

### Первая обязательная веха

**A создает настоящую заметку → файл записан в подключенный репозиторий и прочитан обратно → B в собственной авторизованной сессии видит и читает заметку без GitHub-входа → B оставляет связанный ответ → A видит этот ответ.**

Покажи этот путь до расширения аналитики и вопросов. После подтверждения вехи продолжай до остальных критериев этой постановки.

## 4. Границы архитектуры

### Мира и голос

Центральная Мира остается владельцем диалога, понимания намерения и выбора проекта через typed tools. Backend проверяет полномочия, сохраняет данные, выполняет заявленные операции и возвращает фактические результаты.

Владелец явно разрешил специализированную Gemini-обработку заметки. Это ограниченная операция `готовый текст → структурированный результат`, вызываемая в понятном процессе сохранения заметки. Она не становится скрытым параллельным маршрутизатором, вторым собеседником или заменой центральной Миры.

Аудио, Live session, VAD, interim/final/canonical transcription, reconnect и output продолжают идти через существующий единый shared audio pipeline. Прослушивание заметки и обсуждение используют тот же контур Миры. Не добавляй новый microphone listener, конкурирующий ASR или отдельного TTS-собеседника.

### Личная лента и общие объекты

Сохраняй одну действующую личную ленту на пользователя/workspace при переходе между проектами, reload и смене provider session. Явный «Новый разговор» обозначает границу эпизода/контекста в личной истории; он не создает проектный чат и не удаляет pending sources. Смена проекта сама это действие не выполняет. Сохрани существующую lease одного владельца Live на actor+conversation.

Каждое действие и объект содержат проверенный `project_id`. Мира использует явный проект из запроса и текущий контекст; backend не угадывает проект по ключевым словам. Смена фокуса не перепривязывает уже созданную заметку или вопрос.

Проектные `Note` и связанный `Discussion` доступны участникам по существующему ACL. Ссылки в личной ленте не предоставляют новых прав. В общие объекты попадает только намеренно сохраненный материал и адресованные ответы, а не вся личная транскрипция.

### Маленький устойчивый store

Достаточно расширить существующее хранилище заметками/связями, обсуждением, вопросами и небольшим журналом значимой активности. Сохраняй устойчивые ID и revisions там, где обновление может столкнуться с другим действием. Универсальный event sourcing и новая абстрактная платформа всех видов work items не требуются.

## 5. Заметка: от голоса до общего Markdown

### Создание

Мира вызывает существующий или добавленный typed tool создания заметки. Нужные смысловые аргументы: выбранный проект, исходный текст/ссылка на конкретный source fragment, необязательные заголовок и связь с текущим объектом. Идентичность автора и роли клиент не назначает.

Backend обязан:

1. Проверить actor и право создавать заметку в проекте.
2. Получить автора и **массив его ролей** из серверного membership. Сохранить этот снимок ролей рядом с заметкой; не доверять присланным `author_id`/`author_roles`.
3. Сохранить полный выбранный исходный текст до модельной обработки. Не подменять его выжимкой и не захватывать соседний личный разговор.
4. Создать устойчивый note ID и единственную карточку в ленте; повтор одного tool call не создает вторую заметку.
5. Запустить явную асинхронную Gemini-структуризацию через переиспользованный text pipeline.
6. Записать итоговый структурированный Markdown в **подключенный к этому проекту GitHub-репозиторий**, используя существующие binding и права. Не отправлять все заметки автоматически в inbox IdeaHub.
7. Прочитать сохраненный файл обратно, проверить содержимое и связать receipt/path/revision с той же заметкой. Только после этого утверждать, что файл сохранен в репозитории.

Если у проекта несколько разрешенных repositories, используй существующее назначение хранилища заметок либо закрепи его один раз в настройке проекта. Не спрашивай пользователя об одном и том же назначении при каждой заметке. Отсутствующий доступ обрабатывай существующим connection flow; не требуй PAT от обычного участника.

Проверь соответствие фактической visibility и состава доступа repository аудитории заметок. Ограниченную проектом заметку нельзя публиковать в public repo, прикрываясь app ACL. Непубличные заметки требуют совместимого непубличного binding; public repo допустим для явно установленной публичной аудитории. Закрепи это на уровне настройки проекта, без нового подтверждения на каждую заметку. При несовместимости сохрани принятый текст и покажи конкретный блокер до записи.

### Содержимое и статусы

Структура результата опирается на общий `SummaryPayload`: полезный заголовок, связный материал, выделенные идеи/вопросы/решения при их наличии, исходный текст и необходимые provenance-поля. Не создавай пустые разделы ради шаблона и не выдавай модельные предположения за решения автора. В частности, Gemini task suggestions остаются предложениями в документе: они не создают автоматически принятые поручения, assignees, backlog execution или разработку. Прямо высказанное пользователем поручение и выведенная моделью рекомендация должны различаться.

Metadata содержит project/note ID, автора, список ролей, время и необходимые source/model/schema refs. Публикуемая provenance относится к предназначенному проекту фрагменту и не открывает личные conversation/source IDs, полный разговор или аудио. Для ролей достаточно общей схемы с массивом; отдельный шаблон для каждой комбинации ролей не нужен.

Отдельно показывай готовность заметки и состояние дополнительного анализа. Простая заметка не обязана проходить сильную аналитику. При сбое структурирования исходный текст остается доступен; повтор продолжает ту же заметку. Не выдавай ошибку GitHub-записи за успешную завершенную материализацию.

### Чтение и ответ другого участника

B читает заметку через backend Projects Hub с проверкой проектного ACL, без GitHub-логина и токенов на клиенте. Отображай полезный Markdown без технического front matter, используя существующий безопасный renderer. GitHub-ссылка — дополнительный источник, а не единственный способ чтения.

Карточка дает действия **«Прочитать», «Прослушать», «Обсудить»** и доступ к связанным ответам. Участник дает содержательный ответ Мире и явно направляет его в обсуждение заметки. Тихие предусмотренные ответы доступны кнопками. Для первой вехи не нужно добавлять новую форму ввода или общий composer приложения.

Связанные ответы хранятся в небольшом `Discussion` этой заметки и видны согласно ее проектному ACL. Сохранение итогов личного обсуждения по команде «добавь к заметке / зафиксируй итоги» обновляет общий материал без повторного согласования. Всю беседу автоматически не публикуй.

## 6. Функциональные блоки в переписке и одна доска

Введи или дополни typed blocks в существующем renderer сообщений: заметка, обсуждение/набор вопросов, состояние анализа/задачи, доска и краткая сводка. Точные имена типов согласуй с актуальным кодом; не создавай параллельный renderer того же назначения.

Блок содержит устойчивые ссылки на канонические объекты и их актуальные состояния. Read/listen/discuss, варианты ответа, пропуск и переход к связанному объекту должны реально работать. Кнопка, которая только открывает старый общий popup, не выполняет это требование.

Повтор события, reconnect и обновление транскрипции обновляют существующий block ID. Не вставляй дубли карточек и не теряй их после reload. Типизированные данные не должны превращаться в исполнение произвольного HTML/JS из ответа модели.

**Одновременно смонтирован максимум один полноценный board renderer.** Остальные блоки досок остаются легкими ссылками/представлениями без загруженного в память графа всех объектов. Открытие другой доски сохраняет предыдущую и освобождает ее runtime. Раскрытие и закрытие полного экрана работают с тем же board ID и возвращают человека в прежнее место ленты.

Заметка отображается на доске как представление той же заметки. Из доски доступны ее чтение, прослушивание и обсуждение. Ручное перетаскивание, рисование, toolbar редактирования и свободный текстовый composer в этот срез не добавляй; изменения доски выполняются существующими разрешенными действиями Миры. Popup допустим для дополнительного чтения/раскрытия, но не заменяет inline-блок.

## 7. Анализ и вопросы как продолжение работы

### Запуск и общий контекст

По запросу анализа/обсуждения создай или используй существующий связанный job/task. Создание обычной заметки само по себе не запускает консилиум или разработку.

Сильная модель получает сохраненную заметку, ее актуальную версию и достаточный разрешенный контекст: используй существующие `context_mode=provided_only`, `evidence_bundle` и `request_key`. При необходимости запрошенного исследования сначала получи источники разрешенными tools и добавь их в bundle. Анализ не ограничен выделенными объектами доски: допустимы заметка, документ, задача, обсуждение и их версии. Результат — небольшой полезный набор рекомендаций и вопросов с явной аудиторией. Вопросы сгруппированы по заметке/задаче/проекту с общим вводным контекстом; для прототипа достаточно этих существующих связей, сложная кластеризация не нужна.

Вопрос хранит связь с предметом решения, породившим запуском и конкретным зависимым шагом, если он есть. Завершение analysis run не закрывает автоматически вопрос, нужный следующей стадии. И обратное: отмененная или изменившаяся задача не должна оживать от ответа на устаревший вопрос.

### Адресаты и ответы

Поддержи адресацию владельцу проекта, конкретному участнику и роли проекта. Для роли достаточна политика **первого принятого ответа уполномоченного участника**. У одного человека может быть несколько ролей. Владельца не делай запасным адресатом каждого вопроса без причины.

Проверяй текущие полномочия при чтении и ответе. Если роль не имеет подходящих участников, покажи необходимость назначения адресата вместо тихой потери вопроса. При одновременных ответах первое допустимое изменение фиксируется атомарно; второму участнику показывается уже принятый ответ, без молчаливой перезаписи.

Минимальные исходы:

| Действие | Значение |
| --- | --- |
| Содержательный ответ или вариант, включая отрицательный | Решение по конкретному вопросу принято; проверь зависимые шаги. |
| «Не знаю», «пропустим» | Сейчас содержательного ответа нет; вопрос не считается решенным, остальные доступные темы продолжаются. |
| «Позже» | Отложить для этого пользователя/обсуждения; вопрос остается открытым. Указанное человеком время сохраняется, но сложный планировщик не нужен. |
| Открыть, выбрать карточку, прочитать, переключить режим | Навигация и просмотр; это не ответ и не разрешение на продолжение. |
| Вопрос утратил смысл из-за изменения/отмены работы | Зафиксировать неактуальность с причиной; старый ответ не запускает отмененную работу. |

Пропуск или откладывание одним участником роли не скрывают вопрос от остальных адресатов. Разделяй существующий `blocking` признак и факт прочтения; прочитанное не равно отвеченному.

### Естественная дискуссия

Мира дает общий контекст один раз и обсуждает вопросы спокойным связным разговором. Пользователь может уточнять формулировку, развивать тему и одной репликой ответить на несколько вопросов текущей группы. Не заставляй выбирать карточку перед каждой естественной репликой.

Принятые ответы связываются с конкретными question IDs. Неоднозначность уточняется только там, где она реально меняет решение. Промежуточный transcript, шум уведомления, посторонний звук и команда «покажи вопросы» ничего не отвечают. Обновление canonical transcript не должно само повторять уже принятую mutation.

Режим из уведомления или карточки по умолчанию тихий: текст вопроса и содержательные кнопочные варианты, включая «не знаю / пропустить / позже». Голос — явный выбор. Появление вопросов не прерывает текущую речь, ввод, задачу или открытую доску.

## 8. Продолжение без открытого UI

Работа после ответа обязана продолжаться на backend, когда вкладка/приложение закрыты. `status/get/list` выполняют **только чтение** и не запускают фактическую обработку как побочный эффект опроса.

Сначала переиспользуй имеющуюся durable queue/worker. Если нужного исполнения нет, добавь **один небольшой bounded pump поверх существующего SQLite/store**, запускаемый lifecycle backend. Для него достаточно устойчивого pending/leased/result состояния, ограниченной выборки, истечения lease и ограниченных повторов с backoff. Сохрани или явно задай небольшие лимиты admission и параллельного исполнения; переполнение не создает безграничный in-memory список и не теряет уже принятый исходный текст. Отсутствие места возвращает понятное состояние ожидания/вместимости. Не добавляй broker, BPM или отдельную инфраструктурную платформу.

При принятии ответа атомарно сохрани ответ и намерение проверить/продолжить конкретную работу. Для одной принятой версии ответа и зависимого шага существует одно continuation intent. Повтор tool call, двойной тап, reconnect и повторный запуск worker не создают дополнительные принятые продолжения.

Worker проверяет актуальный вопрос, версию предмета и состояние зависимого шага. Не нужно строить общий DAG: достаточно реальных зависимостей текущего analysis/task шага. Неблокирующие вопросы и пропуски не останавливают независимую работу; все необходимые блокирующие решения открывают только соответствующий следующий шаг.

До внешнего запуска сохрани request/job identity. После неопределенного исхода сначала сверяй имеющийся внешний run/receipt, а не запускай вторую работу вслепую. Пользователь видит отдельно «ответ сохранен» и результат продолжения: в очереди, продолжается, завершено или требуется восстановление.

Ожидание человека освобождает model/inference slot. Приложение после reload читает фактическое состояние, а не восстанавливает запуск из локальной памяти. При завершении работы появляется запись личной активности инициатора; она не начинает самопроизвольную речь Миры.

### Один реальный owner-development resume

Подключи к тому же механизму **один фактический явно разрешенный owner execution в `needs_owner`**, а не только демонстрационную локальную задачу. Для приёмки подходит существующее выполнение либо воспроизводимо подготовленное ограниченное выполнение в рамках запущенной владельцем реализации; наличие случайно зависшей исторической задачи не является gate. После достаточного ответа владельца возобновляется этот же execution/этап через существующий provider path, с сохраненными request identity, проектом и исходным объемом. «Не знаю / позже», неполный ответ и просмотр оставляют необходимую зависимость ожидающей. Ошибку формата/verdict и обычный retry не выдавай за необходимость продуктового решения владельца.

Не выдавай обычному участнику owner-development tools. Ответ участника может дать факт для анализа, но не становится разрешением на owner implementation. Сохрани существующие owner-only проверки, один активный owner execution, ограничения очереди, времени, попыток/rework, ресурсов, разрешенных моделей и design/review/delivery. Не увеличивай bounds ради прохождения примера и не требуй нескольких параллельных Codex задач. Сама аналитика, рекомендация или сохранение заметки не разрешают новое выполнение разработки.

## 9. Приветствие и ненавязчивые уведомления

Используй существующий колокольчик/центр внимания либо добавь один компактный вход. Он доступен и при раскрытой доске. Открытие и смахивание уведомления не отвечают на вопросы.

При нейтральном входе/приветствии сначала кратко покажи важное, адресованное лично actor: ожидающие решения, вопросы, назначенные действия и относящиеся к нему результаты. Затем допустимо одно **общее предложение** необязательного обзора: «Есть новости по проектам. Рассказать?». Только после согласия перечисляй подробности общей активности, например «Ольга добавила две заметки…». Не зачитывай чужие общие новости внутри самого приглашения к сводке.

Если пользователь уже начал конкретный запрос, выполни его: не вставляй обязательный приветственный обзор поверх новой задачи. Приветствие не повторяется при каждом reconnect/status poll. Запуск приложения сам по себе не включает микрофон или озвучивание; в явно начатой голосовой сессии можно произнести короткое приветствие.

Сводка основана на значимых действиях других участников: заметка, связанный ответ, принятый результат. Не считай технические стадии обработки новостями и не выдавай изменение summary за новую заметку. Уважай ACL и персональное состояние просмотра. Достаточно простого журнала и курсора; рекомендательная система не нужна.

«Нет», «позже» и новая тема позволяют сразу продолжить работу. Не прочитанное/не отвеченное сохраняется в соответствующей очереди. Отложенный вопрос не навязывается снова при каждом приветствии; явный возврат или существенная сроковая/блокирующая граница делают его снова актуальным. Новые вопросы группируются, без звука на каждый элемент; используй существующую доступную доставку уведомлений. Первый обязательный результат — in-app очередь, колокольчик и сводка; богатые push-кнопки, новая гарантированная фоновая доставка и сложная временная политика не являются gate этого прототипа и не выдаются за проверенные без отдельной приемки.

## 10. Модели и ресурсы

Легкое структурирование заметки использует объявленный Gemini text pipeline. Более сильная аналитика выбирается по задаче и доступному существующему маршруту; обычный вопрос не запускает автоматически все модели по очереди.

Для NVIDIA действует разрешенный владельцем режим: два параллельных процесса под двумя разными проектными ключами, с соблюдением существующего лимитера. Новое согласование бюджета с владельцем для этих вызовов не требуется. Длительное ожидание ответа участника слот не занимает.

Дополнительная разрешенная Codex-лестница при известном остатке квоты **строго больше 10%**: Luna Medium → Luna High → Sol Low → Sol Medium → Sol High → Astra Low/Medium при необходимости. Это варианты выбора/повышения точности, а не обязательный проход всех уровней и не замена Kimi, DeepSeek или совета. Базовый Codex-участник совета — Luna Medium. Используй точные доступные model IDs из текущего каталога и действующие правила запуска provider; не выдумывай алиасы, квоту или платный fallback. Не понижай уже закрепленный сильный профиль owner-development анализа/ревью ради формального следования этой дополнительной лестнице.

## 11. Порядок реализации

1. **Заметка и второй человек.** Минимальные store/tool/UI изменения, GitHub materialization/readback, app reader, роли автора, Note/Discussion ACL, реальный ответ B. Покажи работающую первую веху.
2. **Общая лента и представления.** Typed функциональные блоки, reload/readback, доска как представление заметок, один mounted renderer, read/listen/discuss без общей формы ввода.
3. **Анализ и вопросы.** Один полный сильный анализ, общий контекст небольшой пачки, owner/member/role addressing, обычный голосовой разговор и тихие контекстные ответы.
4. **Backend continuation.** Переиспользованный worker либо один небольшой store-backed pump, атомарное принятие ответа, возобновление после закрытия UI и restart, отсутствие дублей и один фактический owner `needs_owner` resume с сохранением полномочий/границ.
5. **Личная сводка и поставка.** Значимая активность, приветствие в нужном порядке, необязательная общая сводка, проверка полного сценария, независимое ревью и существующий путь delivery нового изменения.

Сохраняй полезные checkpoints и сообщай о фактически работающем пути. Ранние результаты не являются поводом остановиться до полного DoD. Если обнаружен конкретный внешний блокер, сначала доделай все независимое, затем назови недоступную операцию и необходимое действие; не подменяй реальные ограничения гипотетическими согласованиями.

## 12. Проверка и фактический DoD

Используй две отдельные авторизованные идентичности A/B в разрешенном тестовом проекте и настоящий подключенный репозиторий. Переключение подписи автора в одном payload не считается вторым actor. Не обходи аутентификацию и не рассылай приглашения посторонним ради демонстрации. Внешняя приемка должна подтверждать фактическое сохранение и чтение; одних mocked integrations недостаточно.

Добавь целевые тесты реальных рисков и пройди обязательный существующий CI. Не дублируй огромные соседние suites и не расширяй voice-регрессию без конкретного затронутого риска. Проверяй этот продуктовый UI в доступном браузере/Android-контуре; не утверждай физическую приемку устройства, если ее не было.

| Проверка | Критерий приемки |
| --- | --- |
| A создает заметку | Исходный текст не потерян, Gemini-структура доступна, Markdown реально записан и прочитан обратно из правильного repo, повтор запроса не создает дубль. |
| Автор и роли | Реальный server-derived actor и массив ролей; подмененный клиентом автор/роль не принимается. |
| Рекомендации Gemini | Выведенная моделью задача остается предложением; не появляется принятое поручение/исполнение без соответствующего намерения пользователя. |
| B читает и отвечает | Отдельная сессия B видит заметку и Discussion без GitHub-логина; A видит сохраненный ответ. |
| ACL | Actor вне проекта не получает содержимое через note/discussion/board/question/brief или ссылку на объект; отозванное право проверяется при ответе. |
| Одна лента | Переход A между двумя проектами не создает обязательный новый разговор; объект остается в исходном проекте после смены фокуса и reload. |
| Inline и одна доска | Функциональные действия доступны внутри переписки; максимум один полноценный board renderer; закрытие/переключение сохраняет данные и не оставляет все графы в RAM. |
| Обсуждение | Мира дает контекст один раз, принимает уточнение и одну реплику по нескольким вопросам; исходные вопросы и принятые ответы связаны. |
| Тихий ответ и шум | Открытие карточки, выбор режима, interim text и звук уведомления не считаются ответами; голос включается явно. |
| Пропуск и «позже» | Нет ложного ответа/разрешения; независимые шаги продолжаются, блокируемый шаг ожидает; остальные адресаты роли не теряют вопрос. |
| Role race | Два одновременных допустимых ответа не перезаписывают друг друга и не порождают два continuation. |
| Закрытый UI и restart | После принятого ответа обработка идет без клиента; перезапуск backend на промежуточной стадии восстанавливает работу без потери и повторного принятого продолжения. `status` остается read-only. |
| Устаревший вопрос | Завершение analysis run не снимает нужный следующему шагу вопрос; отмененная работа не возобновляется по старому ответу. |
| Полный путь | Настоящая заметка → сильный анализ → вопрос B → ответ → допустимый job/task продолжен → A видит личный результат. |
| Owner resume | Явно разрешенный существующий либо воспроизводимо подготовленный ограниченный owner execution реально выходит из `needs_owner` после достаточного ответа и продолжает тот же объем; обычному участнику owner tools недоступны, bounds не расширены. |
| Приветствие | Лично адресованное раньше общей активности; общую сводку можно пропустить; конкретный новый запрос не прерывается обзором. |
| Совместимость | Свежие изменения main, PR #114/#115 и shared audio/dependency contracts сохранены; PR #87 остался PAUSED. |

В итоговом отчете приведи короткое воспроизводимое описание полного пути, ссылки на новый PR/результат поставки и разрешенные receipts сохраненного файла, фактические результаты проверок и только существенные оставшиеся ограничения. Различай реализованное, проверенное локально и реально доставленное пользователю. Не называй готовностью один лишь зеленый unit suite.

## 13. Что остается дальнейшим развитием

Сохрани как дальнейшие требования, не являющиеся условиями завершения ближайшего прототипа: семидневный гостевой просмотр/обмен доской и развитие совета моделей. Богатые интерактивные push-кнопки и сложные групповые/временные политики — возможные последующие расширения по реальной потребности.

Ручное редактирование canvas, несколько одновременно живых досок, универсальная workflow-платформа и отдельный проектный чат не являются отложенными обязательствами этой постановки: они не входят в выбранную владельцем модель.

Эти направления не объявляются реализованными и не отменяются. Текущая работа завершается по проверяемому пути двух участников, общей заметке, полезной дискуссии, устойчивому продолжению и спокойному личному приветствию.

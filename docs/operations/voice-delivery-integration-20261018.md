# Единая поставка голоса, анализа заметок и ответов Миры

Дата: **18 октября 2026**. Статус: **продолжение существующей работы; продуктовая приёмка открыта**.

Этот документ объединяет текущую native voice delivery, уже выпущенный intake голосовых заметок в my-data-hub и исследование эффективности Projects Hub в один порядок продолжения. Цель владельца — работающее голосовое взаимодействие на нестабильном мобильном интернете, сжатие в обе стороны, слышимый промежуточный ответ Миры при долгой работе и проверенная эффективность при **четырёх одновременно говорящих пользователях**. Полный перенос на Go/Rust остаётся гипотезой, которую нужно проверять измерениями.

Работа продолжается в исходных Claude PR: [Projects Hub #175][ph-pr] и [live-interaction #51][live-pr]. Исправление ресурсного SDK слито через существующий приватный [ai-resource-control #35][resource-pr]; это слияние само по себе не переключает потребителей и не выполняет миграции. Выпущенный [my-data-hub #48][mdh-pr] сохраняется как принятый этап. Объединяются продуктовый сценарий, контракты и доказательства; каждый существующий компонент сохраняет свою ответственность.

## 3. Один результат из двух существующих способов начать работу

### Живой разговор в Projects Hub

Мира получает исходное аудио через общий Live runtime. Отдельные captions служат проекцией для интерфейса; они не выбирают проект, не запускают скрытый анализ вместо Миры и не заменяют входное аудио текстом. Предметный анализ готовой заметки остаётся явной существующей capability. Мира читает сохранённые вопросы и решения того же пользователя, связывает ответы с конкретными вопросами и продолжает разговор после инструментов и успешных переходов capability.

### Законченная голосовая заметка из my-data-hub

1. **Исходник.** Intake сохраняет запись и итоговую расшифровку; источник анализа фиксируется как `{repository, path, commit_sha, transcript_sha256}`. Проекция анализа в изменяемом Markdown сохраняет ссылку на этот исходный снимок.
2. **Принятие.** Существующая приватная привязка доставляет intent в PH. `accepted`, `request_id` и `event_id` подтверждают долговечную передачу. Успех анализа подтверждается отдельным результатом. Повторная доставка сохраняет исходную логическую операцию и её IDs.
3. **Смысл и контекст.** Существующий обработчик анализа читает точный request, frozen manifest и все относящиеся к идее доступные материалы разрешённого idea-hub, в том числе проекты, ещё не зарегистрированные в PH. Лексический кандидат «задай мне вопросы» проверяется по смыслу всей записи. Цитата, отрицание и обсуждение функции получают объяснённое `not_requested`.
4. **Уточнение по необходимости.** При достаточном контексте voice-origin `question_start` принимает сразу `analysis_result`. При существенных пробелах создаётся существующий `question_package` с полезными вопросами. Пустой пакет означает `not_requested`; он не заменяет полноценный результат анализа без вопросов.
5. **Ответы.** Мира сохраняет реальные ответы владельца через существующий question lifecycle. Продолжение после вопросов начинается после явного завершения и опирается на сохранённые `answer_receipts`. `unknown`, `skip` и `later` сохраняют свой смысл. При паузе или частичном ответе новый анализ не стартует сам по себе.
6. **Результат.** Финал содержит основания, решения владельца, предложения, фактически выполненные изменения с readback и оставшуюся работу. Изменения канонических документов проходят через owning product, его grants, `expected_revision` и durable command ID.
7. **Доставка.** PH сохраняет и проверяет свой result artifact, делает его доступным в личном briefing Миры и отдаёт intake проекцию. Intake обновляет только свой блок исходной заметки с проверкой revision. Ссылка на актуальную исходную заметку отделена от ссылки на неизменяемый input snapshot. Получение уведомления на Android и presentation receipt проверяются отдельно.

Эти шаги следуют [действующему контракту](voice-note-analysis.md) и [выпущенному продолжению my-data-hub][mdh-report]. Фоновый анализ заметки — адресованная предметная работа; текущим голосовым разговором по-прежнему управляет одна Мира. Результат из inbox не становится повторно воспроизведённой пользовательской командой.

### Несколько связанных заметок

Связь устанавливается после чтения содержания через существующий `link_voice_analysis_sources`, с canonical intent, текущими revisions, immutable source refs и причиной связи. Соседство во времени — только повод исследовать материал. Каждый источник сохраняет свой provenance; уже открытые раунды работают со своим frozen manifest, новые источники входят в следующий раунд по контракту.

Отчёт my-data-hub фиксирует, что на момент проверки `link_voice_analysis_sources` отсутствовал в callable каталоге. До фактического readback этого инструмента приёмка сохранённых семантических групп остаётся открытой. Одна заметка может пройти свой полный цикл независимо от этого пробела. Две самостоятельные истории вопросов требуют явного решения о согласовании при `VOICE_HISTORY_CONFLICT`; ни одна история не отбрасывается. [Контракт](voice-note-analysis.md), [состояние выпуска][mdh-report].

## 4. Общие обязательные свойства

| Требование | Проверяемое поведение |
| --- | --- |
| Сжатие телефон ↔ сервер | Native uplink и downlink передают сжатые бинарные аудиофрагменты. PCM/base64, требуемые API внешнего провайдера, остаются на соответствующей границе сервера. Измерять wire bytes отдельно от исходного PCM и JSON envelope |
| Долговечность | ACK источника выдаётся после фактического commit. При отставании сохраняются bounded queues/backpressure и исходные IDs; очередь и повторная отправка не подменяют durable receipt |
| Нестабильная мобильная сеть | Потеря WSS переводит клиент в честное состояние локальной записи/ожидания. После восстановления источники доставляются без повторного смыслового исполнения старой речи. Явный buffered replay использует собственный логический turn и shared activity boundary |
| Stop и повторный Start | Локальный Stop останавливает микрофон и воспроизведение в рамках определённого контракта. Завершённый session/epoch не оживает от позднего события. Повторный Start сохраняет разговор и не повторяет выполненную внешнюю команду |
| Долгий инструмент | До окончания длительной работы слышна уместная короткая реплика Миры; затем приходит результат той же операции. Событие progress или текст в UI сами по себе не подтверждают слышимый ответ. Прерывание, новая речь и Stop подавляют устаревший progress |
| Captions и история | Текст связывается только с доказанным source/utterance и поколением провайдера. Неизвестная шкала времени или отсутствующие offsets дают явную недоступность привязки. Captions — необязательная проекция: её деградация не должна останавливать основной аудиодиалог. Каноническая история основного Live и временные captions имеют разный статус |
| Внешние эффекты и ресурс | Повторно используется исходный command/receipt; UNKNOWN сначала согласуется с фактическим состоянием. Sticky lease/key и правила admission сохраняются. Ошибка квоты не превращается в новый ключ или повторное исполнение инструмента |
| Существующий inbox | Сохраняются утверждённая приватная привязка и существующая подписка. Новые события обрабатываются адресно; старые заметки автоматически не сканируются и не перепосылаются. Voice-запрос с `slack=null` остаётся без назначения Slack |

Основания: [общая Live-архитектура][live-architecture], [центральная Мира](../product/12-central-live-agent.md), [voice analysis contract](voice-note-analysis.md), [исходные требования][native-spec]. Эти строки задают приёмку, а не утверждают, что каждый пункт уже пройден.

## 6. Быстрый цикл отладки и окончательная проверка

Основную повторяемую отладку вести напрямую в подготовленной локальной/серверной среде. GitHub Actions сохраняет роль воспроизводимой проверки кандидата и сборки релиза. Одни и те же Gradle tasks, assertions, известные аудиофразы и receipts используются в обоих местах; новый параллельный framework тестирования не вводится.

| Цикл | Существующая точка входа | Что фиксировать |
| --- | --- | --- |
| Быстрая web/bridge проверка | `web/tests/native-voice-bridge.test.mjs`, обычный TypeScript/Vite build | Инициализацию на поддерживаемом WebView, Start/Stop, реальный bridge contract; отдельный результат от Android audio |
| Backend/shared регрессия | Адресные existing tests соответствующих SDK/host/adapter | Исходный дефект, корреляцию, cancellation/UNKNOWN и сохранность, без нового общего test framework |
| Gradle без устройства | `gradle -p android testDebugUnitTest assembleDebug --stacktrace` | Java unit tests и сборку APK; JDK 17, Gradle 8.10.2, compile/target SDK 35 и точный shared pin. Эти задачи не требуют KVM |
| Android с настоящим audio path | `scripts/android_emulator_smoke.sh`, `NativeVoiceFlowTest`, тот же APK и pin из `.github/workflows/android.yml` | Mic waveform, сжатые originals, источник ответа, AudioTrack/playback receipt, outage/queue recovery, Stop/reopen; logcat и `voice-flow.json` при любом исходе |
| Настоящий провайдер | `devcoveer_pending_audio_canary.py`, отдельный `devcoveer_caption_clock_probe.py`, затем `devcoveer_native_voice_canary.py` | Реальные provider events и звук в нужной фазе, admission/cleanup, точные runtime/harness hashes; синтетический источник явно помечается |
| Анализ заметок | Существующие intake/outbox/PH test fixtures и адресное продолжение конкретного request | Source → intent → request/event → question/answer receipts → result → source projection/readback |

В `devcoveer_native_voice_canary.py` обычный `--run-provider` проверяет основной Live в штатной конфигурации: при `native_offset_clock=unverified` он не включает второй ASR посредством diagnostic observer. Два replay по-прежнему требуют всех известных целых фраз основного `input_transcript`, завершённых ходов и сжатых ответов, затем общей очистки. Дополнительный `--qualify-captions` явно включает прежнюю строгую диагностику; отчёт сохраняет независимый `primary_passed` и статус caption qualification. При явно запрошенных captions общий `passed` требует успеха обеих проверок. Ошибки socket, Stop, незакрытые sidecars/tasks и общий timeout всегда блокируют успех. Исправление шкалы ns не ослабляет исходные portion/offset guards и не меняет FAILED результата прежнего `clock-a3`.

Primary A2 выявил ограничение canary: нормальный бинарный `EPOCH_END` и срочный `output_interrupt` являются разными исходами. Отменённый source может быть полностью сохранён на сервере, но его tail не должен возобновлять live playback. Требование двух normal tail при наличии barge-in смешивало окончание и отмену; диагностический receipt должен различать их по известному source/connection. Совпадение полных входных фраз и общее завершение/очистка остаются независимыми критериями. Новый provider не вызывается для переоценки уже сохранённого A2.

В рабочей среде и на DevCoveer **KVM недоступен**. В рабочей среде также нет Android SDK/adb и звукового устройства; у проверенного DevCoveer — два CPU, нет доступных VMX/SVM и Android SDK. Перенос аппаратно ускоренного Android-прогона на эти среды сейчас технически не подготовлен. Backend и настоящие provider checks уже выполнялись напрямую; три адресных тестовых файла совместно дали **21 PASS за 1,48 s**, проверка shell-синтаксиса — PASS. Быстрые проверки кода остаются локальными, а полный Android audio path в текущей доступной инфраструктуре проверяется в Actions.

Gradle запускает instrumentation через `connectedDebugAndroidTest`, но для выполнения `AudioRecord`, `AudioTrack` и WebView всё равно нужен Android device/emulator: это прямо различено в [Android command-line testing][android-gradle]. На Linux аппаратно ускоренный эмулятор использует [KVM][android-kvm]. Настройка Gradle не создаёт отсутствующую виртуализацию.

Повторяемый local/Actions flow зафиксирован в [Android README](../../android/README.md). `--preflight` проверяет KVM до тяжёлой установки; точный system image проверяется по SHA-256 и кэшируется. Для полного прогона нужны отдельный SDK, disposable AVD, `PH_ANDROID_DISPOSABLE=1` и единственный явно выбранный `ANDROID_SERIAL`; наличие другого или физического устройства останавливает сценарий до изменяющих adb-команд. Каждый запуск использует свежий evidence directory. `--cleanup` удаляет только свои Pulse modules и свой Xvfb, сверяя marker и identity процесса; чужие default audio devices и данные предыдущего прогона сохраняются. Существующие Gradle tasks и `NativeVoiceFlowTest` остаются единой точкой выполнения.

Kaggle сейчас не выбран Android-стендом: доступность нужной виртуализации там не подтверждена, а перенос добавил бы второй lifecycle окружения и передачу APK/evidence. Для повторной локальной отладки полезнее подготовить Linux-хост с KVM и запускать тот же зафиксированный flow. Текущие две доступные локальные среды для полного Android audio E2E не подходят; это ограничение инфраструктуры, а не Gradle.

Эксперимент с одним `PULSE_LATENCY_MSEC=5` завершился **FAIL** в [run 39115240772][android-timer-before]: **850** HAL silence insertions, correlation первой фразы **0,134122**. Кандидат `5b676…` сохранил его и задал **`QEMU_AUDIO_TIMER_PERIOD=1000`** только процессу эмулятора. В опубликованном [QEMU audio timer source][qemu-audio-timer] значение выражено в Hz: default 100 Hz даёт 10 ms, 1000 Hz — 1 ms. В новом [полном прогоне][android-current] все audio assertions прошли; в logcat осталось **11** late/silence событий. Клиентский harness запускался без обеих переменных; исходные фразы, HAL, декодирование и строгие пороги сохранены. Это подтверждение всей проверенной конфигурации, а не изолированный эксперимент одной переменной: тот же кандидат изменил проекцию UI и подготовку стенда. Точный source provenance emulator binary и снижение CPU/RAM этим результатом не утверждаются.

Следующий archive-consumer run сохранил те же SDK audio bytes и emulator timer, но не повторил speaker PASS. В обоих серверных downlink originals PCM совпал с прежним run; отличие локализуется в начале фактического Android/host вывода. В новом logcat обнаружена интенсивная first-boot работа GMS и загрузка моделей Google Search. Это измеренный неконтролируемый фактор стенда, а не установленная единственная причина искажения. Следующий контролируемый профиль отключает только эти неиспользуемые пакеты disposable AVD, проверяет состояние и сохраняет отдельный receipt, не меняя WebView, сеть, сигналы или пороги. Ранний вызов `AudioTrack.play()` сам по себе не доказывает underrun: [Android API][android-audiotrack] имеет собственный start threshold. NativePlayer и опубликованный SDK не исправляются на основании одной этой гипотезы.

Отдельно устранена измеренная избыточность Android → WebView state updates. В [предыдущем отчёте][android-previous] **2768 из 2946** соседних переходов меняли только revision (**93,96%**); сохранение всех изменений любого публичного поля оставляет 179 snapshots из 2947. `NativeVoiceService` сравнивает полное публичное состояние до увеличения revision и сразу отправляет каждое реальное изменение, включая `queued_audio_ms`; ACK, запись аудио, `fsync`, Stop и shared callbacks не меняются. Android-регрессия `nativeVoicePublicationKeepsEveryPublicChangeAndCurrentSnapshot` прошла в run 39118401444. Новый сценарий сохранил **102** публичных snapshots; сценарии разной длительности не образуют CPU/RAM benchmark. Это оптимизация клиентской проекции; причинность в отношении HAL/backlog не заявляется.

Окончательный Android-прогон проходит тот же полный сценарий после устранения найденных ошибок. Direct PCM injection в server fixture, Activity/theme smoke и успешный Java build не подтверждают микрофон и playback. Повторяемые дефекты запуска и базового звукового пути проверяются автоматически до передачи очередной сборки владельцу.

[Исходная постановка][native-spec] отдельно требует **90-минутный Android-разговор** с renewal/recovery, idle/wake и воспоминанием раннего контекста, а также **настоящий Android handset**: screen-off/background, возврат WebView, permissions/audio focus, route change и signed update. Оба критерия ещё открыты. Эмулятор и prepared PCM их не заменяют. При недоступной физической приёмке постановка прямо разрешает выдать **release candidate с конкретными незакрытыми gates**; такой выпуск не объявляется полностью квалифицированным продуктом. Приёмка установленной iOS PWA остаётся следующим отдельным этапом; регрессии текущей PWA проверяются в этой поставке.

Существующий [release workflow](../../.github/workflows/android-release.yml) переведён на явный signed RC по `source_sha` и `android_run_id`; прежняя автоматическая публикация stable по push удалена. До чтения signing secrets validator сверяет source и реально проверенное дерево, текущую попытку run и digest артефакта, шесть Android-тестов, восемь audio assertions и согласованный shared package. Подписанный APK должен сохранить production package/certificate, иметь возрастающий versionCode и RC versionName. Публикация — immutable prerelease вне stable latest, без перезаписи прежних assets; неизвестный исход сначала согласуется с readback. Runtime/provider и совместимая серверная пара проверяются отдельно до передачи сборки владельцу. Debug package не становится production update и его данные автоматически не переносятся.

## 7. Эффективность: принятый порядок вместо полной переписи сейчас

Исследование [Go/Rust][go-report] не измерило выигрыш переноса Projects Hub и не установило Python как причину задержки Start. Opus/AAC уже выполняются нативными библиотеками PyAV/FFmpeg. Проверенные codec/storage pools и byte bounds полезны, однако синхронные store calls из async-пути, общий SQLite lock, внешнее ожидание под lock, RPC queue и интеграция RKB требуют отдельной работы.

| Приоритет | Продолжение в существующей реализации | Критерий результата |
| --- | --- | --- |
| 1. Закончить текущий голос | Сохранить пройденный Android audio E2E и повторить его на точном released SDK consumer; разобраться с провалом полной первой фразы у реального провайдера. Сохранить подтверждённый pending progress и проверить его слышимость в клиенте. Дополнительные captions при недоказанной привязке остаются явно деградированными | Цепочка аудио, reconnect и Stop проходит на точном кандидате; источники и receipts сохранены; ограничения ASR/captions отделены от результата основного голоса |
| 2. Освободить event loop | Применить существующий bounded storage executor ко всем относящимся к голосу обращениям к store, которые сейчас ждут lock/fsync синхронно | Отдельные lock/commit timings; сохранены порядок, FULL durability и ACK после commit |
| 3. Ограничить ожидание инструментов | Задать bound/queue age для DevCoveer pending queue и deadline от admission; сохранить одного владеющего MCP worker, reconciliation и исходные task IDs | Переполнение и истечение ожидания видимы; control path отзывчив; внешний task не запускается дважды |
| 4. Сократить подтверждённые лишние ожидания | Адресный HTTP connection pooling; сужение измеренных lock spans в collaboration/development | Меньше queue/lock wait без нарушения конфликтующих mutations и ревизий |
| 5. Подключить реальный RKB | Установить evidence-returning delegate стандартного server entry point с текущей авторизацией, остаточным deadline, pending job ID и readback | Настоящие разрешённые evidence доступны Мире; неготовый BGE даёт честное pending/fallback |
| 6. Измерить четыре разговора | Сопоставимый paced mixed-load сценарий с captions, durable storage, project reads и RKB | CPU/PSS/RSS/cgroup, задержки и рост очередей измерены при сохранении всех функций |
| 7. Проверить compiled замену при остаточном ограничителе | Go для цельного shared runtime либо Rust/native для доказанно дорогого kernel | Та же нагрузка/качество/ACL/storage/resource/recovery дают значимое улучшение всего процесса и хоста |

Пункты 2–5 — продолжение найденных механизмов, а не уже внесённые этой документацией изменения. Исследование языков не должно задерживать исправление работающего базового голосового пути. Полная миграция backend рассматривается после сравнения, если стоимость доменных функций и сопровождения оправдана доказанным улучшением.

### RKB и общий бюджет

По проверенному RKB source быстрый E5 — один локальный ONNX-процесс, BGE — Kaggle-only с очередью, vector search — Supabase с локальными ACL/текстами. Четыре пользователя не требуют четырёх копий E5. Перенос PH не устраняет external inference, очередь Kaggle или расходы других служб. Кодовое ограничение ожидания BGE — до 0,8 s; общий deadline поиска 2 s не доказан, поскольку у вложенных операций свои пределы. [Assessment, раздел 5][go-report].

Снимок из assessment: 7,25 GiB MemTotal, около 3,00 GiB MemAvailable, 1,86 GiB занятого swap, около 5,01 GiB свободного диска. Это состояние общего хоста в момент чтения; ни активный swap thrashing, ни RSS/PSS самого PH из этих значений не следуют. Заданные владельцем 2 vCPU / 8 GB требуют проверки фактических quotas и расходов каждого процесса.

Mixed-load сценарии: один голос; четыре голоса с captions и project reads; те же четыре плюс один настоящий RKB request; burst из четырёх RKB requests; тот же сценарий при обычной фоновой индексации/разработке. Начать с controlled provider boundary для воспроизводимости локальных расходов, затем отдельно проверить настоящие provider/RKB. Для четырёх одновременных пользователей использовать четыре разрешённых actor-контекста в действующей admission policy. Четыре разговора одного actor — отдельное изменение policy, если такой сценарий потребуется.

Фиксировать длительность и число наблюдений, CPU и PSS/RSS/cgroup memory, рост на сессию, event-loop lag, queue/lock/storage wait, swap I/O/pressure, time to first audible output, время Stop и восстановления. Для RKB — warm/cold, queue wait, pending/fallback и полезность evidence. Измерять весь процесс и общий хост при одинаковых источниках, codecs, quotas, durability и фоне. Малый набор наблюдений показывать как отдельные значения, без убедительных на вид p99.

Ориентир assessment — 20–30% CPU headroom и 1–1,5 GiB MemAvailable под целевой нагрузкой — остаётся предлагаемым параметром калибровки. Он не является уже принятым SLO, измеренной ёмкостью или новым hard limit.

## 8. Порядок завершения и вопросы владельцу

1. Довести speaker waveform archive-consumer до прохождения на зафиксированном AVD profile, сохранив прежний PASS и новый FAIL по их точным source. Подтверждённую в A2 полную клиентскую отправку PCM отделить от неполных final transcripts и отменённого ответа; сохранить failed result и partial receipts. Сохранить успешный pending-a3 receipt и подтвердить слышимый progress в клиентском пути. Caption clock проверять отдельно; недоступная дополнительная проекция не должна бессрочно задерживать основной голос.
2. Выпустить и развернуть совместимый кандидат через существующий release path; сохранить readback установленного исполняемого пакета и результат post-release smoke. Явно указать состояние handset, 90-минутной проверки и обязательных release checks. Если физическая приёмка недоступна, использовать разрешённый постановкой статус release candidate, не заявляя полную квалификацию. Выпущенный my-data-hub повторно переключать только при дефекте, требующем нового кода.
3. Автоматизировать и пройти техническую цепочку source → intent → result/projection с тестовыми источниками, затем продолжить адресный свежий owner request через реальный контекст и ответы. Одна доказанная цепочка не означает автоматическую приёмку сохранённых групп заметок или уведомления телефона.
4. Внести оставшиеся адресные store/queue/RKB изменения и измерить целевые четыре разговора. Привязать ресурсный вывод к воспроизводимому варианту всех компонентов.
5. Вернуться к выбору Go/Rust только с измеренным оставшимся ограничителем и сопоставимым кандидатом.

Новых принципиальных решений владельца для продолжения текущих исправлений не требуется.

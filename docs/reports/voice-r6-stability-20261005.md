# Voice R6 stability release — 2026-10-05

Product version: 0.1.33.

## Physical report and evidence

Android 0.1.32 physical acceptance exposed two independent failures:

1. Mira playback developed increasingly audible gaps during longer use.
2. After parallel Live use and a Projects Hub restart, new Live session creation repeatedly returned HTTP 429.

Production logs separated the two failures. The 429 responses were local `LIVE_BUSY` decisions returned by Projects Hub in a few milliseconds, before a provider call. A previously WSS-attached session had emitted `socket_gap` and remained detached while the product's 180-second client-liveness window still counted it against the per-actor session cap.

For the playback failure, production retained complete provider audio turns (including responses with 24 audio events / ~359 kB and 25 events / ~421 kB) without a matching provider interruption. The shared browser player, however, applied the full 400 ms startup jitter reserve whenever its scheduled playback queue underflowed. Repeated delivery jitter inside one answer could therefore create repeated user-audible 400 ms silences.

## Changes

Shared `live-interaction` 0.3.24 (PR #45, merge `a86221d6b58eeca3df72d8f32c8d8bf44e126305`) keeps the 400 ms reserve only for the first audio run of a provider response. Later underflow in the same response uses a 50 ms recovery cushion and emits `playback_underflow`. The response-level first-output timing marker is no longer regenerated by a mid-response underflow.

Projects Hub now reclaims abandoned WSS sessions without weakening active-session isolation:

- a new start may immediately replace a same-resource session only when that prior session actually used WSS and is now detached;
- a detached session for another resource is reclaimable after a 15-second grace, beyond the browser's bounded reconnect window;
- an attached socket is never reclaimed by this admission cleanup;
- a fresh duplicate that has not attached WSS remains rejected with `LIVE_BUSY`;
- product client-liveness timeout is reduced from 180 seconds to 30 seconds as a backstop.

Browser and Python consumers are pinned to the exact shared 0.3.24 merge commit. Product version is bumped to 0.1.33, which triggers the signed Android release workflow.
